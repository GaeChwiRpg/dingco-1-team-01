## 1. 권한 · 역할

**문제** — 접수 주체와 판정 주체가 다릅니다. 고객이 자기 문의의 분류를 고칠 수 있으면 검증이라는 말이 성립하지 않습니다.

**어떻게** — `ROLE_CUSTOMER` / `ROLE_AGENT` / `ROLE_MANAGER` 셋으로 나눴습니다.

- 고객 — 접수, 그리고 **본인 소유 문의만** 조회 (소유자 스코프)
- 상담원 — 검토 큐 조회와 최종 분류 확정
- 매니저 — 통계·설정값 조회

접수는 고객만 됩니다. 상담원이 대리 접수하는 흐름은 열지 않았습니다.

**설계 판단 하나** — 권한을 **역할 계층(RoleHierarchy)으로 누적**했습니다. `MANAGER > AGENT > CUSTOMER`. 역할마다 권한을 딱 끊으면 상급자가 하급자 화면을 못 보는 상태가 됩니다.

**실제로 잡은 버그** — 인증은 통과했는데 매핑이 없는 경로면, 스프링이 내부적으로 `/error` 로 **ERROR 디스패치**를 하고 그 디스패치가 시큐리티 필터 체인을 다시 탑니다. 그래서 404 로 나가야 할 응답이 401 로 덮였습니다. `/error` 를 `permitAll` 로 열어 해결했고, 상태 코드가 원래 의미대로 나가는지 테스트로 고정했습니다.

## 2. 핵심 트랜잭션

**문제** — 여러 테이블을 함께 바꾸는 지점이 있습니다. 중간에 실패하면 절반만 반영된 상태가 남습니다.

**어떻게** — `@Transactional` 을 정확히 세 군데에만 뒀습니다. 단건 read 에는 안 붙입니다.

| | 경계 | 하는 일 |
| --- | --- | --- |
| ① | `InquiryIngestService.receive` | 문의 저장 |
| ② | `ClassificationService.verifyAndPersist` | 판정 행 저장 + 문의 상태 전이 + 조건부 큐 삽입 |
| ③ | `ReviewService.confirm` | `final_category` 기록 + 상태 전이 + 큐 항목 RESOLVED |

여기가 제일 오래 고민한 부분입니다.

**①과 ②를 한 트랜잭션에 두지 않았습니다.** 묶으면 분류 실패가 접수까지 롤백시킵니다. 고객은 202 를 받았는데 행이 없는 상태가 되죠. 고객에게 나간 응답이 거짓이 되면 안 됩니다.

**대신 생기는 문제** — ②가 실패하면 문의가 `RECEIVED` 로 남습니다. 그래서 그 상태로 10분 넘게 있는 건수를 `stuckReceived` 게이지로 뽑습니다. **없앨 수 없는 구멍이면 최소한 관측 가능하게 만든다** — 이게 저희 원칙입니다.

**②에 감사 표본 큐 삽입을 같이 넣은 이유** — 밖으로 빼면 실패했을 때 실제 감사 비율이 설정값 미달이 됩니다. 그러면 오분류율의 **분모가 조용히 줄어듭니다.** 측정 장치가 고장 났는데 숫자는 계속 나오는 상태가 되는 거죠. "부차적인 건 트랜잭션 밖으로" 라는 일반론은 외부 의존성에만 적용했고, 측정 장치에는 적용하지 않았습니다.

## 3. 검색 · 필터

**문제** — 상담원이 보는 검토 큐입니다. 격리된 건이 쌓이니 필터와 페이징이 필요합니다.

**어떻게** — `status` + 기간으로 좁히고 `created_at ASC` 로 정렬합니다. 최신순이면 오래된 항목이 영원히 안 처리됩니다.

**인덱스를 감으로 붙이지 않았습니다.** 문서에 "이 쿼리는 이런 실행 계획이 나올 것이다" 를 먼저 적고, MySQL 8 에 문의 **10만 행**(99,481)을 심은 뒤 `EXPLAIN` 을 떴습니다.

- 예상 3건이 **전부 일치**했습니다.
- `(status, received_at)` 복합 인덱스가 range 스캔과 정렬을 함께 커버해서 **filesort 가 없습니다.** DESC 정렬은 `Backward index scan` 으로 처리됐습니다.
- 인덱스를 걷어낸 대조군은 `type=ALL` + `Using filesort` 로 떨어집니다. 이 차이를 evidence 에 같이 남겼습니다.

**안 만든 인덱스도 있습니다** — 기존 인덱스와 선행 컬럼이 같고 이름만 다른 걸 또 만들면, 조회 이득은 0 인데 write 비용만 늘어납니다. 인덱스는 read 를 사기 위해 write 를 파는 거래고, 거래인 이상 값을 확인하고 해야 한다는 게 원칙이었습니다.

**N+1** — 큐 목록에서 항목마다 `Inquiry` 와 `InquiryClassificationResult` 를 지연 로딩하면 `1 + 5×2 = 11` 회가 나갑니다. `@EntityGraph` 로 조인해서 **11회 → 2회**(목록 1 + 페이징 COUNT 1)로 줄였고, 적용 전후 쿼리 수를 세서 기록했습니다.

**이 API 에서 일부러 안 준 것** — 격리 사유(`reason`)와 `confidence`, 임계값을 응답에도 파라미터에도 넣지 않았습니다. 감사 표본은 **정의상 `confidence >= threshold`** 라, 두 값을 주면 뺄셈 한 번으로 100% 식별됩니다. `reason` 만 가려서는 소용이 없습니다.

## 4. 캐시

**문제** — 같은 내용의 문의가 반복됩니다. "환불해주세요" 는 하루에 수백 건 옵니다. 매번 LLM 을 부르면 비용이 그대로 나갑니다.

**어떻게** — 본문을 정규화해서(소문자화, 공백·문장부호 정리, 주문번호·연락처·금액 마스킹) `normalized_key` 를 만들고, 2단으로 찾습니다.

```text
1단 Redis (normalized_key)  → hit : AI 호출 없음
2단 DB 조회                  → hit : AI 호출 없음 + 캐시 put
miss                        → AI 호출
```

**여기서 지표를 헷갈리면 안 됩니다.** "캐시 hit rate = AI 절감률" 로 쓰면 틀립니다. Redis 가 비어도 DB 가 막아주기 때문에 **절감률은 항상 hit rate 이상**입니다. 그래서 두 숫자를 따로 계측합니다.

**실측** — 문의 1000건을 실제 접수 경로로 통과시켰습니다.

| | 값 |
| --- | --- |
| Redis hit 비율 | 0.454 |
| AI 절감률 (reused / 1000) | **0.490** |

그 차이 0.036 이 **"Redis 없이 DB 만으로 막은 몫"** 입니다. 이 값을 알아야 Redis 를 계속 쓸지 판단할 수 있습니다.

**측정 지점을 지키려고 신경 쓴 것** — SDK 클라이언트만 스텁으로 바꾸고 `AiClassificationService` 는 실제 빈을 그대로 돌렸습니다. 호출 카운터가 그 서비스 안에 있어서, 서비스째로 목을 끼우면 카운터가 안 올라 **측정 지점 자체가 사라집니다.** Redis 도 실제 컨테이너를 띄웠습니다.

**덤으로 확인한 것** — 같은 키가 동시에 유입되면 둘 다 아직 커밋 전이라 AI 를 중복 호출합니다. 락으로 막지 않고 **수용**했습니다. 막으려면 키 단위 직렬화가 필요한데 그건 접수 경로를 느리게 만들고, 중복 호출은 절감률만 깎을 뿐 정확성은 해치지 않습니다. 대신 손실분을 측정에 기록했습니다.

**2단 DB 조회의 우선순위** — 사람이 확정한 답(`final_category IS NOT NULL`)을 먼저 찾고, 없을 때만 `verdict = AUTO_ACCEPTED` 를 씁니다. **쿼리를 두 번 칩니다** — 우선순위를 `ORDER BY` 식으로 표현하면 filesort 가 확정이고, `LIMIT 1` 로 최신 한 건만 뽑으면 사람 확정 행을 지나칩니다.

**재사용을 재사용하지 않습니다.** 2순위의 `verdict = AUTO_ACCEPTED` 등치 조건이 `REUSED` 를 걸러냅니다. 체인이 생기면 원본이 틀렸을 때 전파 범위를 추적할 수 없습니다.

**캐시 덮어쓰기는 한 방향입니다** — 사람 답은 AI 답을 덮고, AI 답은 사람 답을 덮지 않습니다. 그래서 ②의 put 은 기존 값이 `source=HUMAN` 이면 건너뜁니다. 이 검사를 GET → 판단 → SET 으로 쪼개면 그 사이에 사람 확정이 끼어들어 덮여버려서, **Lua 스크립트 하나로 원자적으로** 처리합니다.

**통계 캐시는 별개입니다** — 대시보드 숫자는 TTL 10초. 안 그러면 Actuator 가 스크랩할 때마다 전수 count 를 칩니다. 큐 삽입·확정에는 evict 를 걸지만, 재사용 자동 확정에는 안 겁니다. 빈도가 높아서 상시 비게 되고, "변경 빈도 << 조회 빈도" 전제가 무너집니다.

## 5. 비동기 · 이벤트

**문제** — LLM 호출은 1~2초 걸립니다. 접수 API 안에서 부르면 고객이 그 지연을 그대로 먹습니다.

**어떻게** — 저장 후 `AFTER_COMMIT` 시점에 `InquiryReceivedEvent` 를 발행하고, 리스너가 `@Async` 스레드풀에서 분류를 돌립니다. 응답은 이미 나간 뒤입니다.

그래서 **200 이 아니라 202 Accepted** 로 줍니다. '완료' 가 아니라 '접수했고 처리는 나중' 이라는 뜻이고, 바디의 status 도 아직 분류 전이라고 정직하게 담습니다.

**왜 `AFTER_COMMIT` 인가** — 커밋 전에 발행하면 롤백된 문의를 분류하게 됩니다. 존재하지 않는 행을 읽으러 가는 거죠.

**부하를 걸어서 실제로 잡은 결함이 두 개입니다. 두 번째가 첫 번째 수정이 만든 것이라 더 중요합니다.**

1. **큐 포화 시 이벤트가 버려져 분류가 통째로 유실**됐습니다. 재현한 뒤 `CallerRunsPolicy` 로 바꿔서, 큐가 차면 버리는 대신 **호출한 스레드가 인라인 실행**하게 했습니다. 느려지는 건 보이지만 사라지는 건 안 보이니까요.

2. 그런데 인라인 실행이면 분류가 **접수 스레드에서 돌고**, 그러면 트랜잭션 ②가 ①의 트랜잭션에 합류합니다(`REQUIRED` 기본값). ①이 이미 정리되는 중이면 `no transaction is in progress` 로 터지면서 판정이 사라집니다. 그래서 ② 두 입구를 `REQUIRES_NEW` 로 바꿨습니다 — 매달린 트랜잭션을 suspend 하고 자기 트랜잭션을 새로 엽니다.

   **애노테이션만 붙이고 끝내지 않았습니다.** `@Transactional` 은 자기 클래스 내부 호출이면 프록시를 안 타서 조용히 무시됩니다. 호출 지점을 전수 확인하고(리스너에서만 호출), 운영 빈 그대로 부하를 다시 걸어 **유실 0** 을 확인했습니다.

**어떻게 확인하나** — 접수 API 응답시간 p95 를 재고, AI 지연이 거기 묻어나오는지 봅니다. 캐시 hit 건과 AI 호출 건의 응답시간이 비슷해야 제대로 떼어낸 겁니다.

## 6. AI 보조 기능

**하는 일** — 문의 본문을 10종 카테고리 중 하나로 분류하고, `confidence` 를 같이 반환하게 합니다. 프롬프트로 `{"category": ..., "confidence": 0.0~1.0}` JSON 을 강제합니다.

**그런데 이 프로젝트의 주제는 분류가 아니라 그 confidence 를 안 믿는 겁니다.** 세 겹입니다.

**첫째, 응답 값을 검증합니다.** 4가지 — `confidence` 필드 존재 / `0.0 <= confidence <= 1.0` / `category` 필드 존재 / 그 값이 `InquiryCategory` 10종에 있음.

**순서가 중요합니다. 이 검증은 임계값 비교보다 앞입니다.** 뒤에 두면 `1.5` 같은 값이 이미 자동 확정을 통과한 뒤가 되고, 그 건은 자동 확정되면서 동시에 신뢰도 구간 집계에서 사라집니다.

**그리고 clamp 하지 않습니다.** `1.5 → 1.0` 으로 자르면 최상위 구간에 "AI 가 1.0 이라 신고한 건" 과 "1.5 를 잘라낸 건" 이 섞입니다.

**둘째, 실패를 삼키지 않습니다.** 파싱 실패도 `@Retryable(3)` 대상이고, 소진되면 `@Recover` 에서 `verdict = FAILED` 로 판정 행을 남기고 `CLASSIFY_FAILED` 로 큐에 넣습니다. 이때 `category` 와 `confidence` 는 **둘 다 null** 입니다.

**왜 0 을 안 쓰냐면** — 0 으로 저장하면 최하위 구간에 "AI 가 스스로 0 이라 신고한 건" 과 "응답이 깨진 건" 이 같이 들어갑니다. 성격이 다른 둘이 한 버킷에 있으면 그 숫자를 읽을 수 없습니다. 실패 사유는 컬럼이나 enum 을 늘리지 않고 **구조화 로그**로 남깁니다.

**셋째, 임계값을 넘겨도 표본을 뽑습니다.** 자동 확정 건의 5% + 재사용 건의 5% 를 `AUDIT_SAMPLE` 로 큐에 넣습니다. 그리고 **상담원에게 감사 표본이라고 알리지 않습니다** — 알리면 평소보다 신경 써서 보고, 측정값이 실제보다 좋게 나옵니다. `suggestedCategory` 는 남기므로 앵커링 편향이 남고, 그래서 **측정된 오분류율은 하한값으로 해석**합니다.

**사람이 확정한 답도 감사 대상입니다.** 주제가 "AI 를 안 믿는다" 가 아니라 **"자동으로 확정된 것을 안 믿는다"** 라서, 사람 답이라도 다른 문의로 자동 전파되는 순간 같은 검증을 겁니다. 오히려 "사람이 정했다" 는 사실이 신뢰의 근거가 돼서 아무도 의심하지 않기 때문에 더 위험합니다.

**최종 산출물** — "AI 가 confidence 0.9 이상이라고 말했을 때 실제 오분류율이 몇 %인가." 이게 이 프로젝트가 내놓는 숫자입니다.

## 필수 6개 밖에서 추가로 · 30초

"여기까지가 필수 6개고, 하나 더 넣었습니다.

**동시성 — 락을 하나로 통일하지 않고 경합 성격에 따라 다르게 골랐습니다.**

**같은 문의가 두 번 분류되는 것**은 조건부 UPDATE 로 막습니다. `SET status=? WHERE id=? AND status='RECEIVED'` — 검사와 갱신을 한 문장에 담아 DB 에 맡기고, 갱신 0행이면 이미 처리된 것으로 보고 반환합니다. 읽고 나서 판단하면(check-then-act) 그 사이에 다른 스레드가 끼어듭니다. 안 막으면 같은 문의가 큐에 2건 들어가서 상담원이 두 번 보고, 오분류율 분모가 부풀어 오릅니다.

UNIQUE 제약을 안 쓴 이유도 있습니다 — 제약 위반을 같은 트랜잭션 안에서 잡아 재조회하면 Hibernate 의 rollback-only 마킹 때문에 `UnexpectedRollbackException` 으로 실패합니다. 재시도를 트랜잭션 밖으로 빼는 구조가 따라오죠. 그래서 조건부 UPDATE 를 골랐습니다.

**두 상담원이 같은 항목을 확정하는 것**은 상태 검사와 `@Version` 낙관적 락을 **둘 다** 씁니다. 상태 검사만으로는 동시에 `PENDING` 을 읽은 경합을 못 막고, `@Version` 만으로는 시간 차 요청까지 경합으로 오보합니다. 두 상황이 다르니 409 안에서도 `code` 를 다르게 줍니다."

## 마무리 · 20초

"정리하면, 필수 6개를 다 넣었는데 넣었다는 것보다 중요한 게 하나 있습니다.

여섯 개 전부 **'이걸 넣으면 대신 이게 나빠진다'** 가 따라붙습니다. 트랜잭션을 나누면 `RECEIVED` 로 방치되는 건이 생기고, 캐시를 쓰면 옛 답이 잠시 재사용되고, 인덱스를 붙이면 write 가 느려집니다.

저희는 그 대가를 숨기지 않고 **측정 항목으로 만들었습니다.** 그게 이 프로젝트에서 제일 신경 쓴 부분입니다."
