# AI 호출이 실패했을 때 정말 3번 다시 부르는지 재봤다 (측정 4 · TRI-55)

> **한 줄 요약** — AI 를 부르는 데 실패했을 때 ① 정말 3번 다시 부르는지 ② 그래도 안 되면
> 상담원이 볼 목록에 들어가는지 ③ 몇 번 불렀는지 DB 에 제대로 적히는지 ④ 개발자에게 알림이
> 실제로 가는지, **일부러 실패를 내서 네 가지를 눈으로 확인한 기록**이다.
>
> 여기 있는 숫자는 전부 직접 돌려서 나온 로그와 DB 값이다. **AI 에게 물어본 추정치는 하나도 없다.**

## 1. 어떤 문제가 있었나

AI 를 부르다 보면 실패한다. 그런데 실패에는 두 종류가 있다.

| 종류 | 예 | 다시 부르면? |
| --- | --- | --- |
| **잠깐 삐끗한 것** | 네트워크가 순간 끊김, 서버가 잠시 바쁨 | 다시 부르면 대개 된다 |
| **계속 안 되는 것** | 열쇠(API key)가 틀림, AI 가 계속 이상한 답을 줌 | 몇 번을 불러도 안 된다 |

**이 둘을 구분하지 않고 전부 "실패"로 처리하면**, 잠깐 삐끗한 것까지 전부 상담원이 손으로
분류해야 하는 목록(검토 목록)에 쌓인다. 사람이 안 해도 될 일을 하게 되는 것이다.

그래서 **다시 부르기(재시도)** 를 붙였다. 이 문서는 그게 **정말 붙어서 도는지**를 확인한 기록이다.

## 2. 왜 굳이 또 재나 — 이미 테스트가 있는데

`RetryingAiClassifierTest` 라는 테스트가 이미 있고 통과한다. 그런데 그것만으로는 부족하다.

이 프로젝트에서 재시도·비동기 처리는 **스프링이 대신 감싸주는 방식**으로 동작한다.
`@Retryable`(다시 불러라), `@Async`(다른 스레드에서 돌아라) 같은 표시를 코드에 붙여두면
스프링이 그 클래스를 몰래 한 겹 감싸서 그렇게 만들어 준다.

**여기에 함정이 있다.** 감싸는 조건이 하나라도 어긋나면 — 예를 들어 같은 클래스 안에서
자기 함수를 부르면 — **표시가 통째로 무시된다.** 그런데 이때 오류도, 경고 로그도 안 난다.
그냥 한 번만 불리고 끝난다. **기능은 멀쩡히 동작하는 것처럼 보이므로 아무도 모른다.**

기존 테스트는 그 클래스 하나만 떼어내서 직접 부른다. 그래서 **감싸는 게 실제로 걸렸는지는
볼 수 없다.** 그걸 보려면 앱을 통째로 띄워서 접수부터 저장까지 실제 경로로 돌려야 한다.
이 문서가 그 일을 한다.

## 3. 확인해야 할 것 4가지 (TRI-55 티켓이 요구한 것)

| # | 확인할 것 | 어디서 봤나 | 결과 |
| --- | --- | --- | --- |
| ① | 재시도가 **몇 번** 도는지 | 통합 테스트 + 실제 앱 로그 | ✅ 설정대로 3번 |
| ② | 마지막에 **검토 목록에 들어가는지** | 통합 테스트 + 실제 앱 DB | ✅ 사유 `CLASSIFY_FAILED` 로 1건 |
| ③ | **몇 번 불렀는지가 DB 에 맞게 적히는지** (`attempt_count`) | 통합 테스트 + 실제 앱 DB | ✅ 실제 호출 수와 일치 |
| ④ | **Sentry(오류 알림 서비스)에 알림이 실제로 도착하는지** | 실제 앱 + Sentry 조회 | ✅ 도착 (이벤트 1건) |

## 4. 전체 흐름 — 무엇이 어디서 도는가

```text
고객이 문의를 남긴다
      │
      ▼
① 문의 저장 ─────────────► 고객에게 "접수됐습니다" 즉시 응답
      │                      AI 결과를 기다리지 않는다 (실측 0.16초)
      │
      │ 저장이 확정되면 "문의 들어왔다" 신호를 보낸다
      ▼
분류 담당이 다른 스레드에서 깨어난다   ← @Async 가 하는 일
      │
      ▼
  AI 를 부른다
      │
      ├─ 실패 ─► 2초 쉬고 다시 ─ 실패 ─► 4초 쉬고 다시 ─ 실패 ─┐
      │                                                        │
    성공                                                  3번 다 씀
      │                                                        │
      ▼                                                        ▼
② 결과 저장                                        「끝내 실패」로 확정
   판정 = 자동 확정                                  · 판정 = FAILED
   검토 목록에 안 들어감                             · Sentry 로 알림 (1건만)
                                                     · 검토 목록에 넣기
```

**쉬는 시간이 2초 → 4초로 늘어나는 이유**: AI 가 아파서 실패하는 중인데 쉼 없이 계속 조르면
더 나빠진다. 그래서 실패할수록 조금씩 더 기다린다. 이걸 **뒤로 미루기(백오프)** 라고 부른다.

**용어 몇 개만 미리 풀어둔다.**

| 이 문서에 나오는 말 | 뜻 |
| --- | --- |
| **트랜잭션 ②** | 분류 결과 저장 + 문의 상태 바꾸기 + 검토 목록에 넣기를 **한 덩어리로** 처리하는 곳. 중간에 실패하면 전부 되돌아간다 |
| **검토 목록** | 상담원이 손으로 분류를 확정하는 화면의 대기줄. DB 테이블은 `inquiry_review_queue` |
| **판정(`verdict`)** | 이 분류를 어떻게 처리했는지. `AUTO_ACCEPTED`(자동 확정) / `NEEDS_REVIEW`(확신 부족) / `FAILED`(끝내 실패) 등 |
| **`attempt_count`** | AI 를 **실제로 몇 번 불렀는지** DB 에 적어두는 칸 |
| **`@Recover`** | 재시도를 다 써버렸을 때 **마지막으로 딱 한 번** 도는 함수에 붙이는 표시 |
| **Sentry** | 오류가 나면 개발자에게 알려주는 외부 서비스 |

## 5. 첫 번째 측정 — 통합 테스트로 (언제든 다시 돌릴 수 있는 쪽)

### 5-1. 어떻게 했나

**한 일을 순서대로 적으면 이렇다.**

1. `ClassifyRetryMeasureIT` 라는 테스트를 새로 만들었다. 앱을 **통째로 띄우는** 테스트다
   (`@SpringBootTest`). 그래야 2번에서 말한 "감싸는 게 실제로 걸렸는지"를 볼 수 있다.
2. DB 는 **진짜 MySQL 8.0** 을 쓴다. 테스트가 시작될 때 도커로 잠깐 띄웠다 지우는 도구
   (Testcontainers)를 이 프로젝트가 이미 쓰고 있어 그대로 붙였다.
3. **AI 를 부르는 부분만 가짜로 바꿔치기했다**(`AiClassificationService` 를 mock 으로 교체).
   이 가짜가 매번 실패를 던지게 해서 일부러 실패를 만든다.
4. 문의를 접수시킨다(`InquiryIngestService.receive`). 그러면 실제 서비스와 **똑같은 경로**로
   신호가 나가고, 분류 담당이 다른 스레드에서 깨어나 AI 를 부르기 시작한다.
5. 분류 결과가 DB 에 저장될 때까지 기다렸다가, 저장된 값과 로그를 읽는다.

### 5-2. 이렇게 정한 이유 (판단이 갈릴 수 있는 곳)

**왜 하필 `AiClassificationService` 를 가짜로 바꿨나 — 더 아래를 건드릴 수도 있었는데.**
더 아래(Anthropic SDK)를 건드리면 SDK 가 오류를 어떻게 바꾸는지까지 같이 재게 된다.
그런데 **지금 재려는 건 재시도·기록·검토 목록이지 SDK 가 아니다.** 그리고 진짜 API 를 부르면
매번 결과가 달라져서 다시 돌릴 수가 없다.

**왜 쉬는 시간(2초·4초)을 줄이지 않았나.** 줄이면 테스트가 빨리 끝난다. 하지만 그러면
**실제 설정이 아니라 테스트용 설정의 동작을 재는 것**이 된다. 재시도 간격 자체가 확인 대상이라
(기다리는 동안 스레드가 묶이므로 — D-047 ⓔ) 실제 값 그대로 돌렸다. 그래서 한 경우당 6초쯤 걸린다.

**다시 돌리는 방법**: `./gradlew test --tests '*ClassifyRetryMeasureIT'`

### 5-3. 무엇이 나왔나 (2026-08-10)

> **측정 환경** — Java 21.0.5 · Spring Boot 3.3.13 · Spring Retry 2.0.12 · MySQL 8.0(도커).
> **설정값** — `max-attempts: 3`(총 3번 시도) · `initial-backoff-millis: 2000`(첫 대기 2초) ·
> `multiplier: 2.0`(대기 시간을 2배씩) · `max-backoff-millis: 10000`(대기 상한 10초).
> ⚠️ **설정이 바뀌면 아래 숫자는 그대로 무효다.** 다시 재야 한다.

세 가지 경우를 만들어 돌렸다.

| 경우 | 실제로 부른 횟수 | `attempt_count` | 판정 | 종류/확신도 | AI 답 원문 | 접수→저장 |
| --- | --- | --- | --- | --- | --- | --- |
| **A. 아예 답을 못 받음** | **3** | **3** | `FAILED` | 둘 다 비어 있음 | 없음 | 6,194 ms |
| **B. 답은 받았는데 못 읽음** | **3** | **3** | `FAILED` | 둘 다 비어 있음 | **남아 있음** | 6,043 ms |
| **C. 두 번째에 성공** | **2** | **2** | `AUTO_ACCEPTED` | `DELIVERY` / `0.950` | 남아 있음 | 2,094 ms |

**표를 읽는 법.**

- **A 와 B 를 나눈 이유**: 「전화를 못 걸었다」와 「전화는 걸렸는데 상대가 알아들을 수 없는 말을
  했다」는 다른 문제다. 프롬프트를 고쳐야 하는 건 B 뿐이라, B 는 **AI 가 준 답 원문을 남긴다.**
  A 는 받은 게 없으니 남길 것도 없다.
- **「실제로 부른 횟수」가 기준값이다.** 이건 로그나 DB 를 읽은 게 아니라 **가짜로 바꿔친 객체가
  실제로 몇 번 불렸는지를 센 값**이다. 그래서 `attempt_count` 가 맞는지 대조하는 잣대가 된다.
  둘이 어긋나면 DB 에 적히는 숫자를 믿을 수 없다는 뜻이 된다. → **세 경우 다 일치했다.**
- **C 가 2인 것이 핵심이다.** 여기가 1 이면 재시도가 아예 안 걸린 것이고, 3 이면 성공했는데도
  계속 부른 것이다. 둘 다 잘못이다.

### 5-4. 쉬는 시간도 설정대로였다

B 경우의 로그에 찍힌 시각을 그대로 뺀 값이다.

```text
15:11:41.823   1번째 호출
15:11:43.829   2번째 호출   → 2.006초 뒤   (설정: 첫 대기 2초)
15:11:47.830   3번째 호출   → 4.001초 뒤   (설정: 2초 × 2.0배)
```

설정에 적어둔 값이 **실제로 그 간격으로 동작한다.** 코드에 적힌 것과 도는 것이 같다는 뜻이다.

### 5-5. 검토 목록에는 어떻게 들어갔나

| 경우 | 검토 목록 행 | 사유 | 분류 결과 id |
| --- | --- | --- | --- |
| A (끝내 실패) | 1건 | `CLASSIFY_FAILED` | 채워짐 |
| C (두 번째에 성공) | **0건** | — | — |

**C 가 0건인 것이 재시도를 붙인 이유 그 자체다.** 잠깐 삐끗한 실패는 다시 불러서 해결됐고,
그래서 상담원 화면에 **아예 나타나지 않는다.** 재시도가 없었다면 이 문의도 사람 손으로 갔을 것이다.

### 5-6. 반대 방향은 여기서 안 쟀다 — 「큐 삽입만 실패하면 판정도 되돌아가나」

위 A 경우는 **판정 저장과 큐 삽입이 둘 다 성공**한 결과다. 그럼 **큐 삽입만 실패하면 앞서 저장한
판정도 함께 되돌아가는가?** 이 문서는 그걸 재지 않았다 — **측정 3(TRI-73)이 이미 잰 자리**다.

**트랜잭션 ②는 네 가지를 한 덩어리로 한다.**

```text
문의 상태 바꾸기 → 문의 행에 결과를 복사해 두기 → 분류 결과 저장 → 검토 목록에 넣기
└──────────────────────── @Transactional 하나 ────────────────────────┘
```

> **「문의 행에 결과를 복사해 두기」가 뭔가** — 분류 결과는 `inquiry_classification_result`(원본)에
> 저장되는데, **같은 값을 `inquiries` 테이블에도 한 번 더 적는다**(`current_category`·`current_confidence`).
> 목록을 보여줄 때마다 두 테이블을 붙여 읽으면(조인) 느리기 때문이다. 이렇게 **읽는 속도를 위해
> 일부러 같은 값을 두 곳에 두는 것**을 「역정규화」라고 부른다 (`GLOSSARY.md`).
>
> **넷이 한 덩어리여야 하는 이유가 여기 있다** — 중간에 하나만 실패하고 나머지가 남으면
> **원본과 복사본이 서로 다른 말을 하게 된다.**

**이 네 단계는 별도로 구현한 게 아니라 `@Transactional` 하나로 보장된다.** `ClassificationService`
에 그 애노테이션이 **딱 한 번** 붙어 있고, 감사 표본 삽입도 "부차적이니 나중에"라며 밖으로
빼지 않는다 (D-012) — 빼면 감사율이 설정값 미달이 되어 측정 8ⓐ 의 분모가 조용히 줄어든다.

**실측은 측정 3 에 있다** (`evidence/measurement-3-rollback.md`, TRI-73, 2026-08-09). 검토 목록
저장소를 목으로 바꿔 `save` 가 예외를 던지게 하고 확인한 결과다.

| 확인 항목 | 실측 |
| --- | --- |
| 분류 결과 저장이 되돌아가는가 | 결과 행 **0건** ✅ |
| 문의 원문은 남는가 | 그대로 조회됨 ✅ |
| 문의 상태가 `RECEIVED` 로 남는가 | 상태 전이도 함께 롤백 ✅ |
| 임계 시간 뒤 `stuckReceived` 가 오르는가 | 0 → **1** ✅ |

**측정 3 과 측정 4 는 같은 트랜잭션 ②를 반대편에서 본다.**

```text
측정 4 (이 문서)   AI 호출이 실패했을 때  → ②가 FAILED 로 정상 저장되는가
측정 3 (TRI-73)    ②의 저장이 실패했을 때 → 앞서 저장한 것까지 되돌아가는가
```

**둘이 합쳐져야 ②가 완결된다.** 어느 한쪽만 보면 "실패를 기록은 하는데 그 기록이 깨질 때는
어떻게 되나"(또는 그 반대)가 빈칸으로 남는다.

⚠️ **감사 표본 삽입이 붙으면 이 확인을 한 번 더 해야 한다.** TRI-65 의 완료 조건에
*"큐 삽입을 실패시키면 분류 결과 저장도 함께 되돌아간다"* 가 들어 있다 — 측정 3 이 잰 것은
**감사 삽입이 없던 시점의 ②**이고, 단계가 하나 늘면 트랜잭션 경계도 다시 확인해야 한다.

## 6. 두 번째 측정 — 진짜 앱을 띄워서

통합 테스트는 실패를 **가짜로 만들어** 냈다. 그래서 "진짜 API 가 거절할 때도 똑같이 도는가"는
아직 확인되지 않았다. 그걸 보려고 앱을 실제로 띄웠다.

### 6-1. 어떻게 했나

1. 같은 코드(브랜치 `feat/p2-classify-retry`, 재시도 커밋 `02c038f`)를 도커로 빌드했다
   (`docker compose up -d --build app`).
2. **AI 열쇠(`ANTHROPIC_API_KEY`)에 일부러 틀린 값을 넣고** 띄웠다. 이러면 진짜 Anthropic 서버가
   401(인증 거절)로 되돌려준다 — 가짜가 아니라 **진짜 실패**다.
   값은 환경변수로만 넘겼고 파일 어디에도 적지 않았다.
3. Sentry 에서 이 측정 건만 골라 보려고 환경 이름을 `ENV=measure4` 로 띄웠다.
4. `POST /api/inquiries` 로 문의 1건을 접수시켰다.

### 6-2. 접수는 AI 를 기다리지 않았다

```text
접수 응답  : HTTP 202, 0.160 초   (06:39:20.976Z)
분류 종료  :                       (06:39:28.236Z)  ← 접수 응답보다 7.3초 뒤
```

**이 두 줄이 이 프로젝트의 큰 전제 하나를 그대로 보여준다.** 고객은 0.16초 만에 접수 확인을
받았고, AI 분류가 실패로 끝난 건 그로부터 7초쯤 뒤 다른 스레드에서였다.
문의 저장(①)과 분류 저장(②)이 **실제로 분리돼 있다**(D-031).

만약 붙어 있었다면 고객이 7초를 기다렸을 것이고, 분류가 실패했으니 **접수 자체가 취소**됐을 것이다.

### 6-3. 기동할 때 찍힌 로그 — 설정끼리의 관계도 성립했다

```text
classify_retry_ready  maxAttempts=3 initialBackoff=PT2S multiplier=2.0 maxBackoff=PT10S
                      callTimeout=PT30S worstCasePerInquiry=PT1M36S threads=8 awaitTermination=PT2M
classify_executor_check          ok threads=8 connections=20
classify_executor_shutdown_budget phase=PT40S awaitTermination=PT2M worstCaseTotal=PT2M40S
```

숫자 두 쌍이 중요하다.

- **분류 1건의 최악 소요 96초 < 끌 때 기다리는 시간 120초** → 배포하느라 앱을 껐다 켤 때
  **재시도 중이던 분류가 중간에 잘리지 않는다** (D-047 ⓒ). 잘리면 그 문의는 조용히 사라진다.
- **분류 스레드 8개 < DB 연결 20개** → 분류가 DB 연결을 다 써버려서 **접수 API 가 연결을 못 얻는
  일이 없다** (D-047 ⓑ). 이게 어긋나면 원인이 AI 인 줄 알기 쉬운데 실제로는 연결 부족이다.

### 6-4. 분류 담당이 남긴 로그

```text
classify_failed reason=API_ERROR inquiryId=1 attempts=3
classification_persisted inquiryId=1 verdict=FAILED resultId=1 attempt=3
```

진짜 API 를 상대로도 **3번 부르고 끝냈다.**

### 6-5. DB 에 실제로 저장된 값

MySQL 에 직접 접속해서 읽은 그대로다.

```text
inquiry_classification_result   (분류 결과)
  id=1  inquiry_id=1  category=NULL  confidence=NULL  verdict=FAILED
        attempt_count=3  raw_response=NULL  model=NULL

inquiry_review_queue            (검토 목록)
  id=1  inquiry_id=1  classification_result_id=1  reason=CLASSIFY_FAILED
        status=PENDING  version=0

inquiries                       (문의)
  id=1  status=UNCLASSIFIED  current_category=NULL  current_confidence=NULL
```

**여기서 팀 규칙을 지켰는지 확인한 것들.** 각 줄이 왜 중요한지 함께 적는다.

| 확인한 것 | 왜 중요한가 |
| --- | --- |
| 종류·확신도가 **둘 다 비어 있다**(`NULL`) | 확신도에 `0` 을 넣으면 "AI 가 스스로 0이라고 답한 건"과 "답이 깨진 건"이 한 칸에 섞여 나중에 통계를 못 읽는다 (D-022) |
| 검토 목록 행에 **분류 결과 id 가 채워져 있다** | 실패한 건도 결과 행을 남긴다. 안 남기면 상담원이 "왜 여기 있는지" 근거를 못 본다 (계약 B) |
| `version=0` 으로 시작한다 | 두 상담원이 같은 항목을 동시에 확정하는 걸 막는 장치의 시작값 (계약 B) |
| 문의 쪽 **복사본**(`current_*`)도 비어 있다 | 원본이 비어 있으면 복사본도 비워둔다. 임의로 채우면 둘이 어긋난다 (D-039) — 복사본이 무엇인지는 6-6 참조 |
| 문의 상태가 `UNCLASSIFIED` 다 | **AI 는 문의를 `CLASSIFIED`(분류 완료)로 못 옮긴다.** 그 전환은 사람만 할 수 있다 (불변 규칙 2) |

### 6-6. 덤 — 정상 경로도 한 번 확인했다

**여기까지 온 측정에는 큰 구멍이 하나 있다. 진짜 AI 가 분류에 성공한 적이 한 번도 없다.**

- 통합 테스트(5장)는 AI 를 부르는 부분을 **가짜로 바꿔치기**했다. C 경우의 「두 번째에 성공」도
  가짜가 미리 정해진 답을 돌려준 것이다
- 실제 앱(6장)은 **일부러 틀린 열쇠**를 넣었으니 성공할 수가 없다

측정 4 가 재려던 것은 「실패했을 때 어떻게 되나」라서 그 자체로 잘못은 아니다. 다만 **"실패는
확인했는데 성공은 확인 안 한" 상태**로 두면, 나중에 정상 경로가 깨져도 이 문서를 근거로
"확인했다"고 착각하게 된다. 그래서 열쇠를 정상으로 되돌린 뒤 문의를 하나 더 넣어봤다.

**넣은 문의**: "어제 주문한 상품이 아직 배송 시작도 안 됐어요. 언제 출발하는지 알려주세요.
주문번호 20260809-334422"

**결과 (2026-08-10)**

```text
접수 응답  : HTTP 202, 0.182 초   (07:38:20.132Z)
분류 완료  :                       (07:38:22.641Z)   → 2.5초 뒤
로그       : classification_persisted inquiryId=2 verdict=AUTO_ACCEPTED resultId=2 attempt=1
```

```text
inquiry_classification_result
  id=2  inquiry_id=2  category=DELIVERY  confidence=0.950  verdict=AUTO_ACCEPTED
        attempt_count=1  model=claude-sonnet-5
        raw_response={"category": "DELIVERY", "confidence": 0.95}

inquiry_review_queue   → 이 문의에 대한 행 0건

inquiries
  id=2  status=CLASSIFIED  current_category=DELIVERY  current_confidence=0.950
```

**여기서 처음 확인된 것들.**

| 확인된 것 | 값 |
| --- | --- |
| **AI 를 한 번에 성공하면 `attempt_count` 가 1 이다** | 앞선 측정은 전부 2·3 이라 1 은 처음이다 |
| **`model` 칸에 실제 모델 이름이 들어간다** | `claude-sonnet-5`. 실패 경로에서는 계속 비어 있었다 |
| **`raw_response` 에 AI 가 준 답이 그대로 남는다** | 프롬프트를 손볼 때 볼 수 있는 원본 |
| **자동 확정되면 검토 목록에 안 들어간다** | 확신도 0.950 ≥ 기준값 0.8 이라 사람 손이 필요 없다 |
| **문의 쪽 복사본에도 같은 값이 들어간다** | `current_category`·`current_confidence`. 아래 「복사본이 뭔가」 참조 (D-011) |
| **문의 상태가 `CLASSIFIED` 로 간다** | 자동 확정 경로다. 불변 규칙 2 가 금지한 것은 **격리된(`UNCLASSIFIED`) 문의를 AI 가 확정하는 것**이지 이 전이가 아니다 |

#### 「복사본」이 뭔가 — 같은 값이 두 곳에 적혀 있다

위 결과를 보면 **같은 분류 결과가 두 테이블에 들어 있다.**

```text
inquiry_classification_result  (분류 결과 테이블)   ← 원본
    category = DELIVERY          confidence = 0.950

inquiries                      (문의 테이블)        ← 복사본
    current_category = DELIVERY  current_confidence = 0.950
```

**왜 굳이 두 번 적나.** 상담원이 문의 목록을 볼 때 "이 문의가 어떤 종류로 분류됐는지"도 함께
보여야 한다. 그런데 분류 결과는 **다른 테이블**에 있어서, 목록 100건을 뿌리려면 매번 두 테이블을
붙여 읽어야(조인) 한다. 느리다. 그래서 **문의 행에 최신 판정을 복사해 둔다.**
이렇게 **읽는 속도를 위해 일부러 같은 값을 중복해 두는 것**을 「역정규화」라고 부른다.

**대신 위험이 따라온다.** 복사본이므로 **원본과 어긋날 수 있다.** 분류 결과는 `DELIVERY` 인데
문의 쪽에 옛 값이 남아 있으면, 상담원 화면과 실제 데이터가 서로 다른 말을 한다.

그래서 팀 규칙(D-011)이 **"복사본은 판정이 확정되는 트랜잭션 안에서만 갱신한다"** 이다.
다른 자리에서 손대면 어긋난다. 위 결과에서 두 테이블의 값이 같다는 것은 **그 복사가 제대로
됐다**는 뜻이다.

> 도서관의 대출 대장(원본)과 책 표지에 붙은 「대출중」 스티커(복사본) 같은 것이다.
> 스티커 덕분에 책을 집어들자마자 알 수 있지만, 대장과 스티커가 어긋나면 사고가 난다.

**⚠️ 헷갈리기 딱 좋은 우연이 하나 있다.** 이 확신도 `0.950` 은 5장 C 경우에서 **가짜가 돌려주도록
적어둔 값과 같다.** 진짜 AI 가 우연히 같은 답을 냈을 뿐이다.

**둘을 가르는 근거는 확신도 값이 아니라 이것들이다.**

1. **실제 앱에는 가짜로 바꿔친 것이 아예 없다** — 도커로 뜬 앱이라 진짜 `AnthropicClient` 를 쓴다
2. **`model` 칸이 채워져 있다** — 실제 응답에서 읽은 모델 이름이다
3. 같은 앱이 조금 전(6-4)에는 **진짜 401** 을 받았다 — 아래 설명 참조

#### 401 이 왜 「진짜와 통신했다」의 증거인가

401(Unauthorized)은 **인증 정보가 없거나 틀려서 거부당했다**는 뜻이다. 그건 맞다.
여기서 짚는 건 다른 것이다 — **그 401 을 누가 만들었는가.**

| | 가짜(mock)로 실패를 낸 경우 | 6-4 의 실제 앱 |
| --- | --- | --- |
| 어디까지 갔나 | **내 컴퓨터 안**에서 예외를 던지고 끝 | 인터넷 건너 **Anthropic 서버까지** |
| 실패를 누가 정했나 | 테스트 코드에 내가 적어둠 | **상대 서버가 판단해 거부** |

**401 은 서버가 보내주는 응답이다.** 서버에 닿지도 못했다면 401 이 아니라 연결 실패(타임아웃,
주소를 못 찾음)가 났을 것이다. 그래서 「401 을 받았다」는 곧 「요청이 실제로 그 서버에 닿았다」가 된다.

가장 단단한 증거는 응답 안에 있다.

```json
{"type":"error","error":{"type":"authentication_error","message":"invalid x-api-key"},
 "request_id":"req_011CdtcHJEEjyH4dCW8o8CF8"}
```

**`request_id` 는 Anthropic 이 요청을 받으면서 발급한 번호**다. 우리 코드로는 만들어낼 수 없는
값이라, 이게 있다는 것 자체가 그쪽 서버가 요청을 실제로 처리(하고 거부)했다는 뜻이다.

**⚠️ 이 응답을 다시 보고 싶다면 Sentry 로 간다.** 다른 두 곳에는 없다.

| 어디 | 있나 | 이유 |
| --- | --- | --- |
| **Sentry** ([`JAVA-SPRING-BOOT-B`](https://dingcodingco.sentry.io/issues/JAVA-SPRING-BOOT-B)) | ✅ | 최종 실패 때 보낸 이벤트의 예외 메시지에 통째로 담겼다 |
| 도커 앱 로그 | ❌ | 정상 키로 되돌리며 **컨테이너가 교체**돼 사라졌다 |
| DB 의 `raw_response` | ❌ | **설계상 저장하지 않는다.** 이 칸은 「AI 가 준 분류 답」 자리이지 HTTP 오류 본문 자리가 아니다 |

**이건 측정 4 의 범위가 아니다.** 정상 경로가 한 번 돈다는 것만 확인했을 뿐,
**AI 가 얼마나 자주 맞히는지·자신 있게 틀리는지는 여기서 아무것도 말하지 않는다.**
그건 정답이 붙은 문의 50건으로 재는 측정 1·8ⓐ(TRI-77)의 몫이다. 표본 1건으로 정확도를
말하면 그게 바로 이 프로젝트가 하지 말자고 한 일이다.

## 7. ④ 개발자 알림(Sentry)이 실제로 도착했나

### 7-1. 먼저 — Sentry 에는 무엇이 가고 무엇이 안 가나

**흔한 오해부터 짚는다. 「실패하면 다 알림이 간다」가 아니다.**

**로그는 한 줄도 안 간다.** Sentry 로 가는 것은 **예외(Exception)** 뿐이다. 로그를 보내려면
`sentry-logback` 을 따로 넣어야 하는데 이 프로젝트에는 없다(`sentry-spring-boot-starter-jakarta`
만 쓴다). 그래서 `classify_failed ...` 같은 로그는 도커 로그에만 남는다.

**예외라고 다 가는 것도 아니다.** 코드에서 Sentry 를 부르는 자리는 셋이고, **일부러 안 부르는
자리가 하나** 있다.

| 자리 | 언제 | 보내나 |
| --- | --- | --- |
| `RetryingAiClassifier` 의 `recoverFromCallFailure` | AI 를 **끝내 못 부른** 최종 실패 | ✅ |
| `RetryingAiClassifier` 의 `recoverFromInvalidResponse` | AI 답을 **끝내 못 읽은** 최종 실패 | ❌ **일부러 안 보냄** |
| `GlobalExceptionHandler` | API 요청에서 처리 못 한 오류(500) | ✅ |
| `AsyncConfig` | 비동기 스레드에서 아무도 안 잡은 예외 | ✅ |

**두 번째 줄이 이 팀의 판단이다.** 답을 못 읽는 실패는 3번을 다 써도 알림이 안 간다.
**외부 장애가 아니라 우리 프롬프트·파서가 손봐야 할 신호**이기 때문이다. 알림으로 띄우면
프롬프트 품질 문제가 장애 알림에 섞여 **양쪽 다 안 보게 된다.** 그 대신 실패 사유별 분포(측정 2)로 센다.

> 그래서 5장의 **B 경우(못 읽음)는 실제 앱에서 냈더라도 Sentry 에 안 갔을 것이다.**
> 「실패하면 알림이 온다」가 아니라 **「우리가 손쓸 수 없는 외부 실패만 알림이 온다」** 가 맞다.

**성공한 요청도 일부 간다 — 오류가 아니라 성능 기록으로.** `traces-sample-rate: 0.1` 이라
요청 10개 중 1개꼴로 성능 추적 데이터가 간다. 오류 목록이 아니라 Performance 쪽에 쌓인다.

정리하면 **오류 이벤트는 위 규칙에 걸린 것만 100%, 성능 추적은 10%, 로그는 0%** 다.

### 7-2. 왜 테스트로 안 재고 굳이 앱을 띄웠나

알림을 보내는 코드는 `Sentry.captureException(e)` 한 줄이다. 테스트에서 이 호출을 가로채면
**"불리기는 했다"까지만** 알 수 있다. 그런데 티켓이 물은 것은 **실제로 도착했는지**다.

이 구분이 중요한 이유가 있다. `SENTRY-GUIDE.md` 2-3 에 이미 실측으로 남아 있다 —
**오류를 잡아놓고(catch) 아무것도 안 하면 Sentry 는 그 오류를 영원히 모른다.** 자동으로도
수동으로도 안 잡히는 사각지대가 실제로 있다는 뜻이다. 그러니 "호출했으니 갔겠지"로 넘기면
바로 그 함정에 빠진다. 그래서 진짜로 보내고 진짜로 조회했다.

| 오류 | `AiCallException: AI 호출이 실패했다: 401 ... authentication_error` |
| 그 원인 | `com.anthropic.errors.UnauthorizedException` — **SDK 가 실제로 받은 401** |
| **발생 횟수** | **1** |
| 환경 | `measure4` |
| 스레드 | `classify-1` (분류 전용 스레드) |
| 실행 환경 | Eclipse Adoptium 21.0.11 |

**앱 로그와 5밀리초 차이로 맞물린다.** 앱 로그의 `classify_failed ... attempts=3` 이
`06:39:28.236Z`, Sentry 이벤트가 `06:39:28.241Z` — **같은 실패의 같은 순간**이다.
서로 다른 두 곳에 남은 기록이 이렇게 맞으면 우연으로 보기 어렵다.

### 7-4. 여기서 가장 값진 숫자는 「1」이다

**AI 는 3번 불렀는데 알림은 1건이다.** 이게 왜 중요한가.

알림을 **AI 를 부르는 자리마다** 보냈다면 3번 실패했으니 **3건**이 갔을 것이다. 그러면
장애 하나가 알림 3개로 부풀고, 실제로 몇 건이 문제인지 알 수 없게 된다.

그래서 알림은 **재시도를 다 써버린 마지막 순간**(`@Recover`)에서만 보내도록 돼 있다.
코드 주석에도 그 이유가 적혀 있다.

> "앞선 판에서 리스너의 `catch` 에 있던 호출이 이 자리로 옮겨온 것이다 — 거기 두면 재시도가
> 남아 있는 실패까지 매번 캡처해 **일시적 장애 하나가 3번 찍힌다**"
> — `RetryingAiClassifier.recoverFromCallFailure` 주석

**「3번 시도 → 알림 1건」이 그 설계가 실제로 지켜졌다는 증거다.**

### 7-5. ⚠️ 헷갈리기 쉬운 것 — 스택트레이스에 `recoverFromCallFailure` 가 안 보인다

Sentry 에 찍힌 오류 발생 흔적(스택트레이스)을 보면 이렇게 이어진다.

```text
InquiryReceivedEventListener.onInquiryReceived   (분류 담당이 깨어난 자리)
   → RetryingAiClassifier.classify               (재시도가 걸린 자리)
      → AiClassificationService.classify         (실제로 터진 자리)
```

**알림을 보낸 함수(`recoverFromCallFailure`)는 여기 없다.** 이건 잘못된 게 아니다.
스택트레이스에는 **알림을 보낸 자리가 아니라 오류가 처음 만들어진 자리**가 담기기 때문이다.
오히려 "어디서 터졌는지"를 보여주므로 이쪽이 쓸모 있다.

**그래서 "마지막 순간에만 알림을 보냈다"의 근거는 스택트레이스가 아니라 「알림이 1건뿐」이라는
사실이다.** 이걸 모르고 스택에서 함수 이름을 찾다가 못 찾으면, **"알림이 안 갔다"고 잘못 읽게 된다.**

### 7-6. 또 하나 헷갈리기 쉬운 것 — DB 는 비었는데 Sentry 에는 401 본문이 있다

DB 의 `raw_response`(AI 답 원문) 칸은 비어 있는데, Sentry 메시지에는 401 응답 본문이 들어 있다.
모순처럼 보이지만 아니다.

- `raw_response` 는 **"AI 가 준 분류 답"** 을 담는 칸이다. 이번엔 분류 답을 못 받았으니 비는 게 맞다
- Sentry 에 있는 401 본문은 **오류 메시지에 딸려 온 것**이지 분류 답이 아니다

두 칸이 담는 게 다르다.

## 8. 이 측정으로 말할 수 없는 것 (한계)

**측정 결과를 쓸 때는 무엇을 못 봤는지도 같이 적는다.** 안 적으면 다음 사람이 이미 확인된 줄 안다.

- **첫 번째 측정(통합 테스트)의 실패는 진짜 장애가 아니다.** 가짜로 바꿔친 객체가 던진 실패라,
  네트워크가 끊기거나 응답이 안 오거나(타임아웃) 호출량 초과(429)일 때도 똑같이 도는지는 모른다.
  두 번째 측정(실제 앱)이 그중 **「열쇠가 틀려서 거절당하는 경우」 하나만** 진짜로 덮는다.
- **위의 소요 시간(6.1~6.2초)은 최악값이 아니다.** 이번 실패는 즉시 났기 때문에 거의 쉬는 시간
  합(2초+4초)만 남았다. 실제 장애에서는 여기에 **응답을 기다리는 시간**(최대 30초 × 3번)이 더해진다.
  기동 로그의 `worstCasePerInquiry=PT1M36S`(96초)가 그 값인데, **그 최악의 경우는 아직 안 재봤다.**
- **재시도가 실패를 몇 퍼센트나 되살리는지는 이 문서에 없다.** C 는 "되살아나면 검토 목록에
  안 들어간다"를 보인 것이지 비율이 아니다. 비율을 내려면 확률적으로 실패하는 조건에서 표본을
  모아야 하고, 그건 측정 2 가 할 일이다.
- **실패를 잰 두 측정에서는 AI 모델이 한 번도 분류를 하지 않았다.** 답을 못 받거나 못 읽는
  경로였기 때문이고, 그래서 그 행들의 `model` 칸은 비어 있다. 정상 경로는 6-6 에서 **1건만**
  따로 확인했다 — **그 1건으로는 AI 가 얼마나 맞히는지 아무것도 말할 수 없다** (측정 1·8ⓐ 의 몫).

## 9. 측정 후 되돌린 것

틀린 열쇠로 띄운 앱을 그대로 두면 **다음 사람이 "분류가 전부 실패한다"를 버그로 신고하게 된다.**
측정이 끝나자마자 되돌렸고 확인까지 했다.

```bash
docker compose up -d app     # .env 의 정상 값으로 다시 띄움
# 확인: health {"status":"UP"} · ENV=local · AI 열쇠 정상값으로 복귀
```

**Sentry 이슈 `JAVA-SPRING-BOOT-B` 는 일부러 지우지 않았다.** 일부러 낸 실패이긴 하지만
지우면 이 문서의 근거가 사라진다. `environment:measure4` 표시가 붙어 있어서 평소 환경
(`local`·`prod`)의 알림과 섞이지 않는다.
