# 접수 API 가 느린 것을 어떻게 고칠 수 있나 — 선택지 검토

> `evidence/api-response-time.md`(측정 a·b, TRI-74) 가 **둘 다 목표 미달**로 나온 뒤,
> **"그래서 무엇을 할 수 있나"** 를 정리한 문서다.
>
> ⚠️ **이 문서는 측정이 아니다.** 여기 적힌 개선 효과는 **전부 예상이고 실측이 아니다.**
> 숫자로 확인한 것은 원본 측정 문서에만 있다.
>
> ⚠️ **아직 아무것도 결정하지 않았다.** 그래서 `DECISIONS.md` 에 넣지 않았다 — 이유는 맨 끝
> 「왜 결정 로그에 안 넣었나」 참조.

---

## 0. 세 줄 요약

1. **접수 API 코드 자체는 느리지 않다.** 요청의 약 4분의 3 은 이미 1초 안에 끝난다
2. 느린 것은 **분류를 대신 떠안은 나머지 4분의 1** 이고, 그건 버그가 아니라 **일부러 고른 설계**(D-045 ⑤)의 대가다
3. 고치는 방법은 있고 **여러 개다.** 다만 **"실제로 얼마나 몰리는가"를 정하기 전에는 고칠 대상이 있는지도 모른다**

---

## 1. 문제 — 무엇이 목표를 못 넘었나

`PRD.md §9` 의 속도 목표 두 개가 **둘 다** 미달이다.

| 측정 | 무엇을 재나 | 목표 | 실측 | 결과 |
| --- | --- | --- | --- | --- |
| **a** | 문의 접수 (`POST /api/inquiries`) | p95 **0.1초** | **6.36 ~ 8.82초** (AI 키 없음)<br>**16.94 ~ 18.77초** (실제 키) | ❌ |
| **b** | 검토 목록 조회 (10만 건) | p95 **0.2초** | **7.59초** | ❌ |

**둘은 원인이 전혀 다르다.** 그래서 고치는 방법도 다르다.

- **a** — 설계에서 일부러 받아들인 대가. **아래 2~5장이 전부 이 얘기다**
- **b** — 조회 방식 문제. **이미 답이 나와 있다** (7장)

> **p95 가 뭔가**: 100번 요청했을 때 **95번째로 느린 요청**의 시간. 평균은 느린 몇 건을 가려버려서,
> "대부분의 사용자가 겪는 최악"을 보려면 p95 를 본다.

## 2. 진단 — 접수 코드는 느리지 않다

측정 a 의 응답 시간은 **두 덩어리로 갈렸다.** (이봉 분포)

```text
73~74%  →  1초 미만        ← 그냥 접수만 한 요청. 이미 빠르다
26~27%  →  6~9초대         ← 분류를 떠안은 요청
```

**평균을 내면 이 사실이 사라진다.** "느린 요청"과 "빠른 요청"이 섞인 게 아니라, **두 종류의 요청이
따로 존재한다.**

### 왜 떠안는가

```text
접수 요청 ──▶ 문의 저장 ──▶ 이벤트 발행 ──▶ 202 응답 (여기서 끝나야 정상)
                                  │
                                  ▼
                        분류 대기열 (50칸)
                                  │
                    ┌─────────────┴─────────────┐
                 자리 있음                     가득 참
                    │                             │
              분류 스레드가 처리          ⚠️ 접수 스레드가 직접 처리
              (접수는 이미 응답함)         (응답이 그만큼 늦어진다)
```

마지막 갈래가 `CallerRunsPolicy` 다 — **"부른 쪽이 직접 뛴다"**.

### 이건 버그가 아니다

`DECISIONS.md` D-045 ⑤ 가 **일부러 고른 것**이다.

> **"느려지는 건 보이지만 사라지는 건 안 보인다."**

대기열이 찼을 때 선택지는 둘뿐이었다.

| 선택 | 결과 |
| --- | --- |
| **버린다** | 접수는 계속 빠르다. **대신 그 문의는 영영 분류되지 않고, 아무도 모른다** |
| **떠안는다** ← 채택 | **한 건도 안 잃는다.** 대신 접수가 느려지고, **그건 눈에 보인다** |

## 3. 최악의 경우는 얼마나 나쁜가 — 설정값으로 계산

접수 스레드가 떠안았을 때 **최대로 기다릴 수 있는 시간**을 `application.yml` 로 계산할 수 있다.

```yaml
anthropic:
  timeout: 30s                    # 한 번 호출에 최대 30초
  retry:
    max-attempts: 3               # 최초 1회 + 재시도 2회
    initial-backoff-millis: 2000  # 2초 쉬고 재시도
    multiplier: 2.0               # 다음엔 4초
    max-backoff-millis: 10000
```

```text
1차 호출 30초  +  2초 대기  +  2차 호출 30초  +  4초 대기  +  3차 호출 30초
= 최악 96초
```

**AI 가 계속 응답을 안 하면 접수 요청 하나가 96초까지 매달릴 수 있다.**

실측 p95 가 16.9~18.8초에 그친 건 **대부분 첫 호출이 성공했기 때문**이다. AI 쪽이 불안정한 날에는
훨씬 나빠진다.

### 실제 키가 더 나빴다는 사실이 원인을 확정해준다

| 조건 | p95 |
| --- | --- |
| AI 키 없음 (호출이 바로 실패) | 6.36 ~ 8.82초 |
| **실제 키 있음** (호출이 진짜로 나감) | **16.94 ~ 18.77초** |

**키가 있을 때가 2배 이상 나빴다.** 떠안는 일이 "즉시 실패 처리"가 아니라 **"몇 초 걸리는 진짜 API
호출을 기다리는 일"** 이 되기 때문이다.

> 이건 원래 **"실제 키가 있으면 더 나을 것"이라고 짐작해 한계로만 적어뒀던 것**을, TRI-74 가
> 실제로 재서 뒤집은 결과다. 짐작이 틀렸다.

## 4. 고치는 방법 — 설정만 바꾸기 (코드 0줄)

### ① 대기열을 키운다 `queue-capacity: 50 → 500`

**가장 싸다.** 대기열이 잘 안 차니 떠안는 일 자체가 줄어든다.

| 얻는 것 | 잃는 것 |
| --- | --- |
| 떠안는 빈도가 크게 감소 | **밀린 문의가 메모리에 쌓인다.** 서버가 죽으면 그만큼 통째로 사라진다 |

> ⚠️ **지금도 서버가 죽으면 대기열이 사라진다.** 500 으로 늘리면 **잃을 수 있는 양이 10배**가 된다.
> `GET /api/stats` 의 `stuckReceived` 로 드러나긴 하지만 **자동 복구는 없다**(「나중에 할 것」 E).
>
> **근본 해결이 아니라 미루기다.** 트래픽이 계속 몰리면 500칸도 결국 찬다.

### ② 스레드를 늘린다 `max-size: 8 → 12`

**천장이 정해져 있다.**

```text
분류 스레드 1개 = DB 커넥션 1개  (트랜잭션 ② 를 쓰니까)
DB 커넥션 풀 = 20개  (maximum-pool-size)

스레드를 20 가까이 올리면 → 접수 API 가 쓸 커넥션이 안 남는다
```

**`AsyncConfig` 가 기동 시 이걸 검사해서, 어긋나면 서버가 아예 안 뜬다** (D-047 ⓑ).

| 얻는 것 | 잃는 것 |
| --- | --- |
| 동시에 더 많이 처리 → 대기열이 덜 참 | **접수가 커넥션을 못 얻어 느려지는 다른 문제**로 바뀔 수 있다 |

### ③ AI 호출 타임아웃을 줄인다 `timeout: 30s → 10s`

떠안았을 때 **최악이 96초 → 약 36초**로 줄어든다.

| 얻는 것 | 잃는 것 |
| --- | --- |
| 최악이 짧아짐 | **정상 호출도 잘린다** → `FAILED` 가 늘고 **검토 목록이 불어난다** |

> **속도 문제를 사람 노동으로 바꾸는 것**이다. 상담원이 대신 처리할 양이 늘어난다.

## 5. 고치는 방법 — 대기열을 메모리가 아니라 DB 에 둔다 ★

**가장 좋은 답으로 보인다.** 라이브러리를 하나도 안 늘리면서 근본 문제를 푼다.

```text
지금:   접수 ─▶ 저장 ─▶ 스프링 이벤트 ─▶ 메모리 대기열(50칸) ─▶ 분류
                                          ↑ 여기가 유한해서 떠안는 일이 생긴다

바꾸면: 접수 ─▶ 저장 + "분류할 일" 한 줄도 같이 저장 ─▶ 즉시 응답 (끝)
                            │
                            ▼
                별도 스케줄러가 주기적으로 긁어서 분류
```

| 얻는 것 | 잃는 것 |
| --- | --- |
| **접수가 항상 빠르다** — 떠안는 일이 아예 없어진다 | 분류가 **몇 초 늦게** 시작된다 (스케줄러 주기만큼) |
| **서버가 죽어도 안 사라진다** — DB 에 있으니까 | 코드가 는다 (테이블 1개 + 스케줄러) |
| 대기열 크기가 사실상 무한 | |

### ⚠️ 이건 이미 티켓으로 존재한다 — `TRI-94`

> **TRI-94** — *"멈춘 문의를 다시 분류한다 — `stuckReceived` 를 **보이는 것에서 없애는 것으로**
> (PRD §8 항목 E)"* · 이용택 · 상태 **할 일**
>
> **즉 이 방법은 새 제안이 아니라, 이미 잡혀 있는 티켓이 속도 문제까지 같이 푼다는 발견이다.**
> TRI-94 를 "유실 방지" 목적으로만 보고 있었는데, **접수 속도(측정 a)의 답이기도 하다.**
> 착수할 때 이 문서를 함께 본다.

### 지금 구조의 가장 큰 약점을 같이 고친다

`GLOSSARY.md` 에 이미 이렇게 적혀 있다.

> *"지금 방식은 라이브러리를 하나도 안 늘리는 대신, **서버가 죽으면 신호가 사라진다**는 한계가 있다."*

그리고 이건 **「나중에 할 것」 E(멈춘 문의 다시 분류하기)와 사실상 같은 장치**다.
측정 1 에서 **응답 실패 3건이 1시간 뒤엔 성공**했으니, 이 기능이 있었으면 자동으로 풀렸다.

> **한 번에 두 개를 고친다** — 속도 목표 a 와 「나중에 할 것」 E.

## 6. 고치는 방법 — 메시지 큐 (Kafka · RabbitMQ)

**정석이다.** 접수는 큐에 넣기만 하고 끝낸다.

| 얻는 것 | 잃는 것 |
| --- | --- |
| 접수와 분류가 완전히 분리 | **인프라가 하나 는다** (운영·모니터링·장애 대응) |
| 재시도·순서·중복 처리를 큐가 담당 | 5일 범위 밖 |

**5장으로 얻는 것과 거의 같은데 비용이 훨씬 크다.** 문의량이 지금의 수십 배가 되기 전에는 과하다.

---

## ❌ 하면 안 되는 것 — 넘치면 버리기 (`AbortPolicy`)

접수는 즉시 빨라진다. **그런데 이 프로젝트의 주제와 정면으로 어긋난다.**

```text
D-045 ⑤ — "버리지 않고 호출한 쪽이 대신 처리한다"
          느려지는 건 보이지만 사라지는 건 안 보인다
```

이 시스템의 존재 이유가 **"자동으로 확정된 것을 믿지 않는다"** 인데, **분류조차 안 된 문의가 조용히
사라지는 것**은 그 반대다.

> 바꾸려면 `DECISIONS.md` 새 항목이 먼저다. **그리고 5장이 있으면 버릴 이유가 없다.**

## 7. 측정 b(검토 목록)는 원인이 다르다 — 이미 답이 나와 있다

**a 와 섞어 보면 안 된다.** b 는 대기열과 아무 상관이 없다.

| | 원인 | 답 |
| --- | --- | --- |
| **a** | 대기열이 차서 접수 스레드가 분류를 떠안음 | 위 4~6장 |
| **b** | 목록 조회가 필요 없는 데이터까지 다 읽어옴 | **프로젝션 전환** (TRI-87 이 이미 판정) |

`evidence/n-plus-one-review-queue.md`(측정 5ⓖ) 가 이미 실측했다.

```text
지금 (search, @EntityGraph)     636ms
프로젝션 (searchProjected)      280ms
목표                            200ms
```

> ⚠️ **이 숫자들을 그대로 믿으면 안 된다 — 원본이 직접 그렇게 적어뒀다.**
>
> 같은 조건의 이전 실행은 **644ms / 399ms (차이 38%)** 였고 이번은 **636ms / 280ms (차이 56%)** 다.
> **절대값도 상대 차이도 실행마다 흔들렸다.** 원본의 결론은 이렇다 —
>
> > *"절대 시간도 이번 상대 차이(56%)도 정확한 값으로 못 박지 않는다.
> > **「프로젝션이 EntityGraph 보다 빠르고 더 안정적이다」라는 방향성만** 결론의 근거로 삼는다."*
>
> **즉 「56% 빨라진다」가 아니라 「빨라지는 방향이 맞다」까지만 말할 수 있다.**
> 얼마나 빨라지는지는 **바꾼 뒤에 다시 재야 안다.**

⚠️ **그리고 위 636ms 는 목표를 넘는 값이다.** 프로젝션(280ms)으로 바꿔도 목표(200ms)를 못 넘는다 —
**프로젝션 전환은 필요조건이지 충분조건이 아니다.** 인덱스·페이지네이션 전략을 더 봐야 한다.

⚠️ **위 636ms 와 측정 b 의 7.59초를 빼서 비교하면 안 된다.** 636ms 는 **리포지토리를 직접 부른 값**이고,
7.59초는 **실제 HTTP 왕복**이라 보안 필터·JSON 변환·동시 요청 커넥션 경합이 더해져 있다.
**잰 대상이 다르다.**

## 9. 고치기 전에 먼저 정할 것 ⚠️

**이번 측정은 「100건을 동시에 10개씩 몰아친」 조건이다.** 실제 트래픽이 그렇게 몰리는지가 먼저다.

```text
문의가 초당 1건씩 들어오면
  → 대기열(50칸)이 찰 일이 없다
  → 떠안는 일도 없다
  → 이미 목표 안에 들어온다 (요청의 73~74% 가 1초 미만)
```

측정 문서 스스로 한계로 적어뒀다.

> *"동시성 10 으로만 쟀다. `PRD.md` 에 지정값이 없어 임의로 골랐다."*

**「동시에 몇 건까지 들어오는가」가 정해지지 않으면, 위 개선은 일어나지 않을 상황을 위해 구조를
바꾸는 것이 된다.**

### 다음에 재야 할 것

| 재는 것 | 왜 |
| --- | --- |
| 동시성 1·3·5·10 을 나눠서 | **어느 지점부터 떠안기 시작하는지**를 찾는다. 그게 이 시스템의 실제 한계선이다 |
| 대기열 500 으로 올린 뒤 같은 조건 | 설정 한 줄이라 5분이면 된다. **효과가 없으면 없다고 그대로 적는다** |
| b 를 `-c 1` 로 | "1건 조회가 느린 것"과 "동시 요청 커넥션 경합"이 지금 섞여 있다 |

## 10. 왜 결정 로그(`DECISIONS.md`)에 안 넣었나

**아직 결정한 게 없기 때문이다.**

- `DECISIONS.md` 는 **되돌릴 수 없는 기록**이다 — 본문을 안 고치고 새 항목으로만 덮는다
- 위 선택지 중 무엇을 고를지는 **9장(실제 트래픽 특성)이 정해져야** 판단할 수 있다
- 지금 넣으면 **재보기 전에 고른 답**이 결정 로그에 남는다 — 이 프로젝트가 계속 피해온 일이다

**한 가지 고르고 실제로 적용할 때 `DECISIONS.md` 항목을 만든다.** 그때 이 문서가 「검토한
선택지」로 인용된다.

> 원본 측정 문서(`evidence/api-response-time.md`)에도 안 넣었다 — **그건 김은빈이 잰 기록**이고,
> 이 문서는 **그 결과를 받아 검토한 것**이라 성격이 다르다. 측정과 검토를 섞으면 나중에
> **"어디까지가 실측이고 어디부터가 짐작인지"** 가 안 보인다.
