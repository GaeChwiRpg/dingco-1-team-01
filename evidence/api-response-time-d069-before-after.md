# D-069 전후 대조 실측 — 접수 API 응답 시간 · 처리량 · 유실 (TRI-94 후속)

> `hey`로 직접 잰 값이다. **개선 전 코드와 개선 후 코드를 같은 기계·같은 도구·같은 조건으로 대조**했다.
> 측정일 2026-08-26. 관련: `DECISIONS.md` D-069, `evidence/api-response-time.md`(단일 시점 측정)

## 왜 이 측정이 가능했나 — 운이 좋았다

로컬 docker 컨테이너가 **2026-08-12 빌드 상태로 13일간 떠 있었다.** D-068(8/14)·D-069(8/15)가 들어가기 전 이미지다.

```text
image      dingco-1-team-01-app:latest   2026-08-12 22:33 빌드
container  2026-08-12T14:45 기동, 측정 시점까지 재기동 없음
확인        classify_task_deferred 로그 0건 · stuck_inquiries_requeued 0건
           → DeferToReclassifyPolicy 도 재분류 스케줄러도 없는 코드가 맞다
```

기존 `api-response-time.md` 의 개선 전/후 값은 **서로 다른 날·다른 조건**에서 잰 것이라 배수를 말할 수 없었다. 이번에는 그 제약이 없다.

> 측정 전에 이 이미지를 `dingco-app:before-d069` 로 태그해 보존했다. 재빌드하면 사라지기 때문이다.

| After 사전 처리 | 재기동 직후라 워밍업 1회 실행 후 본 측정 (Before 는 13일 가동 상태였음) |

## ⚠️ 측정을 두 번 망쳤다 — 조건을 여기 남기는 이유

**이 절이 이 문서에서 제일 중요하다.** 같은 함정을 다시 밟지 않으려고 실패한 시도까지 적는다.

### 실패 1 — 이미 판정된 문구를 썼다

첫 측정에서 개선 **전** 코드인데도 p95 0.1519초 · 251 TPS 가 나왔다. 빨라서가 아니라 **AI 를 한 번도 안 불렀기 때문**이다.

- 측정 직전 `curl` 로 같은 문구를 1건 넣어 동작을 확인했는데, 그 1건이 판정되면서 캐시·DB에 답이 생겼다
- 이후 100건이 전부 2단 절감 경로(재사용)로 빠졌다
- 확인: `GET /api/stats` 의 `audit.reused.eligibleTotal` 이 **36 → 128** 로 증가(=100건 전량 재사용). AI 호출 0

### 실패 2 — 새 문구여도 동시성이 낮으면 대기열이 안 찬다

문구를 바꿔 `-n 100 -c 10` 으로 재니 p95 1.66초. 여전히 기대한 포화 상태가 아니었다.

| 실행 | p50 | p90 | p95 | p99 | TPS |
| --- | --- | --- | --- | --- | --- |
| 새 문구 · `-c 10` | 0.0092초 | 1.5018초 | 1.6648초 | 2.7935초 | 33.79 |

**p50 이 0.009초**인 것이 단서였다 — 같은 문구라 **첫 몇 건만 AI 를 부르고 나머지는 재사용**되어, 대기열(50)이 찰 만큼 동시 AI 호출이 쌓이지 않았다.

### 그래서 확정한 조건 — 새 문구 + 동시성 50

동시성을 50으로 올리자 **캐시가 채워지기 전에 50건이 동시에 유입**되어 전부 AI 호출로 향했고, 대기열 포화가 재현됐다. 이때 값이 기존 `api-response-time.md` 의 6.36~8.82초 범위와 겹친다 — **다른 날 잰 값과 재현성이 확인된 셈**이다.

## 실측 값

### Before — D-069 이전 (2026-08-12 빌드)

```text
Total: 8.6694 secs   Slowest: 7.5560   Average: 1.4851   Requests/sec: 23.0697
p50 0.0938 · p90 5.1049 · p95 7.2803 · p99 7.5226      [202] 200 responses
```

### After — D-069 적용 (2026-08-26 재빌드)

```text
Total: 0.3877 secs   Slowest: 0.2256   Average: 0.0789   Requests/sec: 515.8133
p50 0.0720 · p90 0.1354 · p95 0.1591 · p99 0.2054      [202] 200 responses
```

### 나란히

| 지표 | Before | After | 배수 |
| --- | --- | --- | --- |
| p50 | 0.0938초 | 0.0720초 | 1.3× |
| p90 | 5.1049초 | 0.1354초 | 37.7× |
| **p95** | **7.2803초** | **0.1591초** | **45.8×** |
| p99 | 7.5226초 | 0.2054초 | 36.6× |
| 최대 | 7.5560초 | 0.2256초 | 33.5× |
| 평균 | 1.4851초 | 0.0789초 | 18.8× |
| **처리량** | **23.07 TPS** | **515.81 TPS** | **22.4×** |
| 200건 총 소요 | 8.6694초 | 0.3877초 | 22.4× |

양쪽 다 200건 전량 202 응답, 실패 0.

> **p50 차이(1.3배)가 작은 것이 오히려 설명이 된다.** 이 문제는 대기열이 찬 요청에만 발생하므로, 절반의 요청은 원래도 빨랐다. **꼬리(p90~p99)에서만 45배 가까이 벌어진다** — 개선 대상이 평균이 아니라 꼬리였다는 뜻이다.

## 「빨라졌다」의 뒷면 — 유실은 늘지 않았다

접수가 즉시 반환된 대신 분류가 사라졌다면 개선이 아니다. D-069 의 전제(*"버려지는 것은 문의가 아니라 분류 신호뿐"*)가 실제로 성립하는지 확인했다.

```text
classify_task_deferred      157건   대기열 포화로 미뤄짐 (DeferToReclassifyPolicy 발동)
stuck_inquiries_requeued     20건 × 5회 (12:28:53 ~ 12:32:54, 1분 주기)
stuckReceived                 0건   최종 방치 0
```

측정 직후 `GET /api/stats`:

```text
총 737건 · 자동확정 698 · 검토 대기 35 · 실패 4 · stuckReceived 0
```

**157건이 미뤄졌지만 전량 회수되어 방치된 문의는 없다.** 스케줄러가 `batch-size` 설정값(20)대로 1분마다 집어갔다.

## 호출당 토큰 실측 (측정 6 보조)

절감률(49.0%)을 토큰으로 환산하려면 호출당 토큰이 필요한데, 지금 코드는 응답의 `usage` 를 버린다. **Anthropic 토큰 카운트 API 로 직접 쟀다** — 추정값 아님.

```text
model claude-sonnet-5 · thinking 비활성(D-051) · max_tokens 512
input  585 토큰   output  27 토큰
실제 응답 예시: {"category": "RETURN_REFUND", "confidence": 0.93}
```

**본문 길이에 따른 input 편차**

| 본문 | input 토큰 |
| --- | --- |
| 12자 | 535 |
| 129자 | 585 |
| 385자 | 693 |

입력의 약 520 토큰이 시스템 프롬프트 고정분이라, **본문이 30배 길어져도 총량은 ±13% 안에서 움직인다.**

### 그래서 코드 계측을 안 했다

`AiClassificationService` 에 토큰 카운터를 추가하는 선택지가 있었는데(마이크로미터 카운터 2개), **위 편차 측정이 그 필요를 없앴다.** 대표값 585 로 곱해도 오차가 ±13% 안이고, 실제 키로 1000건을 돌리는 요금이 든다. 필요해지면 그때 붙인다.

### 1000건 기준 환산

호출 건수는 `evidence/measurement-6-11-actual.md` 실측(`triage.ai.calls` 카운터)이다.

| | AI 호출 | input 토큰 | output 토큰 | 합계 |
| --- | --- | --- | --- | --- |
| 2단 절감 없음 (가정) | 1000회 | 585,000 | 27,000 | 612,000 |
| **2단 절감 적용 (실측)** | **510회** | 298,350 | 13,770 | **312,120** |
| 절감 | 490회 | 286,650 | 13,230 | **299,880 (49.0%)** |

**곱셈의 두 항이 모두 실측이다** — 건수는 카운터, 호출당 토큰은 토큰 카운트 API. 「2단 절감 없음」 행만 계산값이고, 이는 *"재사용된 490건이 전부 AI 를 불렀다면"* 이라는 정의상의 값이다.

## 한계 — 안 한 것과 못 하는 것

| 한계 | 내용 |
| --- | --- |
| **각 조건 1회씩만 쟀다** | 기존 측정은 5~6회 반복해 우연을 배제했는데 이번엔 Before·After 각 1회다. **배수(45.8×)는 이 1회 쌍의 값**이다. 다만 Before 값이 다른 날 잰 6.36~8.82초 범위와 겹쳐 재현성은 간접 확인됐다 |
| **문구가 서로 다르다** | 캐시 오염을 피하려면 매 측정마다 새 문구여야 해서, Before 와 After 가 같은 문자열이 아니다. 둘 다 "처음 보는 문구"라는 점에서 동등하지만 완전 동일 입력은 아니다 |
| **워밍업 조건이 비대칭** | Before 는 13일 가동 상태, After 는 재기동 후 워밍업 1회. After 에 불리한 방향이라 배수를 부풀리지는 않는다 |
| **로컬 docker 단일 기계** | 실제 배포 환경 아님. 절대값이 아니라 **같은 기계에서의 상대 비교**로만 읽는다 |
| **45.8배는 포화 조건의 값이다** | 대기열이 차야 발동하던 문제라 포화를 일부러 만든 조건에서 잰 값이다. 포화가 없는 트래픽에서는 개선 전에도 0.1초대였다(위 실패 1·2 참조) |

## 재현하기

```bash
# 1. 개선 전 이미지로 되돌리기 (보존해둔 태그)
docker tag dingco-app:before-d069 dingco-1-team-01-app:latest && docker compose up -d app

# 2. 한 번도 쓰지 않은 문구로 측정 (문구를 재사용하면 실패 1 이 재현된다)
hey -n 200 -c 50 -m POST \
  -H "Content-Type: application/json" -H "X-User-Id: 5001" -H "X-User-Role: CUSTOMER" \
  -d '{"content":"<새 문구>","channel":"WEB"}' \
  http://localhost:8080/api/inquiries

# 3. 현재 코드로 재빌드 후 같은 측정 (문구는 또 새것으로)
docker compose up -d --build app

# 4. 유실 확인
docker logs dingco-1-team-01-app-1 | grep -c classify_task_deferred
docker logs dingco-1-team-01-app-1 | grep stuck_inquiries_requeued
curl -s localhost:8080/api/stats -H "X-User-Id: 9001" -H "X-User-Role: MANAGER"
```
