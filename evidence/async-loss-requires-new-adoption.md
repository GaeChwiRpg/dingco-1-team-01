# 부하 유실 수정을 운영에 적용하고 다시 재봤다 (TRI-96 · D-066 채택)

> **한 줄로**: 이용택이 PR #87 에서 *"`REQUIRES_NEW` 면 유실 0"* 을 **테스트 전용 빈으로** 증명했고,
> 이 문서는 그 애노테이션을 **운영 코드에 붙인 뒤 같은 것을 다시 재본** 기록이다.
>
> **원본 측정은 `evidence/async-loss-prevention.md`(이용택) 이다.** 그 문서를 고치지 않고 새로 쓴다 —
> 남이 잰 기록과 내가 잰 기록을 섞으면 나중에 어디까지가 원본인지 안 보인다.

## 1. 문제 — 무엇이 아직 확인 안 됐었나

PR #87 이 증명한 것은 **"`REQUIRES_NEW` 라는 전파 방식이 유실을 막는다"** 는 **효과**였다. 방식은 둘이었다.

| 테스트 | 어떻게 시연했나 |
| --- | --- |
| `AsyncLossPreventionIT` (모드 C') | `TransactionTemplate` 에 `REQUIRES_NEW` 를 걸어 감쌈 |
| `SeamLoadIT` | `ClassificationService` 를 **상속**해 두 입구를 `REQUIRES_NEW` 로 오버라이드한 빈을 `@Primary` 로 끼움 |

둘 다 **운영 클래스는 건드리지 않았다.** 그래서 남은 질문이 하나 있었다.

> **운영 클래스에 붙인 애노테이션이 실제로 프록시를 타는가.**

스프링의 `@Transactional` 은 **같은 클래스 안에서 자기 메서드를 부르면 무시된다**(프록시를 안 거치므로).
붙였는데 안 먹는 상태는 **테스트가 아니라 운영에서만** 드러나므로, 이걸 재보지 않으면 채택이 끝난 게 아니다.

## 2. 무엇을 바꿨나

`src/main/java/com/dingco/triage/service/ClassificationService.java` — **애노테이션 2줄 + import 1줄.**

```diff
+import org.springframework.transaction.annotation.Propagation;

-    @Transactional
+    @Transactional(propagation = Propagation.REQUIRES_NEW)
     public boolean verifyAndPersist(...)

-    @Transactional
+    @Transactional(propagation = Propagation.REQUIRES_NEW)
     public boolean persistReuse(...)
```

**호출 지점을 전수로 확인했다** — 두 메서드는 `InquiryReceivedEventListener` 에서만 불리고(96·115행),
클래스 안에서 서로 부르는 자리가 없다. 그래서 위에 적은 함정(자기 호출)에는 걸리지 않는다.

## 3. 확인 ⓐ — 애노테이션 경로로 유실 0 이 나온다

### 단건 (`AsyncLossPreventionIT`, 3건 전부 통과)

| 모드 | 무엇을 부르나 | 문의 상태 | 검토 큐 | stuck | 결과 |
| --- | --- | --- | --- | --- | --- |
| C (대조군) | `REQUIRED` 강제 빈 | `RECEIVED` | 없음 | **1** | `no transaction is in progress` → **유실** |
| **C'** | **운영 빈 그대로** | `UNCLASSIFIED` | `LOW_CONFIDENCE` 1건 | 0 | 예외 없음 → **유실 0** |

**두 모드의 호출 모양이 완전히 같고 다른 것은 애노테이션뿐이다.** 감싸는 트랜잭션 템플릿을 없앴으므로,
C' 가 통과한다는 것은 곧 **운영 애노테이션이 프록시를 탔다**는 뜻이다.

### 부하 200건 (`SeamLoadIT`, 접수 스레드 8)

| | 총 접수 | 분류됨 | **유실(RECEIVED)** | 판정 행 | `receive` 예외 |
| --- | --- | --- | --- | --- | --- |
| REQUIRED (대조군 · 3회 반복) | 200 | 23 | **177** | 23 | 0 |
| **REQUIRES_NEW (운영 빈)** | 200 | **200** | **0** | 200 | 0 |

대조군은 **3회 전부 177** 로 나왔다 — 흔들리지 않았다. 운영 경로는 **200/200 분류, 유실 0.**

> PR #87 의 원본 실측(테스트 전용 빈)과 **같은 값**이다. 애노테이션으로 옮겨도 결과가 변하지 않았다.

## 4. 확인 ⓑ — ⚠️ 커넥션이 마르면 `REQUIRES_NEW` 도 완전히는 못 막는다 (새로 발견)

원본 문서가 한계로 적어둔 자리를 실제로 재봤다.

> *"`REQUIRES_NEW` 가 인라인마다 커넥션을 하나 더 쓰므로 접수 스레드를 8(<풀 20)로 제한했다.
> **더 높은 동시성에선 풀 여유를 다시 봐야 한다**"*

접수 스레드를 **24**(커넥션 풀 20 **초과**)로 올려 같은 부하를 다시 걸었다.

| 접수 스레드 | REQUIRED (대조군) | **REQUIRES_NEW (운영)** |
| --- | --- | --- |
| **8** (풀 이내) | 유실 **177** · 예외 0 | **유실 0** ✅ |
| **24** (풀 초과) | 유실 **195** · 예외 **0** | 유실 **122~142** · 예외 **32** |

원인은 예외 종류로 분명하게 드러난다.

```
SQLTransientConnectionException   148   ← HikariPool 커넥션 대기 타임아웃(30초)
CannotCreateTransactionException  142   ← REQUIRES_NEW 가 새 트랜잭션을 못 엶
```

### 왜 이런가 — 인라인 실행은 커넥션을 두 개 쓴다

```text
평소 (분류 스레드)      : ②가 커넥션 1개
인라인 (접수 스레드)    : ①의 커넥션이 아직 정리 중  +  ②가 새로 1개   ← 2개
```

인라인이 동시에 20개를 넘으면 풀이 마르고, 그때 `REQUIRES_NEW` 는 **열 수 없는 트랜잭션을 열려다 실패**한다.

### 그래도 채택 근거는 유지된다 — 두 가지

1. **같은 조건에서 항상 낫다.** 24스레드에서도 195 → 122~142. `REQUIRED` 가 더 많이 잃는다
2. **유실의 성격이 바뀐다.** `REQUIRED` 는 `receive` 예외가 **0건**(완전히 조용)인데, `REQUIRES_NEW` 는
   **32건이 호출부로 전파**된다 — D-066 이 노린 *"조용한 유실을 보이는 것으로 바꾼다"* 가 부분적으로 작동한다

### ⚠️ 이것이 드러낸 더 큰 문제 — D-047 ⓑ 의 불변식에 인라인이 빠져 있다

`AsyncConfig` 가 기동 시 검사하는 규칙은 이렇다.

```text
classification.async.max-size (8)  <  spring.datasource.hikari.maximum-pool-size (20)
```

근거는 *"트랜잭션 ②가 스레드마다 커넥션을 1개씩 쓰므로, 이 값이 커넥션 수에 가까워지면 접수 API(①)가
쓸 커넥션이 남지 않는다"* 였다. **그런데 인라인 실행은 이 계산에 없다.**

| | 커넥션을 쓰는 주체 | 상한 |
| --- | --- | --- |
| 계산에 있는 것 | 분류 스레드 | `max-size` = **8** |
| **계산에 없는 것** | **인라인 실행하는 접수 스레드** | 톰캣 스레드 = **기본 200** |

즉 **"분류가 커넥션을 8개까지만 쓴다"는 전제가 대기줄 포화 시 깨진다.** 이것은 트랜잭션 전파 문제가
아니라 **자원 상한 문제**이고, `REQUIRES_NEW` 로 고쳐지지 않는다 — **이 티켓에서 고치지 않고 후속으로 넘긴다.**

## 7. 회귀 방어 — 애노테이션을 되돌리면 테스트가 실패한다

채택으로 두 테스트의 **역할이 뒤집혔다.** 대조군을 지우지 않았다.

| 테스트 | 채택 전 | 채택 후 |
| --- | --- | --- |
| `SeamLoadRequiredIT` | 운영 빈(REQUIRED) → 유실 발생 | **REQUIRED 강제 빈**(대조군) → 유실 발생 |
| `SeamLoadRequiresNewIT` | 테스트 전용 `@Primary` 빈 → 유실 0 | **운영 빈** → 유실 0 |
| `AsyncLossPreventionIT` 모드 C | 운영 빈 직접 호출 → 예외 | **REQUIRED 강제 빈**(대조군) → 예외 |
| `AsyncLossPreventionIT` 모드 C' | `REQUIRES_NEW` 템플릿으로 감쌈 | **템플릿 없이 운영 빈** → 유실 0 |

**대조군을 남긴 이유**: 지우면 "REQUIRED 면 유실된다"는 사실이 코드에서 사라져, 누가 애노테이션을
되돌려도 **아무 테스트도 실패하지 않는다.** 이 결함은 대기줄이 포화돼야만 나타나므로 평소 테스트로는
안 보인다 — **대조 실험 자체가 회귀 방어 장치다.**

`AsyncLossPreventionIT` 의 대조군은 `@Primary` 로 끼우지 **않았다.** 모드 A 가 운영 경로 전체
(리스너 → 재시도 → `@Recover`)를 그대로 타야 하므로, 빈을 하나 **더** 등록하고 모드 C 만 이름으로 집는다.
