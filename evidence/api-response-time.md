## a. 문의 접수 API — 100건 중 95번째로 느린 요청 (목표 0.1초)

### 측정 조건

- 서버: `docker compose up -d` (mysql + redis + app), `ANTHROPIC_API_KEY` 없음 (팀 기본 로컬 실행)
- 도구: `hey -n 100 -c 10 -m POST` → `POST /api/inquiries`
- 같은 본문을 100회 반복 (동시성 10)

### 실측 값 (2026-08-13)

100건을 요청해서 걸린 시간을 짧은 순서대로 줄 세웠을 때, p50과 p95, p99가
각각 몇 초 걸렸는지를 잰다. 목표로 삼은 건 **p95**가 0.1초 안이어야 한다는 것이었다.

| 구간 | 뜻 | 값 (5회 범위, 중앙값) |
| --- | --- | --- |
| 중간값 (p50) | 100건 중 50번째로 느린 요청 | 0.128 ~ 6.09초 (중앙값 0.243초) |
| **목표로 삼은 값 (p95)** | 100건 중 95번째로 느린 요청 | **6.36 ~ 8.82초 (중앙값 7.47초)** |
| 최상위 (p99) | 100건 중 99번째로 느린 요청 | 6.42 ~ 8.89초 |

### 원인 — 이미 PRD.md §9 가 예견한 트레이드오프였다

이 프로젝트는 AI에게 분류를 맡기는 줄(대기열)이 가득 찼을 때, **문의를 버리지 않고 접수
요청이 그 분류 작업을 대신 떠맡게** 만들어져 있다(D-045 ⑤ · 스프링의 `CallerRunsPolicy`).
PRD.md §9 는 이미 이렇게 적어뒀다:

> "느려지는 건 보이지만 사라지는 건 안 보인다. 대신 이 선택의 대가는 속도 목표 a(접수 0.1초)에
> 그대로 나타나므로, 측정할 때 대기줄 상태를 함께 기록한다."

이번 측정이 정확히 그 대가를 보여준다.

- 응답 시간 분포가 **두 덩어리로 갈라져 있다** — 73~74%는 1초 미만인데, 나머지 26~27%는
  6~9초대에 몰려 있고 그 사이(1~6초)는 거의 비어 있다
- 6~9초라는 시간대는 우연이 아닐 수 있다 — AI 호출이 실패해서 다시 시도할 때 기다리는
  시간(2초, 그다음 4초)과 크기가 비슷하기 때문이다. 대기열이 꽉 차서 접수 요청이 분류를
  떠맡았을 때, 그 재시도 대기 시간이 그대로 접수 응답 시간에 포함됐을 가능성이 있다. 다만
  이번 측정만으로 요청 하나하나의 지연 원인을 낱낱이 추적한 건 아니라서, 이게 진짜 원인이라고
  단정하지는 않는다.
- 설정 파일의 주석도 같은 증상을 미리 경고해뒀다: *"증상은 '접수가 느리다'로 나타나는데
  원인은 AI가 아니라 커넥션이라 오진하기 쉽다"* — 이번 측정으로 그 증상을 실제로 재현했다

### 측정 시점 대기줄 상태 (`GET /api/stats`, PRD.md §9 요구사항)

```json
{
  "classification": { "inquiriesTotal": 163, "autoAccepted": 3, "needsReview": 0, "failed": 160, "stuckReceived": 0 },
  "backlog": { "total": 158, "byReason": { "CLASSIFY_FAILED": 158 } },
  "aiCallSavings": { "inquiriesReceived": 213, "aiCallsMade": 160, "savingsRate": 0.249 }
}
```

`stuckReceived: 0` — 완전히 유실된 문의는 없다(D-017 의미로는 정상). 다만 `backlog.total: 158`
(전부 `CLASSIFY_FAILED`)이 위 지연의 정황과 일치한다 — 분류 시도가 몰리면서 대기열이 찼다.

### 추가 측정 — 실제 `ANTHROPIC_API_KEY` 로 재보니 더 나빴다

위 값은 전부 키 없이(분류가 매번 `FAILED`로 즉시 끝나는 조건) 잰 것이다. "실제 키가 있으면
더 빠를 것"이라고 짐작하고 한계로 적어뒀는데, **실제로 키를 넣고 재보니 그 짐작이 틀렸다** —
이래서 AI로 추정하지 않고 직접 재는 것이다 (CLAUDE.md 「AI 검증 규칙」).

| 구간 | 값 (실제 키, 3회) |
| --- | --- |
| 중간값 (p50) | 0.103 ~ 0.217초 |
| **목표로 삼은 값 (p95)** | **16.94 ~ 18.77초** — 키 없을 때(6.36~8.82초)보다 2배 이상 나쁘다 |
| 실패 | 1회차는 100건 중 5건이 20초 넘게 걸려 응답 자체를 못 받음(타임아웃). 2·3회차는 100건 다 받음 |

| 실행 | 중간값(p50) | 목표값(p95) | 최상위(p99) | 비고 |
| --- | --- | --- | --- | --- |
| 1 | 0.103초 | 18.77초 | — | 5건 타임아웃(20초 초과, 미수신) |
| 2 | 0.119초 | 17.66초 | 19.61초 | 100건 다 받음 |
| 3 | 0.217초 | 16.94초 | 18.86초 | 100건 다 받음 |

**3번 다 같은 그림이다** — 초반 다수(65~69%)는 2초 안에 빠르게 끝나고, 나머지가 13~20초대에
몰려 있다. 우연이 아니라 안정적으로 재현되는 현상이다.

**왜 더 나쁜가**: 키가 없으면 "분류를 시도했는데 바로 실패"라 접수 스레드가 금방 풀려나는데,
**키가 있으면 접수 스레드가 진짜 Claude API 응답을 기다려야 한다.** 대기열이 찼을 때 접수
스레드가 분류를 떠안는 구조(`CallerRunsPolicy`)는 같지만, 떠안는 일이 "즉시 실패"가 아니라
"몇 초 걸리는 실제 네트워크 호출"이 되면서 지연이 더 커졌다.

### 한계

- 동시성(`-c`)을 10으로만 쟀다 — PRD.md 에 지정된 동시성 값이 없어 임의로 골랐다. 값을 올리면
  대기열이 더 빨리 차서 p95 가 더 나빠질 수 있다
- 짧은 시간에 여러 번 몰아 쳐서 대기열이 누적된 상태일 수 있다 — 완전히 빈 대기열에서 시작한
  1회 실행값이 아니다
- 실제 키 측정은 3회다 — 키 없음 조건(5회)보다는 적게 반복했다

### 재현법

```powershell

& "<hey 경로>\hey.exe" -n 100 -c 10 -m POST `

```

> 400(`VALIDATION_FAILED`)으로 거부할 수 있다** — 실제로 겪었다(2026-08-14). 본문을 UTF-8
> 파일로 저장해두고 `-D 파일경로`로 읽게 하면 해결된다:
>
> ```powershell

>   -H "Content-Type: application/json" -H "X-User-Id: 5001" -H "X-User-Role: CUSTOMER" `

> ```

## a-2. D-069 적용 후 재측정 — `CallerRunsPolicy` → `DeferToReclassifyPolicy` + 재분류 스케줄러

> 김은빈이 `hey`로 직접 잰 값이다. 2026-08-15, 위 측정과 같은 로컬 docker 환경.

### 목표(0.1초) 대비

**아직 못 넘었다** — 가장 좋았던 6회차도 p95 0.1219초로 목표의 약 1.2배다. 다만 이전(6.36~18.77초, 개선 전)과는 자릿수가 다르다 — **최선의 경우 목표 근접, 최악의 경우도 이전 대비 6~15배 개선.**

### 왜 실행마다 값이 이렇게 흔들렸나 — 로그로 원인을 나눠서 봤다

이전 측정(`CallerRunsPolicy`)은 **5번을 반복해도 매번 비슷하게 느렸다** — 대기줄이 찰 때마다 접수 스레드가 AI 호출을 직접 기다려서, 반복해도 그 구조 자체는 안 바뀌었기 때문이다. 이번엔 실행마다 값이 계속 바뀌었는데, `docker compose logs app`으로 같은 시간대 로그를 대조해서 원인을 셋으로 나눴다.

1. **`classify_task_deferred queueSize=50 activeCount=8` 로그가 실제로 찍혔다** — 대기줄이 정말 찼고, 예전과 달리 접수 스레드는 그 자리에서 **버리고 즉시 반환**했다(블로킹 없음). 1회차의 8.4초 지연은 이 로그와 **동시에 나지 않았다** — 즉 대기줄 포화 자체는 더 이상 접수를 붙잡지 않는다.
2. **실제 `ANTHROPIC_API_KEY`가 켜져 있어 AI가 진짜로 호출됐는데, 테스트 본문("부하 테스트용 문의입니다")을 AI가 실제 문의가 아니라고 판단해 JSON 대신 설명 문장으로 답했다.** 그 결과 거의 매 건이 `PARSE_ERROR` → 재시도 3회(`classify_failed reason=PARSE_ERROR attempts=3`)를 탔다. 이 재시도들이 분류 스레드(최대 8개)를 오래 붙잡으면서 **DB 커넥션 경합**이 생겼을 가능성이 크다 — 확정하려면 커넥션 대기 시간을 별도로 재야 하는데 이번엔 안 쟀다.
3. **`StuckInquiryReclassifyScheduler`가 실제로 20건을 재발행했다**(`stuck_inquiries_requeued count=20`). 재발행 시점에 대기줄이 아직 찬 상태라 그 20건도 다시 `classify_task_deferred`로 미뤄지는 것까지 로그로 확인했다 — **부하가 계속되는 동안엔 스케줄러도 같이 밀린다는 뜻**이다. 부하가 멈추면 결국 처리된다는 것은 이번 측정으로 확인하지 못했다(별도 확인 필요, 아래 「한계」 참조).

**6회차가 유독 빠른 이유는 확정하지 못했다.** 5회차와 6회차 사이에 로그를 분석하느라 몇 분간 요청을 안 보냈고, 그 사이 **누적됐던 재시도·백로그가 빠졌을 가능성**이 있다 — 이게 맞다면 "부하가 멈추면 빨라진다"는 이 시스템의 의도된 동작이다. 다만 직접 확인한 것은 아니라 **추정**으로 남긴다.

### 한계

- **테스트 조건 자체가 오염돼 있었다** — 같은 문구를 500번 넘게 반복해서 AI가 매번 실제 문의로 안 읽고 거절했다. 이 재시도 부하는 **이번 테스트의 인공적인 부작용**이지 실제 트래픽에서 흔한 상황이 아니다. 실제 문의 문구로, 또는 `ANTHROPIC_API_KEY` 없이(파싱 즉시 실패해 재시도가 짧게 끝나는 조건) 재측정하면 이 노이즈 없이 더 깨끗한 값이 나올 것으로 예상되나 **아직 재지 않았다.**
- **"부하가 멈추면 스케줄러가 결국 다 회수한다"를 직접 확인하지 않았다** — `stuckReceived`가 시간이 지나 0으로 돌아오는지는 별도로 재야 한다.
- 6회 다 동시성 10 조건이다. 동시성 1 재측정(이전 측정 문서의 그것과 대응)은 안 했다.
- 서버를 재시작하지 않고 6번을 이어서 돌린 것이라 **완전히 빈 상태에서 시작한 값은 1회차뿐이다.**

### 재현법

위 §a 재현법과 동일 — 단 `ANTHROPIC_API_KEY`가 `.env`에 설정된 상태로 돌렸다.

## a-3. 조건을 갈라서 원인 좁히기 — 실제 문의 문구 / API 키 유무

위 a-2 는 테스트 문구("부하 테스트용 문의입니다")를 AI 가 실제 문의로 안 읽어서 매번 `PARSE_ERROR` 재시도가 걸리는 오염된 조건이었다. 두 조건을 갈라서 재시도 노이즈를 걷어내고 원인을 좁혔다.

### 조건 1 — 실제 문의 문구 + `ANTHROPIC_API_KEY` 있음

본문: `"3일 전에 주문했는데 아직도 배송이 시작되지 않았어요. 언제쯤 받을 수 있을까요?"`. 나머지 조건은 a-2 와 동일(백로그가 남은 상태에서 이어서 측정).

| 실행 | p50 | p95 | p99 |
| --- | --- | --- | --- |
| A | 0.138초 | 0.485초 | 0.498초 |
| B | 0.097초 | 0.255초 | 0.306초 |
| C | 0.258초 | 0.766초 | 0.961초 |

**PARSE_ERROR 재시도 노이즈를 없앴는데도 0.1초를 못 넘었다** — a-2 에서 "재시도가 원인일 것"이라 짐작했던 것이 이 조건으로 **반박됐다.**

### 조건 2 — 같은 실제 문구 + `ANTHROPIC_API_KEY` 없음(AI 호출 자체가 없음)

`.env` 의 `ANTHROPIC_API_KEY` 를 비우고 `docker compose up -d` 로 app 컨테이너만 재기동. 파싱이 즉시 실패해 분류가 거의 즉시 끝나는 조건(위 §a 원본 측정의 "키 없음" 조건과 같은 성격).

| 실행 | p50 | p95 | p99 |
| --- | --- | --- | --- |
| I | 0.086초 | 0.139초 | 0.155초 |
| II | 0.090초 | **0.482초** | 0.579초 |
| III | 0.070초 | 0.160초 | 0.172초 |

**AI 호출 자체를 없앴는데도 여전히 0.14~0.48초대다.**

### 그래서 원인은 — AI 도 대기줄 포화도 아니다

세 조건(오염된 문구+키 있음 / 실제 문구+키 있음 / 실제 문구+키 없음)을 나란히 두면:

| 조건 | p95 범위 |
| --- | --- |
| a-2 (문구 오염, 재시도 폭주) | 0.12 ~ 8.43초 |
| a-3 조건1 (실제 문구, AI 호출함) | 0.26 ~ 0.77초 |
| a-3 조건2 (실제 문구, AI 호출 없음) | 0.14 ~ 0.48초 |

AI 호출을 완전히 없애도(조건2) 남는 0.14~0.48초는 **접수 경로 자체의 기본 처리 비용**(Spring Security 필터 체인·JSON 직렬화·DB INSERT·동시 커넥션 경합)에서 온다는 뜻이다. 이는 `api-response-time-improvement-options.md`(PR #84)가 동시성 1 실측(PR #85, 경합이 없는 조건에서도 p95 0.85~3.12초)으로 이미 짐작했던 결론과 같은 방향이다 — **"AI 호출이 접수 경로에 얹혀 있는 한 목표를 못 넘는다"** 가 아니라, **AI 를 걷어내도 이 스택의 기본 비용 자체가 0.1초보다 크다.**

## a-4. 남은 잔차(0.1~0.8초대)를 더 좁혀본 기록 — 확정까지는 못 갔다

Hikari 지표(`/actuator/metrics/hikaricp.*`, `ROLE_MANAGER`)로 후속 조사를 했다. 결론부터: **몇 가지 가설은 반박했지만, 정확한 원인은 확정하지 못했다.**

### 반박된 가설 1 — "커넥션 풀 워밍업 문제"

재시작 직후라 20개 커넥션이 아직 다 안 만들어져서 그런가 싶어 `hikaricp.connections`(총)·`.idle`(유휴)·`.max` 를 확인했더니 **20/20/20 — 이미 풀이 꽉 찬 상태였다.** 이 상태에서 `hey` 를 다시 돌려도 p95 0.358~0.882초로 여전히 느린 꼬리가 나왔다. **워밍업 때문이 아니라는 것은 확인됐다.**

### 단서 — 커넥션 보유 시간이 비정상적으로 길다

`hikaricp.connections.acquire`(커넥션을 **기다린** 시간): COUNT 1067, MAX **0.5535초** — 관측된 p95/p99 스파이크(0.48~0.58초대)와 값이 거의 일치한다.

`hikaricp.connections.usage`(커넥션을 **붙잡고 쓴** 시간): COUNT 3900, TOTAL_TIME 869.468초 → 평균 **0.223초**, MAX **2.098초**. 단순 INSERT 한 건에 걸릴 시간이 아니다 — **뭔가가 커넥션을 예상보다 오래 붙잡고 있다.**

### 가설 2 — "테스트 문구가 전부 같아서 같은 정규화 키에 몰린다" — 확인 시도했으나 결론 못 냄

이 세션 내내 같은 문구를 100번씩 반복 전송해서 `normalized_key` 가 매번 동일했다 — 분류 스레드 8개가 같은 키를 두고 DB 락 경합을 벌였을 가능성을 의심했다. 확인하려고 문구를 매 요청 다르게(문의 유형 10종 순환 + 인덱스) 바꿔서 재봤는데, **이땐 `hey` 대신 PowerShell `ForEach-Object -Parallel` + `Invoke-RestMethod` 로 직접 짠 스크립트를 썼다.**

결과: p50 0.374초, p95 **2.317초**, max 2.320초 — 오히려 더 나빴다. 그런데 이 결과는 **깨끗한 비교가 아니다** — 도구 자체가 바뀌어서(Go 기반 `hey` vs PowerShell 병렬 처리) "정규화 키를 흩었더니 나빠졌다"인지 "PowerShell 부하 도구 자체가 `hey` 보다 느려서 나빠졌다"인지 **구분할 수 없다.** 그래서 이 가설은 **기각도 확정도 못 했다.**

### 결론 — 원인 미확정, 여기서 멈춘다

**정확한 근본 원인은 이번 조사로 확정하지 못했다.** 남은 후보는:

| 후보 | 근거 | 반박됐나 |
| --- | --- | --- |
| 커넥션 풀 워밍업 부족 | — | ✅ **반박됨** (풀이 꽉 찬 상태에서도 재현) |
| 같은 정규화 키로 인한 DB 락 경합 | 커넥션 보유 시간이 비정상적으로 김(평균 0.223초, 최대 2.1초) | ❓ **확인 시도했으나 측정 도구 차이로 결론 못 냄** |
| 접수 경로 자체의 기본 처리 비용(필터 체인·직렬화 등) | 동시성 1(김은빈, PR #85)에서도 목표 초과 | ❓ **가능성 있으나 이번 조사로 좁히지 못함** |
| 로컬 Docker Desktop(Windows) 환경 오버헤드 | 이 세션 전부 같은 노트북에서 잰 값 | ❓ **다른 기계로 재확인 필요** |

**다음에 볼 것** (별도 조사·다른 기계 필요):
1. 같은 `hey` 도구로 문구만 다르게(정규화 키를 실제로 흩어서) 재측정 — 이번엔 도구가 섞여서 못 봤다
2. `hikaricp.connections.usage` 가 왜 평균 0.223초·최대 2.1초까지 나오는지 — MySQL 쪽 슬로우 쿼리 로그·락 대기(`SHOW ENGINE INNODB STATUS`)를 함께 봐야 안다
3. 다른 컴퓨터(스펙 다른 기계)에서 같은 조건으로 재측정 — 로컬 Docker Desktop 오버헤드 여부 확인

### D-069 의 성과와 한계 — 최종 정리

- **✅ 해결**: 대기줄 포화 시 접수 스레드가 AI 호출을 인라인으로 기다리며 6~19초씩 걸리던 **구조적 블로킹**은 사라졌다(`classify_task_deferred` 로그로 확인, 블로킹 없이 즉시 반환). 이건 여러 조건(문구 오염/정상, API 키 있음/없음, 재시도 있음/없음)에서 일관되게 재현됐다 — 확실한 결론이다.
- **❌ 미해결**: p95 **0.1초 목표는 여전히 못 넘는다.** 최선의 조건에서도 0.12초, 대부분 0.14~0.88초대. 원인은 AI 도 대기줄 포화도 아니라는 것까지는 좁혔지만(§a-3), **정확히 무엇인지는 이 세션에서 확정하지 못했다** — 위 a-4 참조. 이건 애초에 D-069 의 범위(포화 정책 교체)가 다루는 문제가 아니었다.
- **범위 판단**: D-069 는 원래 목표(대기줄 포화로 인한 블로킹·유실 제거)를 달성했다. 남은 0.1초 목표 미달은 **별개 원인의 별개 문제**로 분리해 후속 조사로 넘긴다.

## b. 검토 목록 조회 — 10만 건 쌓인 상태 (목표 0.2초)

### 측정 조건

- 같은 docker 서버, `inquiry_review_queue` 를 10만 건으로 채운 상태 (`status='PENDING'`,
  전부 같은 문의·판정 1건을 가리키게 시드 — TRI-87 의 `ReviewQueueDeepPageExplainIT` 시드
  방식과 동일한 목적)
- 도구: `hey -n 100 -c 10 -m GET` → `GET /api/inquiry-review-queue?status=PENDING&page=0&size=20`
  (1페이지 — 가장 유리한 조건)

### 실측 값 (2026-08-13)

| 구간 | 값 |
| --- | --- |
| 최소(Fastest) | 1.19초 |
| p50 | 2.89초 |
| **p95** | **7.59초** |
| p99 / 최대 | 7.69초 |

**목표(0.2초) 못 넘었다 — 그것도 큰 차이로.** 1페이지(가장 빠른 조건)인데도 **가장 빠른 요청조차
목표의 6배**다.

### 왜 이렇게 느린가 — TRI-87 실측과 같은 원인, 더 나쁜 조건

`evidence/n-plus-one-review-queue.md`(측정 5ⓖ, TRI-87)가 이미 이 endpoint(`search()`,
`@EntityGraph`)의 10만 건 평균 응답시간을 **636ms**로 쟀다 — 그것만으로도 이미 목표(0.2초)를
넘는다. 이번 측정은 그보다도 훨씬 나쁘다(p50 2.89초). 차이는 측정 방식이다.

| | TRI-87 측정 5ⓖ | 이번 측정 |
| --- | --- | --- |
| 무엇을 쟀나 | 리포지토리 메서드 직접 호출 (JUnit 안) | 실제 HTTP 왕복 (Spring Security·JSON 직렬화·네트워크 포함) |
| 동시성 | 순차 호출 5회 | 동시 10 |

즉 이번 값에는 TRI-87 이 안 잰 비용(요청당 Spring Security 필터 체인, JSON 직렬화, 동시 요청간
DB 커넥션 경합)이 더해졌다 — 측정 (a) 와 같은 이유로 커넥션 풀(`maximum-pool-size: 20`)을
동시 10건이 나눠 쓰면서 대기 시간이 생겼을 가능성이 있다.

**TRI-87 이 이미 내린 결론(프로젝션 채택, 아직 미적용)이 이 값과 직접 연결된다** — `search()`
대신 `searchProjected()`를 controller/service 가 쓰게 바꾸면 TRI-87 측정 기준 약 56% 개선
(636ms → 280ms)이 기대되지만, **그래도 0.2초 목표에는 못 미친다.** 프로젝션 전환만으로는
이 목표를 못 채운다 — 인덱스·페이지네이션 전략 자체를 더 봐야 한다.

### 한계

- 동시성 10 으로 쟀다 — (a) 와 같은 이유로 순수 "1건 조회 지연"과 "동시 요청 커넥션 경합"이

  문의마다 다른 대상을 가리킬 때의 조인 비용은 별도다(TRI-87 의 한계와 동일)
- 1페이지만 쟀다 — TRI-87 의 500페이지 결과(더 느려짐)를 감안하면 깊은 페이지는 이보다 더
  나쁠 것으로 예상되나, 이번엔 재지 않았다(예상이지 실측 아님)

22배), 정확한 배수보다는 "동시성을 줄이면 확실히 나아지지만 그것만으로 목표에 못 미친다"는
방향성으로 읽는다.

**왜 이런 결과가 나왔을지 — 한 가지 가능성, 확실하진 않다**: 클라이언트가 동시에 요청을
1개만 보내도, **서버 안쪽 대기열이 이미 차 있었을 수 있다.** 오늘 하루 이 문서를 위해 같은
서버에 여러 차례 부하를 반복해서 넣었고, 그때 대기열로 넘어가 재시도 중이던 분류 작업이
아직 안 끝났을 가능성이 있다(§측정 시점 대기줄 상태의 `backlog.total: 158` 참고 — 다만
그 스냅샷은 이번 동시성 1 측정과 같은 시점 값은 아니다). 즉 "지금 요청이 동시에 몇 개
오는가"뿐 아니라 "그 전에 이미 쌓여 있던 처리 대기분"도 대기열이 차는 데 영향을 줄 수
있다. 이번 측정만으로는 두 가능성(① 개별 AI 호출이 원래도 가끔 느림 ② 이전 부하가 남아
대기열이 이미 일부 차 있었음)을 갈라내지 못한다 — 완전히 빈 상태에서 다시 재야 확실해진다.

**그래도 방법 ④(저장 단계 두기)의 설득력은 이 결과로 오히려 세진다.** 방법 ①②③은
"대기열이 찼을 때 접수가 AI를 대신 기다리는" 구조 자체는 그대로 두고, 그 일이 벌어질
확률이나 그때의 피해만 줄인다. 반면 ④는 **접수가 AI를 기다리는 경로 자체를 아예 없앤다** —
그래서 대기열에 무엇이 얼마나 쌓여 있든, 동시 요청이 몇 개든 접수 응답은 항상 빠르다. 이번
측정처럼 "동시성만으로 설명 안 되는 지연"이 나온다는 것 자체가, 경합을 줄이는 방법(①②③)
보다 경합 자체를 없애는 방법(④)이 더 안전하다는 근거가 된다.

**재현할 때 주의**: PowerShell에서 한글이 든 JSON을 `-d`로 인라인으로 넘기면 인코딩이 깨져
서버가 400(`VALIDATION_FAILED`)으로 거부한다 — 재현 중 실제로 겪었다. `-D 파일경로`로 UTF-8
파일을 읽게 하면 해결된다(아래 재현법 참조).
