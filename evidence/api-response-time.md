## a. 문의 접수 API — 100건 중 95번째로 느린 요청 (목표 0.1초)

### 측정 조건

- 서버: `docker compose up -d` (mysql + redis + app), `ANTHROPIC_API_KEY` 없음 (팀 기본 로컬 실행)
- 도구: `hey -n 100 -c 10 -m POST` → `POST /api/inquiries`
- 같은 본문을 100회 반복 (동시성 10)

### 실측 값 (2026-08-13)

100건을 요청해서 걸린 시간을 짧은 순서대로 줄 세웠을 때, p50과 p95, p99가
각각 몇 초 걸렸는지를 잰다. 목표로 삼은 건 **p95**가 0.1초 안이어야 한다는 것이었다.

| 구간 | 뜻 | 값 (5회 범위, 중앙값) |
| --- | --- | --- |
| 중간값 (p50) | 100건 중 50번째로 느린 요청 | 0.128 ~ 6.09초 (중앙값 0.243초) |
| **목표로 삼은 값 (p95)** | 100건 중 95번째로 느린 요청 | **6.36 ~ 8.82초 (중앙값 7.47초)** |
| 최상위 (p99) | 100건 중 99번째로 느린 요청 | 6.42 ~ 8.89초 |

**목표(0.1초)를 못 넘었다.** 우연이 아닌지 확인하려고 같은 측정을 5번 반복했는데, **5번 모두 p95가 6.36~8.82초로 측정되어 “가끔 느리다”가 아니라 매번 이 정도로 느리다는 것이 확인됐다.** 서버를 막 띄운 직후의 콜드 스타트 상태뿐 아니라 워밍업 후에도 비슷한 결과가 나왔다. 따라서 단순한 초기 워밍업 문제로 보기는 어렵다.

| 실행 | 중간값(p50) | 목표값(p95) | 비고 |
| --- | --- | --- | --- |
| 1 | 0.243초 | 7.47초 | 워밍업 후 |
| 2 | 0.260초 | 8.82초 | |
| 3 | 0.128초 | 7.50초 | |
| 4 | 6.09초  | 6.36초 | p50도 6.09초로 높게 측정됨 |
| 5 | 0.234초 | 7.23초 | |

### 원인 — 이미 PRD.md §9 가 예견한 트레이드오프였다

이 프로젝트는 AI에게 분류를 맡기는 줄(대기열)이 가득 찼을 때, **문의를 버리지 않고 접수
요청이 그 분류 작업을 대신 떠맡게** 만들어져 있다(D-045 ⑤ · 스프링의 `CallerRunsPolicy`).
PRD.md §9 는 이미 이렇게 적어뒀다:

> "느려지는 건 보이지만 사라지는 건 안 보인다. 대신 이 선택의 대가는 속도 목표 a(접수 0.1초)에
> 그대로 나타나므로, 측정할 때 대기줄 상태를 함께 기록한다."

이번 측정이 정확히 그 대가를 보여준다.

- 응답 시간 분포가 **두 덩어리로 갈라져 있다** — 73~74%는 1초 미만인데, 나머지 26~27%는
  6~9초대에 몰려 있고 그 사이(1~6초)는 거의 비어 있다
- 6~9초라는 시간대는 우연이 아닐 수 있다 — AI 호출이 실패해서 다시 시도할 때 기다리는
  시간(2초, 그다음 4초)과 크기가 비슷하기 때문이다. 대기열이 꽉 차서 접수 요청이 분류를
  떠맡았을 때, 그 재시도 대기 시간이 그대로 접수 응답 시간에 포함됐을 가능성이 있다. 다만
  이번 측정만으로 요청 하나하나의 지연 원인을 낱낱이 추적한 건 아니라서, 이게 진짜 원인이라고
  단정하지는 않는다.
- 설정 파일의 주석도 같은 증상을 미리 경고해뒀다: *"증상은 '접수가 느리다'로 나타나는데
  원인은 AI가 아니라 커넥션이라 오진하기 쉽다"* — 이번 측정으로 그 증상을 실제로 재현했다

### 측정 시점 대기줄 상태 (`GET /api/stats`, PRD.md §9 요구사항)

```json
{
  "classification": { "inquiriesTotal": 163, "autoAccepted": 3, "needsReview": 0, "failed": 160, "stuckReceived": 0 },
  "backlog": { "total": 158, "byReason": { "CLASSIFY_FAILED": 158 } },
  "aiCallSavings": { "inquiriesReceived": 213, "aiCallsMade": 160, "savingsRate": 0.249 }
}
```

`stuckReceived: 0` — 완전히 유실된 문의는 없다(D-017 의미로는 정상). 다만 `backlog.total: 158`
(전부 `CLASSIFY_FAILED`)이 위 지연의 정황과 일치한다 — 분류 시도가 몰리면서 대기열이 찼다.

### 추가 측정 — 실제 `ANTHROPIC_API_KEY` 로 재보니 더 나빴다

위 값은 전부 키 없이(분류가 매번 `FAILED`로 즉시 끝나는 조건) 잰 것이다. "실제 키가 있으면
더 빠를 것"이라고 짐작하고 한계로 적어뒀는데, **실제로 키를 넣고 재보니 그 짐작이 틀렸다** —
이래서 AI로 추정하지 않고 직접 재는 것이다 (CLAUDE.md 「AI 검증 규칙」).

| 구간 | 값 (실제 키, 3회) |
| --- | --- |
| 중간값 (p50) | 0.103 ~ 0.217초 |
| **목표로 삼은 값 (p95)** | **16.94 ~ 18.77초** — 키 없을 때(6.36~8.82초)보다 2배 이상 나쁘다 |
| 실패 | 1회차는 100건 중 5건이 20초 넘게 걸려 응답 자체를 못 받음(타임아웃). 2·3회차는 100건 다 받음 |

| 실행 | 중간값(p50) | 목표값(p95) | 최상위(p99) | 비고 |
| --- | --- | --- | --- | --- |
| 1 | 0.103초 | 18.77초 | — | 5건 타임아웃(20초 초과, 미수신) |
| 2 | 0.119초 | 17.66초 | 19.61초 | 100건 다 받음 |
| 3 | 0.217초 | 16.94초 | 18.86초 | 100건 다 받음 |

**3번 다 같은 그림이다** — 초반 다수(65~69%)는 2초 안에 빠르게 끝나고, 나머지가 13~20초대에
몰려 있다. 우연이 아니라 안정적으로 재현되는 현상이다.

**왜 더 나쁜가**: 키가 없으면 "분류를 시도했는데 바로 실패"라 접수 스레드가 금방 풀려나는데,
**키가 있으면 접수 스레드가 진짜 Claude API 응답을 기다려야 한다.** 대기열이 찼을 때 접수
스레드가 분류를 떠안는 구조(`CallerRunsPolicy`)는 같지만, 떠안는 일이 "즉시 실패"가 아니라
"몇 초 걸리는 실제 네트워크 호출"이 되면서 지연이 더 커졌다.

### 한계

- 동시성(`-c`)을 10으로만 쟀다 — PRD.md 에 지정된 동시성 값이 없어 임의로 골랐다. 값을 올리면
  대기열이 더 빨리 차서 p95 가 더 나빠질 수 있다
- 짧은 시간에 여러 번 몰아 쳐서 대기열이 누적된 상태일 수 있다 — 완전히 빈 대기열에서 시작한
  1회 실행값이 아니다
- 실제 키 측정은 3회다 — 키 없음 조건(5회)보다는 적게 반복했다

> 파일로 저장해두고 `-D 파일경로`로 읽게 하면 해결된다:
>

## b. 검토 목록 조회 — 10만 건 쌓인 상태 (목표 0.2초)

### 실측 값 (2026-08-13)

| 구간 | 값 |
| --- | --- |
| 최소(Fastest) | 1.19초 |
| p50 | 2.89초 |
| **p95** | **7.59초** |
| p99 / 최대 | 7.69초 |

**목표(0.2초) 못 넘었다 — 그것도 큰 차이로.** 1페이지(가장 빠른 조건)인데도 **가장 빠른 요청조차
목표의 6배**다.

### 왜 이렇게 느린가 — TRI-87 실측과 같은 원인, 더 나쁜 조건

`evidence/n-plus-one-review-queue.md`(측정 5ⓖ, TRI-87)가 이미 이 endpoint(`search()`,
`@EntityGraph`)의 10만 건 평균 응답시간을 **636ms**로 쟀다 — 그것만으로도 이미 목표(0.2초)를
넘는다. 이번 측정은 그보다도 훨씬 나쁘다(p50 2.89초). 차이는 측정 방식이다.

| | TRI-87 측정 5ⓖ | 이번 측정 |
| --- | --- | --- |
| 무엇을 쟀나 | 리포지토리 메서드 직접 호출 (JUnit 안) | 실제 HTTP 왕복 (Spring Security·JSON 직렬화·네트워크 포함) |
| 동시성 | 순차 호출 5회 | 동시 10 |

즉 이번 값에는 TRI-87 이 안 잰 비용(요청당 Spring Security 필터 체인, JSON 직렬화, 동시 요청간
DB 커넥션 경합)이 더해졌다 — 측정 (a) 와 같은 이유로 커넥션 풀(`maximum-pool-size: 20`)을
동시 10건이 나눠 쓰면서 대기 시간이 생겼을 가능성이 있다.

**TRI-87 이 이미 내린 결론(프로젝션 채택, 아직 미적용)이 이 값과 직접 연결된다** — `search()`
대신 `searchProjected()`를 controller/service 가 쓰게 바꾸면 TRI-87 측정 기준 약 56% 개선
(636ms → 280ms)이 기대되지만, **그래도 0.2초 목표에는 못 미친다.** 프로젝션 전환만으로는
이 목표를 못 채운다 — 인덱스·페이지네이션 전략 자체를 더 봐야 한다.

## 개선 방안 (2026-08-13 추가)

> **이 절에 나오는 개선 효과는 전부 예상이다.** 위에서 실제로 잰 것은 "지금 얼마나 느린가"뿐이고,
> 아래 방법들은 아직 어느 것도 적용·재측정하지 않았다.

### a — 접수 API: 5가지 선택지

원인은 위 「종합 판정」에 적힌 대로다 — AI에게 분류를 맡기는 줄(대기열)이 다 차면, **원래는
따로 처리돼야 할 AI 호출을 접수 요청을 처리하던 쪽이 대신 떠맡아 처리한다.** 그동안 그 접수
요청은 AI 응답이 끝날 때까지 기다려야 해서 느려진다.

이건 실수로 그렇게 된 게 아니라 **일부러 정한 방식이다**(`DECISIONS.md` D-045 ⑤). 다른
선택지는 "줄이 다 차면 그 문의는 처리하지 않고 넘어간다"였는데, 그러면 접수는 항상 빠르지만
**그 문의는 영영 분류되지 않고 그 사실도 아무도 모르게 된다.** 그래서 "느려지더라도 문의를
잃어버리지 않는" 지금 방식을 택했다. 그러니 고치는 방법도 "문의를 잃어버리지 않는다"는
원칙은 지키는 선에서만 찾는다.

#### 최악의 경우는 얼마나 나쁠 수 있나

AI 호출 한 번에 최대 30초까지 기다리고, 실패하면 2초 쉬었다 다시 시도, 또 실패하면 4초 쉬었다
한 번 더 시도한다 — 최대 3번까지 시도한다.

```text
1차 시도 30초 + 2초 대기 + 2차 시도 30초 + 4초 대기 + 3차 시도 30초 = 최악 96초
```

<sub>설정값: `anthropic.timeout: 30s`(1회 대기 상한) ·
`classification.retry.max-attempts: 3`(최대 시도 횟수) · 재시도 사이 대기 2초→4초</sub>

**AI가 계속 응답을 안 하면 접수 요청 하나가 최대 96초까지 걸릴 수 있다.** 이번에 실제로 잰
값(16.9~18.8초)이 이보다 훨씬 짧았던 건 **대부분 첫 번째 시도에서 성공했기 때문**이다 — AI
쪽 사정이 나쁜 날엔 이보다 훨씬 나빠질 수 있다.

#### 선택지 비교

| # | 방법 | 비용 | 좋은 점 | 나쁜 점 |
| --- | --- | --- | --- | --- |
| ① | 대기열 크기를 늘린다(`50 → 500`) | 설정 한 줄 | 대기열이 꽉 차는 일이 크게 줄어든다. 바로 적용 가능 | 대기열은 메모리에만 있어서, 서버가 갑자기 꺼지면 대기 중이던 문의가 지금보다 10배 더 많이 한꺼번에 사라진다. **근본적인 해결이 아니라 문제를 뒤로 미루는 것뿐** |
| ② | 동시에 처리하는 스레드 수를 늘린다(`max-size: 8 → 12`) | 설정 한 줄 | 한 번에 더 많이 처리해서 대기열이 덜 찬다 | DB 연결 수(20개)가 한계다 — 이 값을 너무 늘리면 이번엔 **접수 요청이 DB 연결을 못 구해 느려지는 다른 문제**가 생길 수 있다(어긋나면 서버가 아예 안 뜨게 미리 막아둠, D-047 ⓑ) |
| ③ | AI 응답을 기다리는 시간을 줄인다(`30s → 10s`) | 설정 한 줄 | 최악의 경우가 96초 → 약 36초로 줄어든다 | 정상적으로 오래 걸리는 요청도 중간에 끊겨 실패로 처리된다 — 그만큼 **사람이 직접 확인해야 할 검토 목록이 늘어난다.** 속도 문제를 사람이 하는 일로 떠넘기는 셈 |

| ⑤ | 메시지 큐(Kafka·RabbitMQ)를 새로 도입한다 | 인프라 추가 | 접수와 분류가 완전히 분리되고, 재시도·순서·중복 처리를 시스템이 대신 해준다 | 새 시스템을 설치하고 계속 운영·관리해야 한다. 지금 규모엔 과하다. ④와 얻는 효과는 비슷한데 비용이 훨씬 크다 |

> ❌ **"대기열이 차면 그냥 처리하지 않고 넘어간다"는 검토하지 않는다.** 접수는 바로 빨라지지만,
> 분류되지 않은 문의가 조용히 사라지는 건 이 시스템이 존재하는 이유("자동으로 확정된 결과를
> 무조건 믿지 않는다")와 정반대다. 굳이 하려면 `DECISIONS.md`에 새 결정 항목부터 남겨야 한다.

#### 왜 ④번이 가장 유력한가

세 가지 이유가 있다.

1. **지금 방식의 약점까지 같이 없앤다.** 지금은 "이 문의를 분류해야 한다"는 신호가 서버의
   메모리에만 있어서, 서버가 갑자기 꺼지면 그 신호도 같이 사라진다는 걸 이미 알려진 한계로
   적어뒀다. 이번 측정 중에도 실패했던 응답 3건이 1시간 뒤엔 저절로 성공했는데, 신호를 DB에
   남겨두는 ④번 방식이었다면 그런 것도 자동으로 다시 처리됐을 일이다. 새 프로그램을 추가로
   들여오지 않으면서 속도 문제와 "문의를 잃어버릴 뻔한 문제"를 동시에 해결하는 셈이다.
2. **새로 낸 아이디어가 아니라 이미 정해뒀던 다음 단계다.** 이 팀은 예전에 이미 "접수 속도가
   목표를 크게 벗어나면(예: 1초 넘으면), 접수와 분류 사이에 저장 단계를 두는 방식을 다음
   단계로 쓴다"고 정해뒀다(`DECISIONS.md` D-045 재평가 조항). 지금 실측값(6.4~18.8초)은 그
   기준(1초)을 이미 한참 넘었고, "접수와 분류 사이에 저장 단계를 둔다"가 바로 ④번이다. 즉
   ④는 이번에 처음 나온 제안이 아니라, 속도가 이 정도로 나빠지면 쓰기로 예전부터 정해둔
   방법이다.
3. **나중에 규모가 커져도 구조를 다시 짤 필요가 없다.** ④번은 "신호를 남기는 쪽"과 "그 신호를
   보고 처리하는 쪽"이 이미 나뉘어 있다. 그래서 문의량이 훨씬 많아져서 지금의 주기적 확인
   방식으로는 부족해지면, 확인하는 부분만 메시지 큐(⑤번)로 바꿔 끼우면 된다 — 접수 API나
   분류 로직 자체는 손댈 필요가 없다. 그래서 ④는 지금 당장만 쓰는 임시방편이 아니라, 나중에
   규모가 커져도 다시 짓지 않아도 되는 설계다.

### b — 검토 목록 조회: 완전히 다른 문제라 답도 다르다

a와 b를 같은 원인으로 묶으면 안 된다. b가 느린 이유는 대기열 문제가 아니라, **화면에 필요한
값보다 훨씬 많은 데이터를 조회하기 때문**이다. 지금 목록 조회는 `@EntityGraph`(연관된
데이터까지 한 번에 통째로 불러오는 JPA 기능)를 써서 문의·분류 결과 엔티티 전체를 읽어오는데,
정작 화면 응답에 필요한 값은 6개 필드뿐이다. **b의 주요 개선 후보는 이 `@EntityGraph` 기반
조회를, 필요한 값만 뽑아오는 방식(프로젝션)으로 바꾸는 것이다.**

`evidence/n-plus-one-review-queue.md`가 이미 "필요한 값만 읽어오도록" 바꿔서 재봤다
(636ms → 280ms, 빨라지는 방향은 확실하지만 정확히 몇 % 빨라지는지는 잴 때마다 값이
달랐다). **다만 이렇게 바꿔도 목표(200ms)는 아직 못 채운다(280ms)** — 이 방법 하나로
목표가 채워지는 게 아니라, 목표 달성을 위한 여러 조건 중 하나일 뿐이다.

**결론: 동시성 1(클라이언트가 한 번에 요청 1개만 보내는 조건)에서도 목표(0.1초)를 못

22배), 정확한 배수보다는 "동시성을 줄이면 확실히 나아지지만 그것만으로 목표에 못 미친다"는
방향성으로 읽는다.

**왜 이런 결과가 나왔을지 — 한 가지 가능성, 확실하진 않다**: 클라이언트가 동시에 요청을
1개만 보내도, **서버 안쪽 대기열이 이미 차 있었을 수 있다.** 오늘 하루 이 문서를 위해 같은
서버에 여러 차례 부하를 반복해서 넣었고, 그때 대기열로 넘어가 재시도 중이던 분류 작업이
아직 안 끝났을 가능성이 있다(§측정 시점 대기줄 상태의 `backlog.total: 158` 참고 — 다만
그 스냅샷은 이번 동시성 1 측정과 같은 시점 값은 아니다). 즉 "지금 요청이 동시에 몇 개
오는가"뿐 아니라 "그 전에 이미 쌓여 있던 처리 대기분"도 대기열이 차는 데 영향을 줄 수
있다. 이번 측정만으로는 두 가능성(① 개별 AI 호출이 원래도 가끔 느림 ② 이전 부하가 남아
대기열이 이미 일부 차 있었음)을 갈라내지 못한다 — 완전히 빈 상태에서 다시 재야 확실해진다.

**그래도 방법 ④(저장 단계 두기)의 설득력은 이 결과로 오히려 세진다.** 방법 ①②③은
"대기열이 찼을 때 접수가 AI를 대신 기다리는" 구조 자체는 그대로 두고, 그 일이 벌어질
확률이나 그때의 피해만 줄인다. 반면 ④는 **접수가 AI를 기다리는 경로 자체를 아예 없앤다** —
그래서 대기열에 무엇이 얼마나 쌓여 있든, 동시 요청이 몇 개든 접수 응답은 항상 빠르다. 이번
측정처럼 "동시성만으로 설명 안 되는 지연"이 나온다는 것 자체가, 경합을 줄이는 방법(①②③)
보다 경합 자체를 없애는 방법(④)이 더 안전하다는 근거가 된다.
