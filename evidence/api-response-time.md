# 속도 목표 a·b 실측 (TRI-74, PRD.md §9)

> `hey`로 직접 잰 값이다. 목표를 못 넘은 것도 그대로 적는다 (AI 추정 금지, CLAUDE.md 「AI 검증 규칙」).

## a. 문의 접수 API — 100건 중 95번째로 느린 요청 (목표 0.1초)

### 측정 조건

- 서버: `docker compose up -d` (mysql + redis + app), `ANTHROPIC_API_KEY` 없음 (팀 기본 로컬 실행)
- 도구: `hey -n 100 -c 10 -m POST` → `POST /api/inquiries`
- 같은 본문을 100회 반복 (동시성 10)

### 실측 값 (2026-08-13)

100건을 요청해서 걸린 시간을 짧은 순서대로 줄 세웠을 때, p50과 p95, p99가
각각 몇 초 걸렸는지를 잰다. 목표로 삼은 건 **p95**가 0.1초 안이어야 한다는 것이었다.

| 구간 | 뜻 | 값 |
| --- | --- | --- |
| 중간값 (p50) | 100건 중 50번째로 느린 요청 | 5번 측정에서 0.128 ~ 6.09초 |
| **목표로 삼은 값 (p95)** | 100건 중 95번째로 느린 요청 | **5번 측정에서 6.36 ~ 8.82초** |
| 최상위 (p99) | 100건 중 99번째로 느린 요청 | 6.42 ~ 8.89초 |

**목표(0.1초)를 못 넘었다.** 우연이 아닌지 확인하려고 같은 측정을 5번 반복했는데, **5번 다
95번째로 느린 요청이 6.36~8.82초로 나와서, "가끔 느리다"가 아니라 매번 이 정도로 느리다는
게 확인됐다.** 서버를 막 띄운 직후(첫 요청들이 느린 "콜드 스타트" 상태)든 아니든 비슷하게
느렸다 — 그러니까 "서버가 아직 안 데워져서 느린 것"은 아니다.

| 실행 | 중간값(p50) | 목표값(p95) | 비고 |
| --- | --- | --- | --- |
| 1 | 0.243초 | 7.47초 | 서버를 갓 띄운 직후 |
| 2 | 0.260초 | 8.82초 | |
| 3 | 0.128초 | 7.50초 | |
| 4 | 6.09초  | 6.36초 | 중간값 자체가 이미 느린 쪽으로 밀림 |
| 5 | 0.234초 | 7.23초 | |

### 원인 — 이미 PRD.md §9 가 예견한 트레이드오프였다

이 프로젝트는 비동기 분류 대기열이 가득 찼을 때 **문의를 버리지 않고, 접수한 요청이 대신
분류를 떠안게** 한다 (`CallerRunsPolicy`, `application.yml` `classification.async.queue-capacity`
주석 · D-045 ⑤). PRD.md §9 는 이미 이렇게 적어뒀다:

> "느려지는 건 보이지만 사라지는 건 안 보인다. 대신 이 선택의 대가는 속도 목표 a(접수 0.1초)에
> 그대로 나타나므로, 측정할 때 대기줄 상태를 함께 기록한다."

이번 측정이 정확히 그 대가를 보여준다.

- 응답 시간 분포가 **이봉(bimodal)** 이다 — 73~74%는 1초 미만인데, 나머지 26~27%는 6~9초대에
  몰려 있고 그 사이(1~6초)는 거의 비어 있다
- 6~9초 구간은 `classification.retry`의 초기 백오프 2초 → 4초와 시간 규모가 유사하다. 대기열이 포화된 시점에 `CallerRunsPolicy`가 접수 스레드에서 분류 작업을 수행하게   되면서 재시도 백오프가 접수 응답시간에 포함됐을 가능성이 있다. 다만 이번 측정만으로 개별 요청의 지연 원인을 추적한 것은 아니므로 원인을 확정할 수는 없다.
- `application.yml` 주석도 같은 증상을 미리 경고해뒀다: *"증상은 '접수가 느리다'로 나타나는데
  원인은 AI가 아니라 커넥션이라 오진하기 쉽다"* — 이번 측정으로 그 증상을 실제로 재현했다

### 측정 시점 대기줄 상태 (`GET /api/stats`, PRD.md §9 요구사항)

```json
{
  "classification": { "inquiriesTotal": 163, "autoAccepted": 3, "needsReview": 0, "failed": 160, "stuckReceived": 0 },
  "backlog": { "total": 158, "byReason": { "CLASSIFY_FAILED": 158 } },
  "aiCallSavings": { "inquiriesReceived": 213, "aiCallsMade": 160, "savingsRate": 0.249 }
}
```

`stuckReceived: 0` — 완전히 유실된 문의는 없다(D-017 의미로는 정상). 다만 `backlog.total: 158`
(전부 `CLASSIFY_FAILED`)이 위 지연의 정황과 일치한다 — 분류 시도가 몰리면서 대기열이 찼다.

### 추가 측정 — 실제 `ANTHROPIC_API_KEY` 로 재보니 더 나빴다

위 값은 전부 키 없이(분류가 매번 `FAILED`로 즉시 끝나는 조건) 잰 것이다. "실제 키가 있으면
더 빠를 것"이라고 짐작하고 한계로 적어뒀는데, **실제로 키를 넣고 재보니 그 짐작이 틀렸다** —
이래서 AI로 추정하지 않고 직접 재는 것이다 (CLAUDE.md 「AI 검증 규칙」).

| 구간 | 값 (실제 키, 3회) |
| --- | --- |
| 중간값 (p50) | 0.103 ~ 0.217초 |
| **목표로 삼은 값 (p95)** | **16.94 ~ 18.77초** — 키 없을 때(6.36~8.82초)보다 2배 이상 나쁘다 |
| 실패 | 1회차는 100건 중 5건이 20초 넘게 걸려 응답 자체를 못 받음(타임아웃). 2·3회차는 100건 다 받음 |

| 실행 | 중간값(p50) | 목표값(p95) | 최상위(p99) | 비고 |
| --- | --- | --- | --- | --- |
| 1 | 0.103초 | 18.77초 | — | 5건 타임아웃(20초 초과, 미수신) |
| 2 | 0.119초 | 17.66초 | 19.61초 | 100건 다 받음 |
| 3 | 0.217초 | 16.94초 | 18.86초 | 100건 다 받음 |

**3번 다 같은 그림이다** — 초반 다수(65~69%)는 2초 안에 빠르게 끝나고, 나머지가 13~20초대에
몰려 있다. 우연이 아니라 안정적으로 재현되는 현상이다.

**왜 더 나쁜가**: 키가 없으면 "분류를 시도했는데 바로 실패"라 접수 스레드가 금방 풀려나는데,
**키가 있으면 접수 스레드가 진짜 Claude API 응답을 기다려야 한다.** 대기열이 찼을 때 접수
스레드가 분류를 떠안는 구조(`CallerRunsPolicy`)는 같지만, 떠안는 일이 "즉시 실패"가 아니라
"몇 초 걸리는 실제 네트워크 호출"이 되면서 지연이 더 커졌다.

### 한계

- 동시성(`-c`)을 10으로만 쟀다 — PRD.md 에 지정된 동시성 값이 없어 임의로 골랐다. 값을 올리면
  대기열이 더 빨리 차서 p95 가 더 나빠질 수 있다
- 짧은 시간에 여러 번 몰아 쳐서 대기열이 누적된 상태일 수 있다 — 완전히 빈 대기열에서 시작한
  1회 실행값이 아니다
- 실제 키 측정은 3회다 — 키 없음 조건(5회)보다는 적게 반복했다

### 재현법

```powershell
docker compose up -d
& "<hey 경로>\hey.exe" -n 100 -c 10 -m POST `
  -H "Content-Type: application/json" -H "X-User-Id: 5001" -H "X-User-Role: CUSTOMER" `
  -d '{"content":"부하 테스트용 문의입니다.","channel":"WEB"}' `
  http://localhost:8080/api/inquiries
```

## b. 검토 목록 조회 — 10만 건 쌓인 상태 (목표 0.2초)

### 측정 조건

- 같은 docker 서버, `inquiry_review_queue` 를 10만 건으로 채운 상태 (`status='PENDING'`,
  전부 같은 문의·판정 1건을 가리키게 시드 — TRI-87 의 `ReviewQueueDeepPageExplainIT` 시드
  방식과 동일한 목적)
- 도구: `hey -n 100 -c 10 -m GET` → `GET /api/inquiry-review-queue?status=PENDING&page=0&size=20`
  (1페이지 — 가장 유리한 조건)

### 실측 값 (2026-08-13)

| 구간 | 값 |
| --- | --- |
| 최소(Fastest) | 1.19초 |
| p50 | 2.89초 |
| **p95** | **7.59초** |
| p99 / 최대 | 7.69초 |

**목표(0.2초) 못 넘었다 — 그것도 큰 차이로.** 1페이지(가장 빠른 조건)인데도 **가장 빠른 요청조차
목표의 6배**다.

### 왜 이렇게 느린가 — TRI-87 실측과 같은 원인, 더 나쁜 조건

`evidence/n-plus-one-review-queue.md`(측정 5ⓖ, TRI-87)가 이미 이 endpoint(`search()`,
`@EntityGraph`)의 10만 건 평균 응답시간을 **636ms**로 쟀다 — 그것만으로도 이미 목표(0.2초)를
넘는다. 이번 측정은 그보다도 훨씬 나쁘다(p50 2.89초). 차이는 측정 방식이다.

| | TRI-87 측정 5ⓖ | 이번 측정 |
| --- | --- | --- |
| 무엇을 쟀나 | 리포지토리 메서드 직접 호출 (JUnit 안) | 실제 HTTP 왕복 (Spring Security·JSON 직렬화·네트워크 포함) |
| 동시성 | 순차 호출 5회 | 동시 10 |

즉 이번 값에는 TRI-87 이 안 잰 비용(요청당 Spring Security 필터 체인, JSON 직렬화, 동시 요청간
DB 커넥션 경합)이 더해졌다 — 측정 (a) 와 같은 이유로 커넥션 풀(`maximum-pool-size: 20`)을
동시 10건이 나눠 쓰면서 대기 시간이 생겼을 가능성이 있다.

**TRI-87 이 이미 내린 결론(프로젝션 채택, 아직 미적용)이 이 값과 직접 연결된다** — `search()`
대신 `searchProjected()`를 controller/service 가 쓰게 바꾸면 TRI-87 측정 기준 약 56% 개선
(636ms → 280ms)이 기대되지만, **그래도 0.2초 목표에는 못 미친다.** 프로젝션 전환만으로는
이 목표를 못 채운다 — 인덱스·페이지네이션 전략 자체를 더 봐야 한다.

### 한계

- 동시성 10 으로 쟀다 — (a) 와 같은 이유로 순수 "1건 조회 지연"과 "동시 요청 커넥션 경합"이
  섞여 있다. 분리해서 재려면 `-c 1` 로 별도 측정이 필요하다(이번엔 안 했다)
- 시드가 전부 같은 문의·판정 1건을 가리킨다 — TRI-87 과 같은 단순화이지만, 실제 운영처럼
  문의마다 다른 대상을 가리킬 때의 조인 비용은 별도다(TRI-87 의 한계와 동일)
- 1페이지만 쟀다 — TRI-87 의 500페이지 결과(더 느려짐)를 감안하면 깊은 페이지는 이보다 더
  나쁠 것으로 예상되나, 이번엔 재지 않았다(예상이지 실측 아님)

### 재현법

```powershell

& "<hey 경로>\hey.exe" -n 100 -c 10 -m GET `
```

## 종합 판정

**a·b 둘 다 목표를 못 넘었다.** 둘 다 원인이 짐작 가는 자리가 있다.

- a — 비동기 분류 대기열이 찼을 때 접수 스레드가 분류를 떠안는 설계(D-045 ⑤)의 대가. PRD.md §9
  가 이미 예견한 트레이드오프였다. **실제 `ANTHROPIC_API_KEY`로 재보니 더 나빴다**(p95
  16.94~18.77초, 3회 실행, 키 없을 때의 2배 이상) — 접수 스레드가 떠안는 일이 "즉시 실패"가
  아니라 "몇 초 걸리는 실제 API 호출"이 되기 때문이다
- b — TRI-87 이 이미 측정한 `@EntityGraph` 오버헤드에, 이번엔 HTTP 왕복·동시 커넥션 경합까지
  더해졌다. 프로젝션 전환(TRI-87 후속 작업)이 되면 개선되겠지만 그것만으로 0.2초를 채운다고
  단정하지 않는다 — 재보기 전에는 모른다

**다음에 볼 것** (이 티켓 범위 밖, 후속 검토용)

1. `searchProjected` 를 controller/service 가 실제로 쓰도록 교체 (TRI-87 이 이미 갈라둔 후속 작업)
2. 커넥션 풀 경합이 a·b 공통 원인인지 — 동시성 1로 재측정해 순수 지연과 분리
3. b 를 동시성 1로도 재서, 이번 7.59초 중 얼마가 "커넥션 경합"이고 얼마가 "쿼리 자체 비용"인지 나누기
