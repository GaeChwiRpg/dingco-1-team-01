# 고객 문의 목록 조회 — `(customer_id, received_at)` 인덱스 실측 (D-071)

> 직접 잰 값이다. AI 추정 없음. 관련: `DECISIONS.md` D-071,
> `evidence/measurement-5-list-query-explain.md` G 항목(이 문제를 처음 기록한 자리)

## 무엇을 재나 — 미해결로 남아 있던 자리

측정 5(TRI-36)의 **G 항목**이 이렇게 적어뒀다.

> *"고객 범위 쿼리는 현재 인덱스를 못 탄다 — 풀스캔 + filesort. 기존 인덱스 3개가 전부
> `status`·`normalized_key` 선행이라 `customer_id` 필터를 못 받는다. (…) 후보 대응은
> `(customer_id, received_at)` 인덱스이나, **지금 붙이지 않는다** — 쓰기 비용을 얹기 전에
> 고객 목록 p95 가 실제로 문제인지 먼저 본다(D-018)."*

그 측정을 한다. **읽기 이득만 재면 D-018 이 요구한 판단을 못 하므로 쓰기 비용을 같이 잰다.**

## 측정 조건

**두 환경에서 각각 쟀다.** 하나는 재현 테스트, 하나는 독립 컨테이너다. 서로 다른 자리에서 같은
방향이 나오는지 보기 위해서다.

| 항목 | ① 재현 테스트 (기준) | ② 독립 컨테이너 (교차 확인) |
| --- | --- | --- |
| 실행 | `CustomerScopeExplainIT` (Testcontainers) | `docker exec` 로 SQL 직접 |
| 엔진 | `mysql:8.0` | MySQL 8.0.45 (`mysql:8.0`) |
| DB | 테스트가 띄운 일회용 | `triage_perf` — **`triage_db` 를 오염시키지 않으려고 따로 만들었다** |
| 스키마 | Flyway V1~V4 적용 | `V2` 의 `inquiries` DDL 을 손으로 |
| 행 수 | 100,000 | 100,000 |
| 고객 분포 | 5,000명. `customer_id=1` 에 **2,000건**, 나머지는 20건 안팎 | 같음 |
| 통계 | 시드 후 · 인덱스 추가 후 `ANALYZE TABLE` | 같음 |

아래 수치는 별도 표기가 없으면 **①의 중앙값**이다. ①이 기준인 이유는 **커밋돼 있어 누구나 다시
돌릴 수 있기 때문**이다.

**고객 하나를 일부러 크게 만든 이유** — 5,000명에 균등 분산하면 한 고객이 20건씩이라
*"결과가 작아서 빠른 것"* 과 *"인덱스가 들어서 빠른 것"* 이 구분되지 않는다. 2,000건 보유
고객을 함께 재서 **결과가 커도 이득이 남는지**를 본다.

## 개선 전 — 인덱스 3개

```
EXPLAIN  SELECT * FROM inquiries WHERE customer_id=2003 ORDER BY received_at DESC LIMIT 20
```

| 쿼리 | type | key | rows | Extra |
| --- | --- | --- | --- | --- |
| 일반 고객 1페이지 | `ALL` | `NULL` | 99,444 | Using where; **Using filesort** |
| 다건 고객 1페이지 | `ALL` | `NULL` | 99,444 | Using where; **Using filesort** |
| 페이징 `COUNT` | `ALL` | `NULL` | 99,444 | Using where |

`possible_keys` 자체가 `NULL` 이다. **옵티마이저가 인덱스를 고르지 않은 것이 아니라 고를 수 있는
인덱스가 없다.** 세 인덱스가 전부 `status`·`normalized_key` 선행이라 `customer_id` 등치를 받지
못한다.

`EXPLAIN ANALYZE` 로 본 실제 실행:

| 쿼리 | 실제 읽은 행 | 소요(중앙값) | 3회 | ② 교차 확인 |
| --- | --- | --- | --- | --- |
| 일반 고객 1페이지 | **100,000** | **32.2ms** | 59.1 / 32.2 / 23.0 | 30.5ms |
| 다건 고객 1페이지 | **100,000** | 22.7ms | 22.6 / 22.7 / 22.7 | 23.4ms |
| 페이징 `COUNT` | **100,000** | 10.5ms | 10.7 / 10.5 / 10.5 | 10.3ms |

**20건을 돌려주려고 10만 행을 읽고 정렬한 뒤 버린다.** 그리고 페이지 요청 한 번에 목록과
`COUNT` 가 함께 나가므로 **풀스캔이 두 번** 일어난다.

## 인덱스 추가

```sql
ALTER TABLE inquiries ADD KEY idx_inquiries_customer_received (customer_id, received_at);
-- 10만 건에서 168.697 ms
```

**컬럼 순서가 이 인덱스의 전부다.** `customer_id` 가 등치라 선행에 두면 뒤의 `received_at` 이 이미
정렬된 상태로 붙어 필터와 정렬을 한 인덱스가 함께 커버한다. 뒤집으면(`received_at, customer_id`)
정렬은 되지만 `customer_id` 로 좁히지 못해 전 구간을 훑는다.

## 개선 후 — 인덱스 4개

| 쿼리 | type | key | rows | Extra |
| --- | --- | --- | --- | --- |
| 일반 고객 1페이지 | `ref` | `idx_inquiries_customer_received` | 19 | **Backward index scan** |
| 다건 고객 1페이지 | `ref` | 〃 | 2,000 | Backward index scan |
| 페이징 `COUNT` | `ref` | 〃 | 19 | **Using index** |

`COUNT` 는 **커버링 인덱스**가 됐다. 인덱스만 읽고 테이블에 가지 않는다.

| 쿼리 | 개선 전 | 개선 후 | 3회(개선 후) | 실제 읽은 행 |
| --- | --- | --- | --- | --- |
| **일반 고객 1페이지** | **32.2ms** | **0.0222ms** | 0.104 / 0.0217 / 0.0222 | 100,000 → **19** |
| 다건 고객 1페이지 | 22.7ms | 0.0169ms | 0.0313 / 0.0169 / 0.0153 | 100,000 → **20** |
| 페이징 `COUNT` | 10.5ms | 0.0054ms | 0.0055 / 0.0033 / 0.0054 | 100,000 → **19** |

**시간보다 「실제 읽은 행」을 먼저 읽어야 한다.** 개선 후 값은 수십 마이크로초대라 측정 정밀도와
버퍼 풀 상태에 좌우된다(②에서는 0.0717 / 0.049 / 0.0139ms 로, 같은 방향이되 값이 다르다).
**환경에 안 흔들리는 것은 읽은 행 수다.**

그리고 그 행 수가 말하는 것은 **성질이 바뀌었다**는 것이다. 개선 전은 읽는 행이 **전체 건수**에
비례했고, 개선 후는 **그 고객의 보유 건수**에만 비례한다. 데이터가 10배로 늘어도 한 고객의 목록
조회는 그대로다.

### 실제로 나가는 쿼리 모양에서도 타는가

`searchForCustomer` 는 선택 필터 4개가 `(:param IS NULL OR ...)` 로 붙는다. 리터럴로만 확인하면
*"실제 쿼리도 탄다"* 를 증명하지 못한다(측정 5 의 F 항목이 같은 우려를 남겼다).

| 쿼리 모양 | type | key | Extra |
| --- | --- | --- | --- |
| 선택 필터 4개 전부 `null` | `ref` | `idx_inquiries_customer_received` | Backward index scan |
| `status` 만 지정 | `ref` | `idx_inquiries_customer_received` | Using where; Backward index scan |

두 번째가 특히 중요하다. `status` 를 주면 기존 인덱스 2개도 후보에 오르는데, 옵티마이저가
**`customer_id` 쪽을 골랐다** — 고객 한 명이 상태 하나보다 훨씬 좁기 때문이다.

## 쓰기 비용 — D-018 이 요구한 나머지 절반, 그런데 **분해되지 않았다**

같은 10,000건을 넣고 잰 시간이다.

| 환경 | 인덱스 3개 | 인덱스 4개 | 판정 |
| --- | --- | --- | --- |
| ② 독립 컨테이너 (3회) | 64.8ms<br><sub>57.9 / 64.8 / 76.2</sub> | 106.6ms<br><sub>104.2 / 106.6 / 118.9</sub> | 구간이 안 겹침 |
| ① 재현 테스트 (9회) | 145ms<br><sub>60 ~ 178</sub> | 105ms<br><sub>72 ~ 233</sub> | **구간이 겹치고 대소가 뒤집힘** |

**①에서는 인덱스가 더 많은 쪽이 오히려 빠르게 나왔다.** 인덱스를 늘렸는데 쓰기가 빨라질 리
없으므로 이건 잡음이다. 재려는 차이가 **InnoDB 의 비동기 플러시가 만드는 편차와 같은
자릿수**라, 9회를 재도 조건 내 편차(60~178 · 72~233)가 조건 간 차이를 삼킨다.

### 그래서 배수를 주장하지 않는다

| 말할 수 있는 것 | 말할 수 없는 것 |
| --- | --- |
| **느는 방향인 것은 확실하다** — 인덱스가 하나 늘면 INSERT 마다 B-tree 를 하나 더 갱신한다 | **몇 배 느는지** — 두 환경이 다른 답을 준다 |
| ②에서는 64.8 → 106.6ms 로 구간이 겹치지 않았다 | ②의 1.6배를 일반화할 수 있는지 |

**그럼에도 도입한다.** 읽기 쪽은 **읽는 행이 100,000 → 19 로** 바뀌는 구조적 변화이고, 이건
어느 환경에서 재도 같다. 쓰기 쪽은 최악으로 잡아 ②의 1.6배라 해도 접수 1건당 0.0065 →
0.0107ms 인데, 접수 경로 p95 는 0.159초(D-069)다. **비교할 자릿수가 아니다.**

> 처음에는 JDBC {@code batchUpdate} 로 쟀는데 왕복 비용이 섞여 더 심하게 뒤집혔다(288 vs 245ms).
> 서버 안에서 `INSERT ... SELECT` 한 문장으로 바꿔 네트워크를 뺐고, 그래도 위 결과다.
> **측정 방식을 고쳐도 안 나오는 것은 안 나온다는 것을 남긴다** — 안 나온 측정을 지우면 다음
> 사람이 같은 시도를 반복한다.

> 이 판단은 **지금 데이터 규모와 쓰기/읽기 비율에서**의 판단이다. `inquiries` 는 INSERT 위주
> 테이블이므로, 접수 처리량이 크게 늘면 **전용 부하 시험으로** 다시 본다 — 이 방식으로는 안 된다.

## 인덱스로 해결되지 않는 것

깊은 오프셋은 **인덱스가 있어도 남는다.** 앞의 행을 읽고 버리는 것은 실행 비용이라 계획을
바꿔도 사라지지 않는다.

| 다건 고객(2,000건 보유) | 소요(중앙값) | 실제 읽은 행 |
| --- | --- | --- |
| 1페이지 (`OFFSET 0`) | 0.0169ms | 20 |
| 100페이지 (`OFFSET 1980`) | **0.788ms** | **2,000** |

약 47배 저하다. 2,000건이라 이 정도이고, 보유 건수가 늘면 그만큼 나빠진다.
**커서 페이징이 필요한 자리이고, D-071 「범위 밖」으로 남긴다.**
