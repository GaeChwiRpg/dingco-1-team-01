# 측정 1 · 8ⓐ-1 · 8ⓐ-2 를 어떻게 재나 (TRI-77)

> **이 프로젝트의 결론이 나오는 자리다.** AI 가 「자신 있다」고 말하면서 틀리는지, 그리고
> 5% 감사가 그중 몇 건을 집어내는지를 숫자로 낸다.
>
> 아직 **재지 않았다.** 이 문서에 숫자는 없다 — 어떻게 재는지만 적는다.
> 결과는 `evidence/measurement-1-8a.md` 에 따로 남긴다.

## 무엇을 재나

| 번호 | 무엇 | 어떻게 계산하나 |
| --- | --- | --- |
| 1 | AI 답이 정답과 얼마나 맞는지 (확신도 구간별) | 맞은 건수 ÷ AI 가 실제로 답한 건수 |
| **8ⓐ-1** | **자동 확정된 건이 실제로 틀린 비율** (구간별) | 틀린 건수 ÷ 자동 확정 건수 |
| **8ⓐ-2** | **5% 감사가 그중 몇 건을 집어냈나** | 감사가 잡은 오분류 ÷ 8ⓐ-1 의 오분류 전체 |

**8ⓐ-1 이 0 이 아니면**, 「확신도가 낮으면 사람에게 넘긴다」만으로는 못 잡는 실패가 실재한다는
증거다. 자동 확정된 건은 아무도 다시 보지 않기 때문이다.

## 파일 두 개로 나눈 이유

| 파일 | 하는 일 |
| --- | --- |
| `run.sh` | 실제 앱에 문의를 넣고 **원자료를 모은다.** AI 를 50번 부른다 |
| `analyze.py` | 원자료를 읽어 **표를 만든다.** AI 를 안 부른다 |

**집계 방식이 틀렸을 때 AI 를 다시 50번 부르지 않기 위해서다.** 원자료(`raw/`)만 있으면
집계는 몇 번이든 다시 돌릴 수 있다.

## 재는 순서

### 0단계 — 재사용을 끄고 앱을 다시 띄운다

```bash
CLASSIFICATION_REUSE_ENABLED=false docker compose up -d --force-recreate app
```

**켜진 채로 재면 안 된다** (D-043 ⓒ). 같은 내용의 문의가 AI 를 건너뛰어, 정답과 대조할
표본이 조용히 줄어든다 — 50건 중 뜻이 같은 묶음이 12건 있다.

⚠️ **실행 중에는 못 바꾼다** (D-028). 반드시 재기동한다. `run.sh` 가 이 조건을 먼저
확인하고, 안 맞으면 **AI 를 부르기 전에 멈춘다.**

### 1단계 — 돌린다

```bash
evidence/measurement-1-8a/run.sh
```

안에서 일어나는 일:

```text
① 조건 확인   재사용 꺼짐 · 모델 · 기준값 · 감사 비율을 raw/conditions.txt 에 기록
② 투입        seed 50건을 POST /api/inquiries (고객 권한)
③ 대기        넣은 건이 전부 RECEIVED 를 벗어날 때까지
④ 수집        GET /api/inquiries/{id} 로 판정 이력 (상담원 권한)
⑤ 감사 확정   감사로 뽑힌 건을 PATCH 로 확정 ← 8ⓐ-2 는 여기서 나온다
```

**⑤가 없으면 8ⓐ-2 가 안 나온다.** 감사로 뽑히기만 해서는 오분류를 못 잡는다 — 사람이
확정해서 `category ≠ final_category` 가 되어야 「감사가 잡아냈다」가 성립한다.

### 2단계 — 집계한다

```bash
python3 evidence/measurement-1-8a/analyze.py
```

## 알아둘 것 세 가지

### 감사로 뽑힌 건을 어떻게 알아내나

검토 큐는 사유(`reason`)를 안 준다 (blind, D-010). 대신 **두 응답을 겹친다.**

```text
검토 큐에 있는 문의   ∩   그 문의의 판정이 자동 확정   =   감사로 뽑힌 건
```

자동 확정된 건이 검토 큐에 있을 이유는 감사밖에 없기 때문이다. 이건 규칙을 뚫는 것이
아니라 **D-010 이 이미 인정한 사실**이다 — "두 값을 주면 뺄셈 한 번으로 감사 표본이 100%
식별된다"고 적혀 있고, 그래서 blind 는 확신도와 기준값을 **함께** 가리도록 설계됐다.

### 감사 확정에 넣는 답은 정답지다

「완벽한 감사자」를 가정한다. 상담원이 실제로 판단하면서 생기는 오차는 반영되지 않는다
(그건 측정 12 소관). **이 가정을 결과에 반드시 적는다.**

### 두 가지로 센 감사 표본 수가 어긋나면 8ⓐ-2 를 쓰지 않는다

`analyze.py` 는 감사 표본 수를 **두 경로로** 센다.

1. 검토 큐 + 판정을 겹쳐서 (위 방법)
2. `GET /api/stats` 의 `audit.autoAccepted.sampledTotal` 측정 전후 차이 (TRI-66)

두 값이 다르면 어느 한쪽이 틀린 것이고, 가리기 전에는 8ⓐ-2 를 쓰지 않는다.
**한쪽만 세면 어긋난 줄도 모른다.**

## 결과를 적을 때

- **측정 조건을 맨 위에 둔다.** 아래에 묻히면 표만 인용될 때 조건이 떨어져 나가고,
  그러면 재사용을 켜고 잰 숫자와 끄고 잰 숫자가 같은 표에 섞인다
- **8ⓐ-2 옆에 한계를 붙인다** — 50건 기준 감사 표본은 기대값이 2건 안팎이라 검출률을
  「비율」로 말할 수 없다 (D-043)
- **기준값을 옮긴 값은 계산값임을 밝힌다.** 실제로 바꿔 돌리면 감사 표본 자체가 달라지고
  (8ⓐ-2 에 직접 영향) 사람의 행동도 달라지는데, 그 둘은 계산으로 안 잡힌다
- **오분류율이 0 으로 나와도 그대로 적는다.** 다만 그때는 감사가 잡아낼 것이 없어 결론을
  못 읽으므로, 기준값을 낮춰 자동 확정 구간을 넓힌 뒤 다시 잰다 (D-043 재평가 조건)
