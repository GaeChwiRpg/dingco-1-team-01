## 1. `PRD.md` §4-0 제목과 본문 불일치

- **AI 출력**: 섹션 제목 `### 4-0. 데이터 모델 (4 테이블)`, 본문에는 `errors` / `error_group` / `classification_result` / `review_queue` / `classification_policy` **5개** 나열
- **왜 틀렸나**: 설계 도중 테이블이 4→5개로 늘었는데 제목만 갱신되지 않음. 긴 문서를 한 번에 생성할 때 앞부분 메타데이터가 뒷부분 내용과 어긋나는 전형적 패턴
- **잡은 방법**: 문서 4개 작성 후 `grep -n "테이블"` 로 개수 표현을 교차 대조. 같은 pass 에서 임계값 `0.7` 잔존, 응답 코드 `201`/`202` 혼용도 함께 적출
- **수정**: 제목 → `(5 테이블)`, `§7` 의 "4개 테이블 + classification_policy" 표현도 "5개 테이블"로 통일
- **교훈**: **개수·버전·코드값처럼 "세는 것"은 생성 직후 반드시 grep 으로 대조한다.** 읽어서는 안 걸린다

## 2. `CLAUDE.md` 작업 경계 규칙의 자기모순

- **AI 출력**: 작업 경계에 *"루트 문서(`PRD.md`, `API-CONTRACT.md`, `DECISIONS.md` 등)는 코드 PR 에 동반 변경만 허용. 단독 리팩터링 금지"*
- **왜 틀렸나**: 규칙의 의도는 "API 계약이 구현과 몰래 어긋나는 것 방지"였는데, 문구가 넓어서 **기획 단계 산출물 작성 자체를 차단**했다. `PRD.md`·`DECISIONS.md` 는 코드보다 먼저 쓰이는 문서다
- **잡은 방법**: 사람이 규칙을 실제로 적용하려는 순간 발견. 첫 문서 커밋을 준비하다가 *"이 커밋이 방금 만든 규칙 위반 아닌가?"* 를 확인
- **수정**: 적용 대상을 `API-CONTRACT.md` 로 좁힘 (D-009)
- **교훈**: **AI 가 만든 규칙은 "이 규칙을 지금 하려는 작업에 적용하면 어떻게 되나"를 한 번 돌려봐야 한다.** 규칙은 문장으로 읽으면 다 그럴듯하다

## 3. `.mcp.json` 의 지원 종료 엔드포인트

- **AI 출력**: `claude mcp add --transport sse atlassian https://mcp.atlassian.com/v1/sse`
- **왜 틀렸나**: 해당 SSE 엔드포인트는 **2026-06-30 부로 지원 종료**됐고 작업 시점(2026-07-30)은 이미 한 달 경과. 유예 기간이라 동작은 했으나 팀 전원이 공유하는 설정 파일에 들어갈 값이 아니었다
- **잡은 방법**: **외부 시스템이 알려줌.** MCP 서버 첫 호출 응답에 deprecation 공지가 포함돼 있었다. AI 내부 지식만으로는 절대 못 잡는 부류
- **수정**: streamable HTTP(`/v1/mcp`)로 교체 후 커밋
- **교훈**: **엔드포인트·API 버전·SDK 버전은 AI 지식을 신뢰하지 않는다.** 실제 호출 응답 / 공식 문서로만 확정. 이 부류는 "그럴듯하고 실제로 동작까지 해서" 가장 늦게 발견된다

## 4. blind 규칙이 다른 필드로 역산 가능

- **AI 출력**: 감사 표본 blind 를 위해 `GET /api/review-queue` 응답에서 `reason` 만 제거. `confidence` 와 `threshold` 는 "검토자가 판단 근거로 쓴다"며 유지
- **왜 틀렸나**: 격리 사유는 3종뿐이고 `AUDIT_SAMPLE` 은 **정의상 `confidence >= threshold`** 다. 두 값을 함께 주면 **뺄셈 한 번으로 감사 표본이 100% 식별**된다. `reason` 을 가린 것이 완전히 무의미했다
- **잡은 방법**: **AI 코드리뷰 1차** (Claude GitHub Actions). 사람도 자체 grep 도 못 잡았다 — 각 필드가 개별적으로는 타당해서 읽어서는 안 걸리고, 필드 간 관계를 추론해야 보인다
- **수정**: `confidence`·`threshold` 응답 필드와 `category` 필터 제거. `suggestedCategory` 는 남기되 앵커링 편향(사람이 AI 제안값에 끌려가는 인지 편향)을 인정해 **오분류율을 하한값으로 해석**한다고 명시 (D-010)
- **재발 방지**: `CLAUDE.md` 에 규칙 신설 — *"새 응답 필드를 추가할 때는 '이 값으로 감사 표본을 역산할 수 있나'를 먼저 확인한다"*
- **교훈**: **정보 은닉은 "가린 필드"가 아니라 "남긴 필드 전체의 조합"으로 검증해야 한다.** AI 는 지시받은 필드만 가리고 나머지 조합을 검토하지 않았다

## 5. 인덱스 표와 실제 필터 컬럼 불일치

- **AI 출력**: `CLAUDE.md` 인덱스 표에 `GET /api/review-queue — status / category / 기간 필터 → (status, created_at)`. `GET /api/error-groups` 는 `category` 필터와 `last_seen_at` 범위를 받는데 인덱스는 `(status, occurrence_count DESC)`
- **왜 틀렸나**: ① `category` 는 `review_queue`·`error_group` 어느 쪽에도 없는 컬럼(`classification_result` 소유)이라 인덱스가 커버 불가 ② `last_seen_at` 범위는 해당 인덱스에 없음. **문서의 인덱스와 API 의 필터 파라미터를 따로 생성해서 서로 대조하지 않았다**
- **잡은 방법**: **AI 코드리뷰 1차**. 두 문서를 나란히 놓고 컬럼 단위로 대조해야 보이는 종류
- **수정**: `error_group` 에 `current_category`/`current_confidence` 역정규화(D-011), `sort` 파라미터 + `(status, last_seen_at)` 인덱스 추가(D-013). **커버 불가한 조합은 숨기지 않고 예상 EXPLAIN 과 함께 명시**
- **교훈**: **API 파라미터 ↔ 인덱스 컬럼 ↔ 테이블 스키마 3자를 컬럼 단위로 대조한다.** 문서가 여러 개면 AI 는 각각 그럴듯하게 쓰고 서로 안 맞춘다

## 6. 측정 장치를 트랜잭션 밖에 둬 측정값을 훼손

- **AI 출력**: *"감사 표본 삽입 실패는 자동 승인 자체를 되돌릴 필요는 없으므로 별도 트랜잭션 + 실패 로깅으로 관측 가능하게 둔다"*
- **왜 틀렸나**: 표본 삽입이 누락되면 실제 감사율이 설정값 5% 미달이 되고, **오분류율 측정의 분모가 조용히 줄어든다.** 측정 무결성이 이 프로젝트의 주제인데 **측정 장치 자체를 best-effort 로 만든** 것. 게다가 "부차적이니 분리한다"는 직관은 외부 의존성에 적용되는 것이고, 여기 두 쓰기는 같은 DB·같은 커넥션이라 분리해서 얻는 격리 이득이 애초에 없었다
- **잡은 방법**: **AI 코드리뷰 2차**. 리뷰가 *"별도 트랜잭션이면 누락 시 감사율이 5%보다 낮아지고 그게 측정 8을 직접 흔든다"* 로 정확히 지적
- **수정**: 분류 트랜잭션(②) 안으로 이동. 추가로 `GET /api/stats` 에 `eligibleTotal`/`actualSampleRate`/`configuredSampleRate` 를 노출해 **감사 장치 자체를 감사** (D-012)
- **재발 방지**: `CLAUDE.md` 규칙 신설 — *"측정 장치를 트랜잭션 밖에 두지 않는다"*
- **교훈**: **일반 원칙("부차적 작업은 분리")을 적용하기 전에 이 맥락에서 그 원칙의 전제가 성립하는지 확인한다.** AI 는 원칙을 맥락 검사 없이 가져다 썼다

## 7. "캐시 hit rate = AI 절감률" 등식

- **AI 출력**: D-004 에 *"hit rate 가 그대로 비용 절감률 지표가 된다"*, *"없으면 AI 비용이 30배 드는 캐시"*. 같은 주장이 `PRD.md`·`CLAUDE.md` 등 **5곳에 전파**됨
- **왜 틀렸나**: 수신 경로는 `캐시 miss → DB SELECT → 그룹 존재 → AI 호출 없음` 경로가 있다. **AI 호출을 막는 것은 "그룹이 이미 존재한다"는 사실이고, 캐시는 그 사실을 DB 에 묻지 않아도 알게 해줄 뿐**이다. TTL 만료·재기동 후엔 miss 지만 AI 는 호출되지 않으므로 `hit rate < AI 절감률` 이 정상. 캐시의 효과를 과대평가했고, 더 나쁘게는 절감률 측정을 캐시 메트릭으로 대체 가능하다고 오독할 여지를 남겼다
- **잡은 방법**: **AI 코드리뷰 3차**. *"그룹은 있는데 캐시만 miss 인 경우엔 AI 호출 없이 miss 가 잡히지 않나요?"* 라는 반례 질문으로 지적
- **수정**: 측정 6 을 `1 - (AI 호출/투입)` 으로만 정의, 캐시 hit rate 를 측정 11 로 분리. 두 값의 격차 자체를 관측 대상으로. 캐시 정당화 근거도 "AI 비용"에서 "수신 경로 DB 부하"로 교체 (D-014)
- **교훈**: **A 가 B 를 유발하는 경로가 하나뿐인지 확인한다.** 여기선 "AI 호출 회피" 경로가 둘(캐시 hit / DB 에 그룹 존재)인데 AI 는 하나만 보고 등식을 세웠다. 그리고 **틀린 주장은 한 곳이 아니라 문서 전체에 전파되므로 정정 시 grep 으로 전수 수색**해야 한다

## 8. 캐시 값 구조 미정의 상태로 병렬 작업 계약 확정

- **AI 출력**: `CLAUDE.md` 에 모듈 간 계약 A(이벤트)·B(큐 삽입)를 정의하며 *"이 두 계약만 고정하면 3명이 병렬로 갈 수 있다"* 고 단언
- **왜 틀렸나**: 수신 경로가 캐시 hit 시 `errors INSERT + occurrence_count++` 를 하려면 **캐시 값에 `groupId` 가 있어야 하는데 값 구조를 어디에도 정의하지 않았다.** P1(읽기)과 P2(쓰기)가 서로 다른 구조를 가정하면 통합 시점에 깨진다 — 계약을 만들면서 정작 계약이 필요한 지점 하나를 빠뜨림
- **잡은 방법**: **AI 코드리뷰 3차**. 시퀀스 다이어그램의 캐시 hit 분기와 캐시 정의를 대조해 지적
- **수정**: 계약 C 신설 — key/value/put 시점/evict 정책 명시 (D-014)
- **교훈**: **"이것만 있으면 충분하다"는 AI 의 완결성 주장은 검증 대상이다.** 흐름도의 각 화살표가 계약으로 덮이는지 하나씩 대조해야 한다

## 9. 트랜잭션 경계를 안 써서 실행 불가한 전략

- **AI 출력**: D-007 락 전략에 *"신규 그룹 동시 생성 → `fingerprint` UNIQUE + **위반 예외 캐치 후 재조회**"*
- **왜 틀렸나**: 전략(제약 조건을 신뢰 근거로 삼는다)은 **맞다.** 그런데 **어느 트랜잭션에서 캐치할지를 쓰지 않았다.** Hibernate 는 제약 위반이 발생하면 세션을 오염된 것으로 간주하고 트랜잭션을 rollback-only 로 마킹하므로, **같은 트랜잭션 안에서 캐치해 재조회하면 `UnexpectedRollbackException` 으로 반드시 실패**한다. 문장만 읽으면 완벽히 타당하고, 실제로 D-007 을 세 번의 리뷰가 "잘한 점"으로 칭찬까지 했다. 그대로 구현했다면 동시성 테스트(측정 7)에서야 발견됐을 것이다
- **잡은 방법**: **AI 코드리뷰 4차**. 문서 간 대조가 아니라 **런타임 동작에 대한 지식**으로 잡아낸 첫 사례 — 앞의 8건과 결이 다르다
- **수정**: 예외를 트랜잭션 밖으로 전파해 롤백을 끝낸 뒤 새 트랜잭션에서 재시도하는 구조를 명시. `@Retryable` 은 `@Transactional` **바깥 빈**에 둔다(내부 호출은 프록시를 안 탐). MySQL `ON DUPLICATE KEY UPDATE` 대안은 Phase 3 로 (D-016)
- **교훈**: **"무엇을 할지"만 쓰고 "어디서 할지"를 안 쓴 설계는 미완성이다.** 트랜잭션·스레드·프로세스 경계가 걸린 전략은 경계를 명시하지 않으면 검증할 수 없는 문장이 된다. 특히 위험한 이유는 **읽어서는 옳아 보이고 리뷰도 통과한다**는 점이다

## 10. 존재하지 않는 복구 경로를 근거로 안심 — 좁은 의미의 hallucination

- **AI 출력**: D-012 에 *"삽입이 실패하면 분류째로 롤백되어 그룹이 `NEW` 로 남고, **다음 재분류에서 다시 표본 추첨 대상이 된다**"*
- **왜 틀렸나**: **"다음 재분류"라는 것이 이 시스템에 존재하지 않는다.** `ErrorGroupCreatedEvent` 는 그룹 생성 시 1회만 발행되고 이미 소비됐으며, 자동 재분류는 Phase 3(항목 G)로 미뤄둔 상태다. 즉 롤백된 그룹은 분류도 안 되고 큐에도 없이 **`NEW` 로 영구 방치**된다. 앞의 사례들이 "있는 것을 잘못 연결한" 오류라면 이건 **없는 것을 있다고 서술한** 오류다
- **더 나쁜 점**: 이 문장이 **실제 구멍을 덮었다.** "복구된다"고 적혀 있으니 아무도 그 경로를 확인하지 않는다. 게다가 그 구멍이 만들어내는 것이 정확히 **"조용히 유실된 에러"** — 이 시스템의 존재 이유인 실패 유형이다. AI 가 자기가 만든 시스템의 주제를 스스로 위반하는 코드를 정당화한 셈
- **잡은 방법**: **AI 코드리뷰 4차**. *"ErrorGroupCreatedEvent 는 이미 소비되고 자동 재분류는 Phase 3 입니다. 그러면 NEW 로 영구 방치되지 않나요?"* 로 지적
- **수정**: Phase 2 는 고치지 않고 **관찰 가능하게** 만든다 — `stats.classification.stuckNew` + Actuator gauge `triage.groups.stuck_new`. 0 이 아니면 파이프라인이 조용히 실패 중이라는 신호. 재분류 스윕은 Phase 3 항목 G 와 같은 문제이므로 함께 처리 (D-017)
- **교훈**: **AI 가 "나중에 처리된다 / 자동으로 복구된다"고 쓰면 그 주체를 이름으로 지목해 실재를 확인한다.** 어떤 컴포넌트가, 어떤 트리거로, 어느 Phase 에 그것을 하는가. 이름을 못 대면 그 메커니즘은 없는 것이다. **미래 시제 서술이 가장 위험한 hallucination 형태**다 — 지금 확인할 수 없기 때문이다

## 11. 형식 규칙을 우회하려다 문서를 모순 상태로 만듦

- **AI 출력**: D-002 의 팀 배정이 확정됐을 때, `DECISIONS.md` 형식 규칙(*"본문 불변, `상태` 필드만 갱신 가능"*)을 지키려고 확정 내역을 **`상태` 필드 괄호 안에** 넣었다 — `**상태**: **채택** (2026-07-30 확정 — 기획 김준현 / 코딩 팀 전원 / ...)`
- **왜 틀렸나**: 규칙의 **문자는 지켰지만 목적은 어겼다.** 본문 `결정` 필드는 여전히 *"**미확정.** 팀 미팅에서 확정한다"* 로 남아, **같은 항목 안에서 상태와 본문이 서로 모순**하게 됐다. 형식 규칙의 목적은 "결정 이력을 신뢰할 수 있게 보존"하는 것인데, 결과물은 **읽는 사람이 어느 쪽을 믿어야 할지 모르는 문서**였다. 후속 항목을 만드는 것이 정답이었고 그 장치는 이미 규칙에 있었는데도 쓰지 않았다
- **잡은 방법**: **AI 코드리뷰 5차**. *"상태는 채택인데 본문 결정이 '미확정'으로 남아 서로 충돌합니다"*
- **수정**: D-020 을 후속 항목으로 만들어 확정 내역을 기록하고, D-002 의 `상태` 는 `채택 — 확정 내역은 D-020 참조` 한 줄로 축소 (D-020)
- **교훈**: **제약을 만족시키는 가장 짧은 경로가 제약의 목적을 배신할 수 있다.** `상태` 필드 갱신 허용은 "보류 → 채택" 같은 **한 단어 전환**을 위한 것이지 내용을 담으라는 뜻이 아니었다. 규칙을 우회하는 방법을 찾았을 때는 **"이 규칙이 왜 있었나"를 먼저 되묻는다**

## 12. 원인이 다른 두 실패를 한 코드로 뭉뚱그려 검증 불가능하게 만듦

- **AI 출력**: `API-CONTRACT.md` 에 *"409 | 낙관적 락 충돌 (이미 확정된 큐 항목 재확정)"*
- **왜 틀렸나**: 한 줄 안에 **검출 시점이 다른 두 시나리오**가 섞였다. "이미 확정된 항목"은 조회 시점 **상태 검사**로 걸리고, "낙관적 락 충돌"은 커밋 시점 **`@Version`** 으로 걸린다. 뭉뚱그린 대가는 문서 품질이 아니라 **검증 가능성**이다 — 동시성 테스트에서 409 가 나와도 그게 *"시간 차를 두고 온 두 번째 요청"*(경합 없음)인지 *"진짜 동시 경합"*인지 구분할 수 없어, **락이 실제로 동작했는지 증명할 방법이 사라진다.** "409 나왔으니 통과"로 잘못 결론 내기 딱 좋다
- **잡은 방법**: **AI 코드리뷰 5차**. *"이미 RESOLVED 는 상태 검사만으로도 걸립니다. `@Version` 충돌과 상태 위반을 구분해 각각 어떤 시나리오에서 발생하는지 명시하는 게 좋겠습니다"*
- **수정**: `ALREADY_RESOLVED` / `CONCURRENT_UPDATE` 2종 `code` 로 분리. 두 장치가 **서로 다른 창을 막는다**는 근거도 명시 — 상태 검사만으로는 둘 다 `PENDING` 을 읽은 경합(check-then-act)을 못 막고, `@Version` 만으로는 시간 차 요청을 경합으로 오보한다. 측정 7 에 **"`CONCURRENT_UPDATE` 가 0 이면 경합 창이 재현되지 않은 것이므로 테스트가 무의미"** 라는 판정 기준을 추가 (D-021)
- **교훈**: **같은 결과 코드를 쓰더라도 원인이 다르면 분리한다 — 판단 기준은 "이걸 뭉치면 무엇을 측정할 수 없게 되는가"다.** 응답 코드는 클라이언트를 위한 것이기도 하지만 **자기 시스템을 검증하기 위한 계측 지점**이기도 하다

## 13. Docker Desktop 다운로드 링크의 버전 라벨을 잘못 전달

- **AI 출력**: Testcontainers/Docker API 버전 호환성 조사 중 `docs.docker.com/desktop/release-notes/` 페이지를 웹 요약 도구로 조회해 "Docker Desktop 4.47.0 (build 222858)" 다운로드 링크를 사용자에게 제시. `curl -I` 로 URL 이 실제로 존재하고 200 을 반환하는 것까지 확인한 뒤 전달함

  ```text
  Server: Docker Desktop 4.44.2 (202017)
   Engine:
    Version:          28.3.2
    API version:      1.51 (minimum version 1.24)
  ```

## 15. 계약의 404 가 도메인 fallback 규칙과 모순

- **AI 출력**: `API-CONTRACT.md` §7 `PATCH /api/policies/{category}` 의 **오류**: *"400 (`threshold` 가 0.0~1.0 밖), 403, **404 (미정의 카테고리)**"*
- **왜 틀렸나**: 같은 저장소의 `CLAUDE.md` 도메인 모델과 `V1__init_schema.sql` 주석은 **"미등록 카테고리는 기본값 0.9 fallback"** 이라고 말한다. 즉 `classification_policy` 에 **행이 없는 상태를 정상으로 인정**하는 설계다. 그런데 404 는 바로 그 정상 상태를 오류로 취급한다 — 결과는 **순환**이다. 임계값을 설정하려면 행이 있어야 하고, 행을 만들려면 임계값을 설정해야 한다. 그 카테고리는 영원히 0.9 에 고정된다.
  두 문장이 **각각은 타당한데 조합하면 목적을 달성 못 하는** 전형적 설계 결함이고, 사례 5·6·8 과 같은 부류다. 특히 지금 이 결함이 겉으로 안 드러나는 이유가 **"설계가 맞아서"가 아니라 "V1 seed 가 10종을 다 넣어줘서"** 라는 점이 나쁘다 — D-001 재평가 조항(카테고리 10종 → 5종 축소)이나 enum 확장이 발동하는 순간 바로 터진다
- **잡은 방법**: **문서 간 교차 점검** — 계약의 오류 코드 표를 헌법의 도메인 규칙과 나란히 놓고 읽음. 사례 14 와 달리 기계적으로는 안 잡힌다. *"이 오류를 반환하면 사용자는 다음에 무엇을 할 수 있나"* 를 한 번 물어야 보인다
- **수정**: upsert 로 변경하고 이 endpoint 에서 404 제거. enum 에 **없는** 값은 400, enum 에 **있고 행만 없는** 것은 생성. `previousThreshold` 에는 그때 실제로 적용되던 값(= `defaultThreshold`)을 담아 행 유무와 무관하게 같은 방식으로 읽히게 함 (D-029)
- **교훈**: **오류 코드는 "무엇이 잘못됐나"가 아니라 "클라이언트가 다음에 무엇을 할 수 있나"로 검증한다.** 404 를 받은 관리자에게 남은 행동이 없다면 그 404 는 틀린 것이다. 사례 12(409 를 뭉뚱그림)와 짝을 이루는 교훈이다 — 그쪽은 *같은 코드에 다른 원인을 담아* 검증 가능성을 잃었고, 이쪽은 *오류가 아닌 것에 오류 코드를 붙여* 기능을 잃었다

## 16. 잘린 diff 를 보고 "없다"고 단정

- **AI 출력**: PR #11 리뷰에서 *"`constitution-guard.py` 가 `V[12]__*.sql` 을 막는데 **이 PR diff 에 V2 마이그레이션이 안 보입니다**"*, *"**코드 0줄** 대비 문서 변경이 큽니다. 다음 PR 에서 엔티티 3종 + V2 를 함께 올려 `ddl-auto: validate` 로 검증하는 걸 우선순위 1로"*
- **왜 틀렸나**: 둘 다 **이미 이 PR 에 있었다.** `V2__domain_switch.sql` 이 추가됐고 `src/` 27파일이 바뀌었으며, 리뷰가 "다음 PR 에서 하라"고 권한 `ddl-auto: validate` 검증은 **같은 커밋에서 이미 통과**한 상태였다(`./gradlew test` exit 0).
  원인은 hallucination 이 아니라 **입력 절단**이다. `.github/workflows/ai-review.yml` 이 `head -c 200000 /tmp/pr.diff` 로 자르는데, 이 PR 은 41파일 / ±3,300줄이라 한도를 넘었다. 그리고 `git diff` 는 경로 알파벳 순이라 **`src/` 가 뒤쪽에 몰려 통째로 잘려 나갔다.**
- **이 오류가 특히 위험한 이유**: 리뷰는 자기가 **못 본 것**을 **없는 것**으로 바꿔 말했고, 그 위에 *"다음 PR 에서 하라"* 는 **행동 지시**까지 얹었다. 그대로 따랐다면 이미 끝난 일을 다시 하거나, 더 나쁘게는 "아직 검증 안 됐다"고 믿고 머지를 미뤘을 것이다. **틀린 사실보다 그 사실에 근거한 지시가 더 멀리 간다.**
- **잡은 방법**: CI 로그에서 워크플로가 실제로 무엇을 모델에 넣었는지 확인 + PR 의 실제 파일 목록 대조. *"리뷰가 이렇게 말했는데 내 기억과 다르다"* 를 그냥 넘기지 않은 것이 시작이었다
- **수정**: 워크플로의 절단 자체는 남긴다(무한정 넣을 수 없다). 대신 **한계를 명시적으로 다룬다**:
  - PR 이 200KB 를 넘으면 리뷰는 **부분만 본 것**이다 → 리뷰 코멘트를 근거로 쓰기 전에 범위를 확인한다
  - 큰 변경은 **문서 PR / 코드 PR 로 나누는 것이 리뷰 품질 면에서 유리**하다. 다만 이번처럼 나누면 트렁크가 모순 상태가 되는 경우는 예외 — **리뷰 품질과 트렁크 정합성이 상충하면 정합성이 우선**이다
- **교훈**: **"AI 가 X 를 언급하지 않았다"와 "X 가 없다"는 다르다.** 사례 13(URL 이 응답한다 ≠ URL 이 맞다)과 같은 계열이되 방향이 반대다 — 13 은 *본 것*을 과신했고, 16 은 *못 본 것*을 부정으로 단정했다. **검증 도구의 입력 범위를 모르면 그 도구의 침묵을 해석할 수 없다.**

## 17. 검증하라는 지적은 맞는데 검증에 쓸 값이 틀렸다

- **배경**: TRI-49 에서 `confidence` 를 소수점 3자리로 맞추며 반올림 방식을 `HALF_UP` 으로 골랐다. 리뷰가 *"어떤 방식을 쓰는지 테스트로 고정하라"* 고 지적했다 — **맞는 지적이다.** 안 고정하면 나중에 누가 방식을 바꿔도 테스트가 통과한다.
- **AI 출력**: 그러면서 **`0.9315` 를 테스트 값으로 제안**했다.
- **왜 틀렸나**: 그 값으로는 방식이 갈리지 않는다.

  | 값 | `HALF_UP` | `HALF_EVEN` | 버림 | 갈리나 |
  | --- | --- | --- | --- | --- |
  | `0.9315` | 0.932 | **0.932** | 0.931 | ❌ 앞 둘이 같다 |
  | `0.9325` | **0.933** | 0.932 | 0.932 | ✅ 셋이 다 다르다 |

  `HALF_EVEN` 은 **버림 자리 앞이 짝수일 때만** 내린다. `0.9315` 는 앞자리가 `1`(홀수)이라 올려서 `HALF_UP` 과 결과가 같아진다. **앞자리가 짝수인 값(`0.9325`)을 골라야** 두 방식이 갈린다.
- **이 오류가 위험한 이유**: 사례 16 과 성격이 정반대다. 16 은 **못 본 것을 없다고** 했고, 이번엔 **다 보고도 계산이 틀렸다.** 그리고 지적의 방향이 맞았기 때문에 더 받아들이기 쉽다 — **그대로 넣었으면 테스트는 초록불인데 반올림 방식은 여전히 아무도 안 지키는 상태**가 된다. 나중에 누가 `HALF_EVEN` 으로 바꿔도 이 테스트는 통과한다.
- **잡은 방법**: 제안받은 값을 **세 방식으로 직접 계산해 대조**했다. *"이 값이 정말 방식을 갈라주나"* 를 한 번 물은 것이 전부다
- **수정**: `0.9325` 로 교체하고, **왜 이 값이어야 하는지를 테스트 주석에 남겼다** — 값만 바꾸면 다음 사람이 "0.93 근처 아무 값"으로 되돌린다 (커밋 `46b1c17`)
- **교훈**: **검증 도구가 "무엇을 검증하라"고 할 때, 방향이 맞다고 값까지 맞는 것은 아니다.** 테스트는 통과 여부만 보여주고 **자기가 무엇을 못 잡는지는 안 보여주므로**, 이 부류는 사후에 드러나지 않는다. 사례 12(409 를 뭉뚱그려 검증 불가)와 같은 계열이되 이쪽이 더 조용하다 — 12 는 *검증할 수 없음*이 명세에서 보였고, 17 은 **검증되는 것처럼 보인다.**

## 18. "PR 이 머지됐다" 를 "티켓이 끝났다" 로 단정한 판정 규칙

- **배경**: `/ticket` 커맨드(`.claude/commands/ticket.md`)를 만들면서, GitHub 에서 일어난 일을 Jira 에 반영하는 **모드 D** 의 판정 규칙을 표로 적었다. 이 저장소는 GitHub Issue 를 안 써서 **PR 제목의 `TRI-번호` 가 티켓과 코드를 잇는 유일한 선**이다.
- **AI 출력**: PR 상태 하나만 보고 Jira 상태를 정하는 판정표 — `MERGED → 완료` · `OPEN → 검토 중`.
- **왜 틀렸나**: **PR 과 티켓의 관계가 1:1 이 아니라 양방향 다대다**인데 규칙이 1:1 을 전제했다. 두 갈래로 깨진다.

  | 갈래 | 실제로 겪은 것 | 규칙대로 하면 |
  | --- | --- | --- |
  | **한 티켓이 여러 PR 에** | TRI-47 이 **#21**(클래스 개명 문서, 머지됨)과 **#30**(실제 구현, 열림) 양쪽에 있다 | 머지된 #21 만 보고 **완료로 옮긴다** — 아직 리뷰 중인 일이 끝난 게 된다 |
  | **한 PR 이 여러 티켓을** | **#18** 이 TRI-37·39·38 을 담았는데 37·39 만 `완료`, 38 만 `진행 중` | "덜 옮긴 것"으로 읽고 **38 도 완료로 옮긴다** — 담당자가 일부러 남긴 신호를 지운다 |

- **이 오류가 위험한 이유**: **틀리는 방향이 한쪽으로 쏠린다 — 항상 「끝났다」 쪽으로 틀린다.** 그리고 완료로 옮겨진 티켓은 **지연 목록에서도 현황판에서도 사라지므로**, 틀렸다는 사실 자체가 관측되지 않는다. 사례 6(측정 장치를 트랜잭션 밖에 둠)과 같은 모양이다 — **분모가 조용히 줄어든다.**
- **잡은 방법**: **규칙을 실제로 돌려보다가.** 옮길 후보 목록을 뽑아 놓고 *"이 티켓을 담은 PR 이 정말 이것 하나뿐인가"* 를 한 번 더 물은 것이 전부다. 사례 2(작업 경계 규칙의 자기모순)와 같은 계열 — **규칙은 읽으면 다 그럴듯하고, 적용해봐야 드러난다.**
- **수정**: 모드 D 에 예외 2개를 명문화했다. ① **같은 티켓을 담은 PR 이 여럿이면 가장 나중 것이 이긴다** ② **한 PR 의 형제 중 혼자만 안 옮겨져 있으면 담당자가 일부러 남긴 것으로 본다 — 특히 남의 구역이면 대신 옮기지 않는다.** 실제 실행에서는 3건(TRI-51·52·82)만 옮기고 2건(TRI-47·38)은 손대지 않았다.
- **왜 이 규칙이 이번엔 사고로 안 이어졌나**: 커맨드가 **"보여주고 사람이 확인한 뒤에만 전환한다"** 를 강제하고 있었다. 규칙이 틀렸어도 **자동으로 실행되지 않는 구조**라 사람이 볼 기회가 있었다. 규칙의 정확성과 별개로 **확인 단계 자체가 방어선이었다.**
- **교훈**: **한 사건과 한 상태를 1:1 로 잇는 판정 규칙을 쓸 때는, 그 관계가 실제로 1:N·N:1 인지 먼저 확인한다.** 사례 12(원인이 다른 둘을 한 코드로 뭉뚱그림)와 방향이 반대다 — 12 는 **서로 다른 것을 하나로 묶었고**, 18 은 **여럿인 것을 하나로 셌다.** 둘 다 결과는 같다: **집계가 조용히 틀린다.**

## 19. 리뷰 봇 2종이 존재하지 않는 마스킹 토큰을 지어냄

- **배경**: `MaskingConsistencyIT`(TRI-38) PR #36 리뷰에서, Claude 리뷰와 데브캠프 봇이 **각각 독립적으로** 같은 제안을 냈다.
- **AI 출력**: *"원문에 이메일이 있는데 단언 (2)의 `contains` 목록에 `[이메일]` 토큰이 빠졌다. `assertThat(aiPath).contains("[이메일]")` 를 추가하라."*
- **왜 틀렸나**: `ContentMasker` 는 이메일을 `[이메일]` 이 아니라 **`[연락처]`**(전화와 같은 토큰)로 가린다 — `[이메일]` 토큰은 구현에 **존재하지 않는다.** 제안대로 넣으면 그 문자열이 응답에 없어 **테스트가 실패하고 빌드가 깨진다.**
  - 단 **지적의 방향은 절반 맞다** — 이메일·전화가 둘 다 `[연락처]` 라, 전화의 `[연락처]` 가 이메일 검사를 덮어 이 IT 안에서는 이메일 마스킹이 **독립적으로** 검증되지 않는다. 그러나 그 커버는 `ContentMaskerTest`(단위, 이메일 케이스 독립)가 이미 한다. **방향은 맞고 해법이 허구다** (사례 17 과 같은 함정).
- **이 오류가 특별한 이유**: **독립적인 두 봇이 같은 허구를 만들었다.** 관찰 2 는 *같은 AI가 만든 설계를 같은 AI가 검증*할 때 맹점이 겹친다고 했는데, 이번엔 **다른 봇들이** 같은 그럴듯한-오답에 수렴했다 — 같은 표면 정보(원문에 이메일이 있다)에서 같은 추론이 나오기 때문이다. **"여러 리뷰어가 동의함"은 정답의 근거가 못 된다.**
- **잡은 방법**: 봇이 참조하라는 코드 요소(`[이메일]` 토큰)가 **실제 구현에 있는지 소스(`ContentMasker.RULES`)를 대조.** 사례 13(존재 확인)의 반대 방향이다 — 13 은 있는 것을 "맞다"고 과신했고, 19 는 **없는 것을 "있다"고 참조**했다.
- **수정**: 미반영, 그대로 머지. 근거는 사용자 보고와 이 로그에 남겼다.
- **교훈**: **리뷰가 코드베이스의 구체적 사실(토큰·심볼·시그니처)을 인용하면 그 인용을 소스로 한 번 확인한다.** 지적의 방향이 맞을수록 인용된 값은 안 따져보게 된다(사례 17). 그리고 **봇 수는 검증이 아니다.**

## 20. 각각 통과한 두 PR 이 합쳐지자 develop 이 컴파일되지 않았다

- **배경**: PR #44(측정 4)를 올리려는데 push 전 검증 훅이 막았다. 내 변경 때문인 줄 알았으나 아니었다 — **`origin/develop` 을 그대로 꺼내 `compileTestJava` 를 돌려도 실패했다.**
- **무엇이 틀렸나**: 두 PR 이 **각각은 통과했는데 합쳐지자 깨졌다.**

  | PR | 무엇을 했나 |
  | --- | --- |
  | **#35** (TRI-54, 김준현) | 리스너 생성자를 3개 인자로 바꿈 — `(ContentMasker, RetryingAiClassifier, ClassificationService)` |
  | **#36** (TRI-38, 이용택) | 옛 4개 인자로 부르는 테스트를 추가 — `(..., AiClassificationService, AiResponseParser, ...)` |

  각자 브랜치에서는 둘 다 컴파일됐다. **머지 가능 여부를 판정하는 GitHub 의 검사는 텍스트 충돌만 본다** — 그래서 충돌 없이 머지됐고, 합쳐진 결과가 깨졌다.

  ⚠️ **"합친 결과를 아무도 안 봤다"는 아니다.** PR CI(`e2e`)는 `pull_request` 트리거라 **머지 결과(merge ref)에서 돈다.** 즉 합친 상태를 보긴 봤다. 그런데도 못 잡은 이유는 **그 CI 가 `bootJar -x test` 를 돌려 테스트 코드를 컴파일하지 않기 때문**이다 (아래 참조). **본 지점이 아니라 본 범위가 문제였다.**
- **이 오류가 위험한 이유**: **영향이 팀 전체이고, 아무도 자기 잘못이라고 생각하지 않는다.** 이 저장소는 push 전에 전체 테스트를 도는 훅이 있어서 **세 사람 모두 develop 에 push 하지 못하는 상태**였다. 게다가 두 PR 모두 리뷰·CI 를 통과했으므로 커밋 이력만 봐서는 어디서 깨졌는지 안 보인다.
- **잡은 방법**: **push 가 막혀서.** 훅이 없었다면 다음 사람이 자기 코드를 의심하며 한참 헤맸을 것이다 — 검증 지점이 앞당겨져 있어 원인과 증상이 가까웠다.
- **수정**: PR #43. 파손 원인이 내 PR #35 의 생성자 변경이라 **P1 파일이지만 내가 고쳤다.** 리스너가 이제 AI 를 직접 부르지 않으므로 캡처 지점을 `RetryingAiClassifier` 로 옮겼고, **테스트가 검증하는 내용(리스너가 가린 문자열을 넘기는가)은 한 줄도 바꾸지 않았다.**
- **⚠️ 첫 진단이 틀렸다 — 고쳐 적는다.** 처음에는 *"머지 직후 develop CI 를 한 번 더 돌려야 한다"* 고 적었다. **그 장치는 이미 있었다.** `e2e.yml` 에 `push: branches: [develop]` 트리거가 있고, 주석에 이렇게까지 적혀 있다.

  > "develop 머지 후 한 번 더 도는 것은 의도한 것이다. … **세 패키지가 병렬로 머지하는 동안 서로의 변경이 겹쳐 깨지는 것은 여기서만 잡힌다.**"

  실행 이력을 보니 문제의 머지(`2b8ba85`) 직후 e2e 가 실제로 **돌았고 `success` 였다.** 그때 develop 은 이미 컴파일이 깨져 있었는데도.

- **진짜 원인 — CI 는 도는데 「테스트 코드」를 아무도 컴파일하지 않는다.** e2e 는 `docker compose up --build` 로 앱을 띄우고 health 를 친다. 그 빌드는 `Dockerfile` 의 이 줄이다.

  ```dockerfile
  RUN ./gradlew --no-daemon clean bootJar -x test
  ```

  `bootJar -x test` 는 **`src/main` 만 컴파일한다.** 깨진 곳은 `src/test` 였으므로 **e2e 입장에서는 아무 문제가 없었다.** 앱은 정상적으로 떴고 health 도 200 이었다 — 그게 사실이기도 하다.

  즉 이 저장소에서 **테스트 코드를 컴파일하는 곳은 개발자 로컬의 push 훅뿐**이었다. CI 는 한 번도 본 적이 없다.

- **교훈**: **「CI 가 돈다」와 「CI 가 그것을 본다」는 다른 말이다.** 초록불의 의미는 그 워크플로가 **무엇을 입력으로 받았는지**까지 봐야 정해진다. 여기서는 `-x test` 한 조각이 검사 범위를 갈랐다.
  - 막으려면 **테스트 컴파일(또는 전체 테스트)을 CI 단계에 명시적으로 넣어야 한다.** develop CI 를 더 돌리는 것으로는 안 된다 — 이미 돌고 있고 앞으로도 계속 초록불일 것이다.
  - **이건 AI 가 틀린 사례가 아니라 「검사가 봐야 할 대상을 안 보는」 사례다.** 그래도 여기 남기는 이유는, 이 로그가 쌓아온 질문이 *"무엇을 못 잡았나"* 이고 그 답이 이번엔 **사람도 AI 도 아닌 파이프라인**이었기 때문이다.
  - 사례 16(잘린 diff 를 보고 "없다")과 **같은 계열이다** — **도구가 무엇을 입력받았는지 알아야 그 도구의 침묵을 해석할 수 있다.** 16 은 리뷰 봇이 diff 를 다 못 봤고, 20 은 CI 가 **테스트 소스를 아예 안 받았다.**
  - **첫 진단이 틀렸던 것 자체가 이 사례의 일부다.** "장치가 없다"고 단정하기 전에 **있는 장치가 무엇을 보고 있는지**를 먼저 확인해야 했다. 워크플로 파일을 열어보는 데 1분이면 됐다.

> **후속(이 PR 범위 밖)**: CI 에 `./gradlew compileTestJava` 또는 `test` 단계를 넣는 건은 `.github/` 변경이라 별도 PR 이고, 실행 시간·비용 트레이드오프가 있어 팀 합의가 필요하다.

## 21. 끈 상태에서는 불릴 수 없는 메서드를 "불린다"고 서술

- **배경**: PR #56 에서 **D-062**(재사용을 끄는 스위치)를 신설했다. AI 리뷰가 *"D-062 와 D-063 을 연결하라"* 며 ⓓ 항목에 한 문장을 덧붙이라고 제안했다.
- **AI 출력**: *"`reuse.enabled=false` 일 때도 `persistReuse`(D-063)는 호출된다 — 캐시에 넣는 동작은 계속되기 때문"*
- **무엇이 틀렸나**: **끄면 그 메서드에 도달할 길이 없다.**

  ```text
  reuse.enabled = false
    └ 리스너가 재사용 조회를 건너뛴다
        └ 재사용 판정(hit)이 아예 안 생긴다
            └ persistReuse 는 호출되지 않는다   ← 제안이 "호출된다"고 한 자리
  ```

  D-062 ⓓ 의 *"꺼도 넣기는 계속한다"* 는 **AI 경로의 `putIfNotHuman`** 을 말한 것인데, 리뷰가 이를 **재사용 경로의 저장**으로 읽었다. 두 입구(D-063) 중 **AI 쪽만 열린 상태**라는 것이 정확한 서술이다.
- **이 오류가 위험한 이유**: 결정 문서에 들어가면 **다음 사람이 코드를 안 열어보고 그 문장을 믿는다.** 특히 이 문장은 「측정할 때 무엇이 도는가」를 설명하는 자리라, 틀린 채로 남으면 **측정 1·8ⓐ 를 어떤 조건에서 잰 것인지 잘못 기록하게 된다.**
- **잡은 방법**: **제안 문장을 흐름에 넣어 따라가 봤다.** 「조회를 끈다」에서 출발해 `persistReuse` 까지 가는 경로를 찾으려 했고, 없었다. 소스에 그 심볼이 **있는지**(사례 19 의 방법)가 아니라 **거기까지 갈 수 있는지**를 물어야 보이는 종류다.
- **수정**: **미반영.** 대신 **「두 결정을 연결하라」는 방향은 맞아서** ⓓ 에 정확한 문장으로 넣었다 — *"꺼진 동안 캐시를 채우는 것은 AI 경로다. 재사용 저장(`persistReuse`)은 호출되지 않는다 — 들어오는 길 둘 중 AI 쪽만 열린 상태다."*
- **교훈**: **방향이 맞으면 내용을 안 따져보게 된다** — 사례 17(검증값 오산)과 같은 계열이다. 17 은 *"검증하라"* 가 맞고 값이 틀렸고, 21 은 *"연결하라"* 가 맞고 **연결의 내용**이 틀렸다.
  - **제안을 그대로 받았다면 손해가 컸다.** 문서에 없는 동작을 적는 것이라 코드로는 절대 드러나지 않고, 나중에 "왜 이렇게 적혀 있지"를 되짚을 근거도 남지 않는다.

## 22. 문서가 "아직 모른다"로 비워둔 자리에 숫자를 채우라는 요구

- **배경**: 사례 21 과 **같은 리뷰**에서 나온 두 번째 제안이다. D-062 배경에 *"재사용을 켜 두면 정답과 대조할 표본이 줄어든다"* 고 적고, **줄어드는 건수는 일부러 비워 뒀다.**
- **AI 출력**: *"「표본이 50 → 38 건으로 줄어든다」처럼 구체적인 숫자를 넣어 영향을 분명히 하라"*
- **무엇이 틀렸나**: **그 값은 재본 적이 없다.** 근거로 삼을 만한 것은 시드의 `dup_group` 12건뿐인데, 그것은 **「사람이 보기에 뜻이 같다」** 는 표시다. 실제로 AI 호출이 줄려면 **정규화 키까지 같아야** 하고, **D-061 이 밝혔듯 띄어쓰기 하나로 키가 갈린다.** 12건이 그대로 12건의 절감이 되지 않는다.
  - 실제 수치는 **측정 6(TRI-71)에서 나온다.** 8/11 의 1000건 파생에서도 *"사람 기준 중복 956 / 시스템 절감 상한 550"* 처럼 **두 숫자가 갈렸다** — 사람 기준과 키 기준이 다르다는 것이 이미 데이터로 나와 있다.
- **이 오류가 위험한 이유**: **이 프로젝트의 결론이 측정값이다.** 추정치가 문서에 한 번 들어가면 나중에 나온 실측과 나란히 놓였을 때 어느 쪽이 잰 값인지 구분되지 않고, **인용될 때는 둘 다 그냥 「문서에 적힌 수치」가 된다.** 헌법이 *"재보지 않은 성능 수치를 만들지 않는다"* 를 문서 작성 규칙 5번으로 못박은 이유다.
- **잡은 방법**: **헌법 규칙과 대조.** "이 값의 출처가 무엇인가"를 물었더니 **없었다** — 계산도 실측도 아니고, 옆에 있는 다른 숫자(12건)에서 그럴듯하게 파생된 값이었다.
- **수정**: **미반영.** 대신 **비어 있는 이유**를 적었다 — *"줄어드는 표본이 몇 건인지는 아직 모른다. `dup_group` 은 사람 기준이고 실제 절감은 키가 같아야 생긴다. 그 수치는 측정 6 에서 실측으로 나온다."*
- **교훈**: **새 부류 「추정치 요구」다.** AI 리뷰는 **빈칸을 결함으로 읽는다** — 문서가 정직하게 비워둔 자리와 빠뜨린 자리를 구별하지 못한다.
  - **판별 질문**: *"이 값을 넣으라는 요구에, 값의 출처가 함께 왔나?"* 안 왔으면 그 값은 **문서를 채우기 위해 만들어진 값**이다.
  - **빈칸을 채우는 대신 빈칸인 이유를 적는다.** 그러면 다음 사람이 "왜 없지"를 묻지 않게 되고, 실측이 나왔을 때 **어디를 채워야 하는지도 분명해진다.**

## 23. 헬퍼 이름만 보고 "그 호출이 없다"고 단정

- **배경**: PR #58(TRI-90, 재사용 스위치)의 통합 테스트다. `stillWritesToCacheWhileDisabled` 는 **「재사용을 꺼도 캐시 넣기는 계속된다」**를 확인한다 — 넣기까지 꺼지면 다시 켠 직후의 hit rate 가 실제보다 낮게 나오기 때문이다 (D-062 ⓓ).
- **AI 출력**: *"이 테스트가 `givenAutoAcceptedAnswerFor(key)` 만 호출하고 정작 `classificationService.verifyAndPersist()` 를 부르지 않아, 캐시 넣기가 실제로 발생하지 않습니다. **이전 테스트의 부수 효과에 의존할 위험이 있습니다.**"*
- **무엇이 틀렸나**: **그 헬퍼 안에서 부르고 있었다.**

  ```java
  private void givenAutoAcceptedAnswerFor(String normalizedKey) {
      Inquiry earlier = givenReceivedInquiry(normalizedKey);
      classificationService.verifyAndPersist(...);   // ← "없다"고 한 호출
  }
  ```

  「부수 효과 의존」도 아니다 — 키가 매번 새 `UUID` 이고 `@MockBean` 은 테스트마다 초기화된다.
- **이 오류가 위험한 이유**: **제안이 통과했어도 테스트는 초록불이다.** 제안대로 헬퍼를 풀어 인라인하면 같은 호출이 한 번 더 생기는 게 아니라 **같은 코드가 두 벌**이 된다. 즉 이 지적은 **틀렸는데 따라도 안 깨져서**, 근거가 틀렸다는 사실이 영영 안 드러난다.
- **잡은 방법**: **단언이 통과한다는 사실 자체를 반증으로 썼다.** 그 테스트는 `verify(cache).putIfNotHuman(...)` 으로 끝나는데, 넣기가 안 일어났다면 **그 단언이 실패했어야 한다.** 초록불이라는 것이 곧 호출이 있었다는 증거다 — 코드를 열기 전에 이미 갈렸다.
  - 사례 16(잘린 diff 를 보고 "없다"고 단정)과 **같은 부류**다. 16 은 도구가 잘라서 못 봤고, 23 은 **이름을 보고 안 열어서** 못 봤다. 둘 다 **못 본 것과 없는 것을 구분하지 않았다.**
- **수정**: **미반영.** 다만 **이름이 오해를 부른 것은 맞다** — `given...` 은 준비를 뜻하는데 이 테스트에서는 **그 한 줄이 재는 대상 그 자체**다. 헬퍼 javadoc 에 **지나는 길 세 단계**(`verifyAndPersist` → 이벤트 → 리스너의 `putIfNotHuman`)를 그려 넣었다.
- **교훈**: **지적이 틀려도 그 지적을 부른 원인은 맞을 수 있다.** 여기서 고칠 것은 테스트가 아니라 **왜 그렇게 읽혔는지**였다.
  - **판별 질문**: *"그 말이 사실이라면 지금 초록불일 수 있나?"* — 테스트에 대한 지적은 **테스트 결과로 먼저 반증**된다. 코드를 읽기 전에 물을 수 있어서 가장 싸다.

## 24. 실재하는 메서드를 실제와 다른 역할로 지목

- **배경**: 사례 23 을 고친 뒤 받은 **재리뷰**다. *"어떤 메서드가 그 트랜잭션을 유발하는지 명시하라"* 는 지적은 **맞았고**, 제안 문구까지 함께 왔다.
- **AI 출력**: *"`verifyAndPersist` → 판정 저장 + **커밋 후 캐시 넣기(`ClassificationService#persistReuse`)** 까지"*
- **무엇이 틀렸나**: **`persistReuse` 는 실재하지만 이 경로에 없다.** 두 가지가 어긋났다.

  | 제안이 말한 것 | 실제 |
  | --- | --- |
  | 캐시 넣기를 `persistReuse` 가 한다 | 넣기는 **커밋 후 `ClassificationPersistedEventListener`** 가 한다 |
  | 그 메서드가 이 흐름에 있다 | `persistReuse` 는 **재사용 저장 입구**다. 이 테스트는 재사용이 **꺼진** 상태라 아예 안 불린다 |

- **이 오류가 위험한 이유**: **사례 19 의 방법으로는 안 걸린다.** 19 는 인용한 심볼이 **실재하지 않아서** 소스 대조로 잡혔고, 넣었으면 빌드가 깨졌다. 24 는 **이름이 실재한다** — `grep` 하면 나오고, 주석이라 컴파일도 통과한다. 그대로 넣었으면 **javadoc 이 없는 호출을 가리킨 채 남는다.**
- **잡은 방법**: **그 동작의 주체를 호출자 검색으로 확인했다.** *"`putIfNotHuman` 을 실제로 부르는 곳이 어디인가"* 를 물었더니 **`ClassificationPersistedEventListener` 한 곳뿐**이었다. **「이 이름이 있는가」가 아니라 「이 동작을 누가 하는가」**를 물어야 갈린다.
  - ⚠️ **이 사례를 적으면서 나도 같은 실수를 했다.** 초안에 *"부르는 곳은 리스너 2개뿐"* 이라고 썼는데, 다른 리스너(③)는 `putIfNotHuman` 이 아니라 **`put`** 을 쓴다 — 덮어쓰기 방향이 한 방향이라 메서드가 다르다 (D-036). 호출자 검색을 **주석까지 세면** 2건이 나오는데 그중 하나는 javadoc 언급이었다. **grep 결과를 세기 전에 실제 호출인지부터 봐야 한다.**
- **수정**: **방향만 반영.** 메서드명을 적으라는 지적은 맞아서 **지나는 길 세 단계**를 그림으로 넣되 이름은 **호출 그래프대로** 썼고, 헷갈리기 쉬운 자리라 **「이 길에 `persistReuse` 는 없다」**를 경고로 함께 남겼다.
- **교훈**: **부류는 21 과 같은 「허구 메커니즘」이다 — 새 부류가 아니다.** *"`persistReuse` 가 캐시 넣기를 한다"* 는 **시스템에 없는 동작**이기 때문이다. 다만 **변종**이라 잡는 방법이 다르다.

  | | 심볼 | 잡는 질문 |
  | --- | --- | --- |
  | 19 | **없음** | 이 이름이 실재하나 |
  | 21 | 있음 | 여기서 **거기까지 갈 수 있나** |
  | 24 | 있음 | **이 동작을 누가 하나** |

  - **세 번 다 "방향은 맞고 내용이 틀렸다"였다** (17·21·24). 방향이 맞으면 내용을 안 따져보게 되는데, **이 팀에서 반복 확인된 가장 비싼 습관**이다.

## 25. 쉬운 말로 풀어 쓰다가 대상 범위가 좁아짐 — 이 프로젝트의 주제를 뒤집을 뻔했다

- **배경**: *"「감사」를 처음 보는 사람에게 어떻게 설명하지"* 라는 질문에서 시작해, 용어집에 **한 문장 요약**을 새로 넣었다 (PR #63).
- **AI 출력**: *"**AI 가 확신해서** 사람 손을 안 거치고 넘어간 건 중 20건에 1건을 몰래 뽑아 상담원이 다시 보는 것입니다"*
- **무엇이 틀렸나**: **감사 대상을 「AI 가 답한 것」으로 좁혔다.** 자동으로 확정되는 길은 둘인데 한쪽만 가리켰다.

  | 확정되는 길 | 요약에 들어갔나 |
  | --- | --- |
  | AI 가 확신도를 높게 매겨 바로 확정 (`AUTO_ACCEPTED`) | ✅ |
  | 같은 내용의 지난 답을 다시 씀 — **AI 를 아예 안 부름** (`REUSED`) | ❌ **빠졌다** |

  하필 **헌법이 이 프레임을 명시적으로 부정한 자리**다. D-033 은 *"이 시스템의 주제는 「AI 를 믿지 않는다」가 아니라 **「자동으로 확정된 것을 믿지 않는다」**"* 라고 적어뒀고, 재사용 건을 감사 대상에 넣은 근거가 통째로 그 문장이다.
- **이 오류가 위험한 이유**: **용어집은 다른 문서가 인용하는 기준점**이다. 게다가 **문장이 더 읽기 쉬워졌기 때문에 틀렸다는 티가 안 난다** — 어려운 말이 사라진 자리에 범위 축소가 같이 묻어 들어갔다.
  - 실제 영향도 있었다. 이 정의대로면 **재사용 건은 감사 대상이 아닌 게 되고**, 그러면 바로 전날 만든 `audit.reused` 집계(TRI-66)와 계약이 **설명 없이 어긋난다.**
- **잡은 방법**: **AI 리뷰가 API 계약과 대조**했다 (CodeRabbit). *"`audit` 객체는 `autoAccepted` 와 `reused` 를 별도 모집단으로 관리하는데 이 설명은 `autoAccepted` 만 대상인 것처럼 읽힌다."* **문서를 문서끼리가 아니라 「문서 ↔ 계약」으로 대조**해야 보이는 종류다.
- **수정**: 요약을 **「사람이 한 번도 안 보고 자동으로 확정된 건」** 으로 넓히고, **두 갈래를 표로 명시**했다(하나 틀렸을 때의 파급이 다르다는 것까지). 표기 예시 표에도 *"~~AI 가 답한 것 중에서 뽑는다~~ — 재사용 건이 빠진다"* 를 한 줄 넣어 같은 축소가 다시 일어나지 않게 했다.
- **교훈**: **새 부류 — 「쉬운 말로 바꾸다 범위 축소」.**
  - **쉽게 쓰려면 예시를 하나 세우게 되는데, 그때 다른 갈래가 조용히 빠진다.** 이 팀은 *"신입 개발자 기준으로 쓴다"* 를 헌법 규칙으로 두고 있어서 **앞으로도 반복될 자리**다.
  - **판별 질문**: *"이 쉬운 문장이 원래 정의보다 **좁아지지 않았나** — 원래 정의에 있던 갈래가 전부 들어 있나?"*
  - 22(추정치 요구)와 짝을 이룬다. **22 는 빈칸을 채우라 하고, 25 는 채운 값이 원본보다 작다.** 둘 다 **문서를 더 읽기 좋게 만드는 방향**이라 거르기 어렵다.

## 26. 프레임워크 동작을 「알고 있다」고 단정하고 그것을 기대값으로 박아 넣음 (TRI-86)

- **배경**: 감사 표본 삽입을 트랜잭션 ② 밖으로 빼면 표본이 몇 건 새는지 재는 대조 실험(TRI-86)을 짜는 중이었다. 「밖으로 뺀 판」은 커밋 후에 저장 묶음을 새로 여는 코드로 만들었다.
- **AI 출력**: 테스트의 기대값을 **미리 단정**해서 적었다.

  ```java
  @DisplayName("밖 (실험) · 정상 — 여기서도 10건이 다 들어간다.
               새는 것은 「밖에 뒀다」는 사실만으로는 안 생긴다")
  assertThat(sampling.sampledTotal()).isEqualTo(N);   // 10 을 기대
  ```

- **무엇이 틀렸나**: **실측은 0 건이었다.** 커밋 후에 저장 묶음을 평범하게 열면 스프링이 **이미 커밋된 그 트랜잭션의 자원을 그대로 물려받아**, 새 트랜잭션이 열린 것처럼 보이는데(`isNewTransaction=true`) 실제 DB 트랜잭션은 시작되지 않는다. INSERT 가 아무 데도 안 간다.
  - **저장 메서드는 정상 반환한다.** 예외도, 로그도 없다. 강제로 밀어내 봤을 때에야 `InvalidDataAccessApiUsageException: no transaction is in progress` 가 나왔다.
- **이 오류가 위험한 이유**: **틀린 방향이 하필 「안전한 쪽」이었다.** 기대값이 *"밖에 둬도 안 샌다"* 였으므로, 만약 이 단언이 **통과하는 모양으로** 나왔다면 그대로 *"D-012 는 과한 걱정이었다"* 는 결론을 evidence 에 적었을 것이다.
  - 더 나쁜 것은 **테스트가 빨간불이었기에 살았다**는 점이다. 기대값을 반대로 적었다면(0 을 기대) 테스트는 초록불이고 **원인은 영원히 안 봤다** — 같은 0 건이 「밖에 뒀으니 샌다」로 잘못 설명됐을 것이다.
- **잡은 방법**: **실행.** 문서 리뷰도 AI 리뷰도 아니고, Testcontainers 로 실제 MySQL 에 돌린 결과가 기대와 어긋나서 잡혔다. 어긋난 뒤에도 **원인을 추측으로 메우지 않고** 저장된 id 와 트랜잭션 상태를 찍어 확인했다 — 처음 세운 가설(FK 위반)은 틀렸다.
- **수정**: 실험을 **세 갈래**로 다시 짰다 — 안(현행) · 밖·평범 · 밖·분리(`REQUIRES_NEW`). 그 결과 **「평범하게 옮기면 아무것도 안 터졌는데 전부 샌다」** 는 것이 이 측정의 가장 중요한 결과가 됐다. 처음 기대대로 나왔다면 못 얻었을 결과다. → `evidence/measurement-3-rollback.md` 「대조 실험」
- **교훈**: **새 부류 — 「프레임워크 동작을 단정하고 그것을 기대값으로 박기」.**
  - 사례 23·24(호출 관계를 이름만 보고 단정)와 뿌리가 같지만 **대상이 우리 코드가 아니라 프레임워크**라 더 잘 속는다. 우리 코드는 열어보는데, 프레임워크는 *"원래 그렇게 동작한다"* 로 넘어간다.
  - **판별 질문**: *"이 기대값은 **실행해서 본 것인가**, 아니면 프레임워크가 그럴 것이라고 **믿는 것인가**?"*
  - **측정 코드에서 특히 위험하다.** 측정은 정의상 **모르는 값을 알아내려고** 짜는 것인데, 기대값을 미리 박으면 **아는 값을 확인하는 코드**가 된다. 이 팀의 규칙 *"재보지 않은 성능 수치를 만들지 않는다"* 가 문서뿐 아니라 **테스트 단언에도 적용된다**는 뜻이다.

**관찰 1 — 검출 난이도가 방법별로 갈린다.** grep 은 표면적 불일치만 잡는다. AI 리뷰가 잡은 9건은 grep 으로 한 건도 안 잡혔다. 각 문장이 개별적으로는 타당하고, 문장 **사이의 관계**를 추론하거나 **런타임 동작을 알아야** 보이기 때문이다.

> 사례 14·15 는 이 경계를 정확히 갈라 보여준다. 둘 다 문서를 나란히 놓고 발견했지만, **14(인용 번호 오류)는 기계화할 수 있고 15(404 ↔ fallback 모순)는 안 된다.** 14 는 `grep -o 'D-[0-9]\{3\}'` 로 인용을 모아 `DECISIONS.md` 제목과 짝지으면 끝이고, 15 는 *"이 오류를 받은 사람에게 남은 행동이 있나"* 를 물어야만 보인다. **기계화 가능한 것을 사람이 계속 잡고 있으면, 사람이 15 를 볼 여력이 줄어든다.**

**관찰 2 — AI 코드리뷰가 잡은 9건은 전부 AI 가 만든 설계였다.** AI 를 AI 로 검증한 사례이며, 최종 판단(무엇을 고치고 무엇을 한계로 수용할지)은 사람이 했다. 예: 사례 4 에서 앵커링 편향은 **제거하지 않고** "측정값을 하한값으로 해석"하는 쪽을 택했다 — 5일 일정에서 완전 제거보다 편향의 방향을 아는 쪽이 정직하다는 판단.

> ⚠️ 단, 동일 AI가 만든 설계를 동일 AI가 검증할 경우 같은 전제를 공유해 맹점이 겹칠 수 있다. 사람의 최종 판단이 이 위험을 줄이는 핵심 역할을 한다.

**관찰 3 — 리뷰 5회가 각각 다른 층위를 잡았다.** 한 번의 리뷰로 끝내지 않은 것이 유효했고, **회를 거듭할수록 문서 대조로는 못 잡는 층위로 내려갔다.**

| 회차 | 층위 | 대표 사례 |
| --- | --- | --- |
| 1차 | **구조** — 정보 은닉, 인덱스 컬럼 | 4, 5 |
| 2차 | **원자성** — 트랜잭션 경계 | 6 |
| 3차 | **논리** — 인과관계, 계약 완결성 | 7, 8 |
| 4차 | **실행 가능성** — 런타임 동작, 존재하지 않는 메커니즘 | 9, 10 |
| 5차 | **검증 가능성** — 이 명세로 무엇을 측정·증명할 수 있나 | 11, 12 |

**관찰 4 — 리뷰가 "잘한 점"으로 칭찬한 항목에서 결함이 나왔다.** 사례 9(D-007 락 전략)는 1·2·3차 리뷰가 모두 "잘한 점"으로 언급했고 4차에서야 실행 불가임이 드러났다. 5차는 그 **수정본**(D-016 트랜잭션 경계)을 다시 칭찬했다. **칭찬받은 부분이 검증된 부분은 아니다** — "설계 의도가 잘 정리됐다"는 평가는 그 설계가 동작한다는 뜻이 아니다.

**관찰 5 — 마지막 두 층위(실행 가능성·검증 가능성)는 문서만으로는 자기 검증이 불가능하다.** 사례 9·10 은 런타임 동작 지식이, 11·12 는 *"이 명세로 무엇을 측정할 수 있나"* 라는 외부 관점이 있어야 보인다. **문서를 아무리 여러 번 읽어도 안 나오는 층위**이며, 이것이 코드 착수 전에 리뷰를 5회 돌린 실질적 이유다.

**관찰 6 — 코드 층으로 내려오자 리뷰가 틀리는 방식이 바뀌었다** (2026-08-06~07 추가).

| | 문서 층 (사례 1~15) | 코드 층 (사례 16·17) |
| --- | --- | --- |
| 틀리는 방식 | 관계를 잘못 추론하거나 없는 것을 있다고 함 | **입력을 다 못 보거나(16), 다 보고도 계산이 틀림(17)** |
| 알아채기 | 다른 문서와 대조하면 보인다 | **대조할 문서가 없다.** 직접 돌려보거나 계산해야 한다 |
| 안 잡혔을 때 | 문서가 모순 상태로 남는다 | **테스트가 초록불인 채로 아무것도 안 지킨다** |

**관찰 7 — 세 번째 층이 열렸다: 우리가 만든 도구 자체** (2026-08-08 추가).

사례 18 은 문서도 코드도 아니라 **`.claude/commands/` 의 작업 도구**에서 나왔다. 앞의 두 층과 다른 점이 셋 있다.

- **틀리는 방식**: 규칙 문장은 맞는데 **전제한 관계(PR ↔ 티켓이 1:1)가 실제와 다르다.** 읽어서는 안 걸리고 **적용해야 걸린다** (사례 2 와 같음)
- **알아채기**: 대조할 대상이 문서도 테스트도 아닌 **실제 데이터**다. 이번엔 PR 34건과 Jira 89건을 나란히 놓고서야 보였다
- **안 잡혔을 때**: 도구가 **팀 공유 상태(Jira)를 틀리게 바꾼다.** 게다가 틀리는 방향이 「끝났다」 쪽으로 쏠려서 **틀린 결과가 관측 대상에서 빠진다**

> **이 층에서는 「사람이 확인한 뒤에만 실행」이 정확성보다 먼저다.** 규칙은 틀릴 수 있고 실제로 틀렸지만, 확인 단계가 있어서 사고로 이어지지 않았다.
> 도구를 만들 때 **자동화의 범위를 넓히는 것보다 확인 지점을 남기는 것이 먼저**라는 근거가 이 사례다.

코드 PR 6건에서 리뷰가 잡은 진짜 결함도 함께 늘었다(정규화 키 병합 결함 2종 → D-053 / record 생성자가 절반만 채워진 실패를 통과 / blind 시드의 정답 역산). **검출력 자체는 코드 층에서도 유효했다** — 다만 **틀렸을 때 그 사실이 드러나는 경로가 사라졌다**는 것이 이 관찰의 요지다.

**관찰 8 — 여러 봇의 합의가 정답의 근거가 아니다** (2026-08-08 추가).

사례 19 는 **독립적인 리뷰 봇 2종이 같은 허구**(`[이메일]` 토큰)를 만든 경우다. 관찰 2 가 경고한 *"같은 AI가 만든 설계를 같은 AI가 검증하면 맹점이 겹친다"* 의 변주인데, 이번엔 **다른 봇들**이 같은 결론에 도달했다 — 같은 표면 정보(원문에 이메일이 있다)에서 같은 그럴듯한-오답으로 수렴했기 때문이다. **"두 리뷰어가 같은 말을 한다"를 교차검증으로 착각하면 안 된다.** 코드베이스의 구체적 사실(토큰·심볼)을 인용받으면 봇 수와 무관하게 **소스로 한 번 확인한다.** 이 사례가 미검출됐다면 테스트에 빌드를 깨는 단언이 들어갔을 것이다.

> **모델 ID 행이 한동안 이 표에 남아 있던 이유**: 한 번 닫았던 항목이 **계약이 바뀌면서 다시 열렸다.** 근거 사슬이 순환하던 문제(계약의 AI 생성 예시 → D-024 가 그 값을 "기존 값"이라며 인용 → `.env.example`·테스트로 전파)를 실물 조회로 끊었는데, 값이 교체되면 그 검증은 새 값에 대해 아무것도 말해주지 않는다. **검증은 값에 붙는 것이지 항목에 붙지 않는다.**

- **문서 리뷰로는 한 건도 안 잡힌다.** 전부 실제 데이터를 넣어봐야 드러나는 층위다 (관찰 5 가 말한 "문서만으로는 자기 검증이 불가능한" 영역)
