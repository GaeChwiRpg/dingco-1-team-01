**재현 방법** — 두 답안지를 `ref` 로 맞춰 마지막 칸만 비교한다.

⚠️ **세는 것보다 먼저 「셀 수 있는 상태인지」를 확인한다.** `join` 은 한쪽에만 있는 `ref` 를
**조용히 버리고**, 중복된 `ref` 는 **곱해서 늘린다.** 그러면 분모가 50 이 아닌데도 숫자는 멀쩡히
나온다 — 일치율이 실제보다 높게도 낮게도 될 수 있고, **어느 쪽인지 알 방법이 없다.**
그래서 아래 1단계가 실패하면 거기서 멈춘다.

```bash
cd src/test/resources/seed

# 1) 셀 수 있는 상태인지 — 각 파일이 정확히 50행이고 ref 1~50 이 한 번씩만 있는가
for f in inquiries-50-label-1st-junhyun.csv inquiries-50-label-2nd-yongtaek.csv; do
  n=$(tail -n +2 "$f" | wc -l | tr -d ' ')
  u=$(tail -n +2 "$f" | cut -d, -f1 | sort -n | uniq | wc -l | tr -d ' ')
  s=$(tail -n +2 "$f" | cut -d, -f1 | sort -n | tr '\n' ' ')
  [ "$n" = 50 ] && [ "$u" = 50 ] && [ "$s" = "$(seq 1 50 | tr '\n' ' ')" ] \
    || { echo "❌ $f — 행 $n / 고유 ref $u. 여기서 멈춘다"; exit 1; }
  echo "✅ $f — 50행, ref 1~50 각 1회"
done

# 2) 그다음에 센다
tail -n +2 inquiries-50-label-1st-junhyun.csv  | awk -F, '{print $1"\t"$NF}' | sort -n > /tmp/l1.tsv
tail -n +2 inquiries-50-label-2nd-yongtaek.csv | awk -F, '{print $1"\t"$NF}' | sort -n > /tmp/l2.tsv
joined=$(join -t$'\t' /tmp/l1.tsv /tmp/l2.tsv | wc -l | tr -d ' ')
[ "$joined" = 50 ] || { echo "❌ 맞춰진 행이 $joined 건 — 50 이 아니다"; exit 1; }
join -t$'\t' /tmp/l1.tsv /tmp/l2.tsv | awk -F'\t' '$2==$3' | wc -l
```

## ⚠️ 이 값을 읽을 때 알아야 할 것 — 조건이 완전히 깨끗하지 않다

**세 가지를 숨기지 않고 적는다.** 숨기면 나중에 "일치율이 왜 이렇게 높지"를 설명할 수 없게 되고, 그러면 이 숫자로 측정 8ⓐ-1 에서 검토자 불일치 몫을 떼어낼 수 없다.

### ⓐ 1차는 두 번 매겼다 — 90.0% → 98.0%

| | 조건 | 일치율 |
| --- | --- | --- |
| **첫 판** | 갈린 자리를 모르는 상태 | **45/50 = 90.0%** |
| **재작성** (채택) | **갈린 5건의 `ref` 번호를 아는 상태.** 2차 답은 보지 않음 | **49/50 = 98.0%** |

첫 판 직후 대조를 돌렸고, 그 과정에서 **어느 건이 갈렸는지가 1차 작성자에게 알려졌다.** 답 자체는 보지 않고 다시 매겼다(작성자 확인). 다만 *"이 5건을 다시 보라"* 는 정보는 이미 전달된 뒤였다.

바뀐 4건은 다음과 같다. **첫 판은 커밋되지 않았으므로 이 기록이 유일한 근거다.**

| ref | 첫 판 | 재작성 | 2차 |
| --- | --- | --- | --- |
| 14 | `PROMOTION` | `SERVICE_USAGE` | `SERVICE_USAGE` |
| 16 | `PAYMENT` | `SERVICE_USAGE` | `SERVICE_USAGE` |
| 28 | `PROMOTION` | `SERVICE_USAGE` | `SERVICE_USAGE` |
| 41 | `SERVICE_USAGE` | `COMPLAINT` | `COMPLAINT` |
| 45 | `ACCOUNT` | `ACCOUNT` (유지) | `SERVICE_USAGE` |

> **보수적으로 읽는다: 90.0% 를 하한, 98.0% 를 상한으로 본다.** 측정 12 가 재려는 것은 *"두 사람이 서로 안 보고 매기면 얼마나 일치하나"* 이고, 그 조건에 더 가까운 것은 **첫 판(90.0%)** 이다.
>
> ⚠️ **단 아래 ⓑ 의 노출 3건까지 빼면 89.4% 로 기준을 밑돈다.** 네 값을 한 표로 정리한 것은 「어느 값을 쓰나」 절에 있다 — **"어느 쪽이든 90% 를 넘는다"고 읽지 않는다.**

**첫 판에서 갈린 5건 중 4건이 `SERVICE_USAGE` 와 얽혀 있었다** (적립금 사용처 · 쿠폰 미적용 · 쿠폰 미표시 · 앱 튕김). 우연으로 보기 어렵고, **§7 표에서 `SERVICE_USAGE` 와 다른 항목의 경계가 얇다**는 신호다. 재작성으로 수치는 올랐지만 **경계가 얇다는 사실 자체는 그대로 남아 있다.**

### ⓑ `ref 1·2·3` 의 2차 답이 1차 작성 전에 노출됐다

AI 보조 도구(Claude Code)가 작업 상태를 확인하는 과정에서 2차 답안지의 앞 3줄을 화면에 띄웠다. 나머지 47건은 노출되지 않았다.

- 세 건 모두 두 사람의 답이 **일치**했다 (`SERVICE_USAGE` · `ACCOUNT` · `ORDER_CHANGE`)
- **제외하고 계산하면 46/47 = 97.9%** — 노출이 결과를 크게 움직이지는 않았다
- 다만 첫 판 기준으로는 42/47 = **89.4%** 로 90% 를 밑돈다

## 어느 값을 쓰나 — 네 값이 나오는 이유

보정이 둘(ⓐ 첫 판 / ⓑ 노출 제외)이라 조합이 넷이다. **골라 쓰지 말고 넷을 다 적는다.**

| | 전체 50건 | 노출 3건 제외 (47건) |
| --- | --- | --- |
| **첫 판** (조건에 더 가까움) | 45/50 = **90.0%** | 42/47 = **89.4%** ← 가장 보수적 |
| **재작성** (채택) | 49/50 = **98.0%** | 46/47 = **97.9%** |

**⚠️ 가장 보수적인 값 89.4% 는 판정 기준 90% 를 0.6%p 밑돈다.** 이걸 숨기지 않는다.

**다만 89.4% 가 「노출 때문에 부풀었다」는 증거는 아니다.** 뺀 3건이 **전부 일치**한 건이라,
빼면 분자에서 3, 분모에서 3 이 함께 빠진다 — 원래 비율이 90% 인 표본에서 100% 일치인 3건을
덜어내면 **산술적으로 반드시 내려간다.** 즉 이 하락은 노출의 영향이 아니라 **표본이 47건으로
작아서 생긴 흔들림**이다. 1건이 0.6%p 를 좌우하는 크기다.

**그래서 이렇게 읽는다.**

- **판정에 쓰는 값**: 90.0% (첫 판, 전체 50건) — 노출된 3건도 **두 사람이 독립적으로 같은 답을
  낸 건**이라 표본에서 뺄 이유가 없다. 뺀 계산은 **민감도 확인용**이다
- **89.4% 가 말해주는 것**: 이 표본에서는 **1건이 판정을 뒤집을 수 있다.** 50건은 90% 선을
  가르기엔 작은 표본이고, 그 사실이 결론보다 중요하다

### ⓒ 1차 작성자는 AI 가 붙인 `expected_category` 를 이미 본 상태다

`inquiries-50.csv` 의 `expected_category` 는 AI 가 붙인 값이고(`seed-draft-provenance.md`), 1차 작성자는 그 파일을 만든 사람이라 **앵커링이 남는다.** 2차 작성자는 blind 서식만 받아서 이 영향이 없다. `README.md` 가 미리 적어둔 한계 그대로다.

## 판정

**98.0% (판정에 쓰는 하한 90.0%) → 「90% 이상」에 해당하므로 그대로 진행한다.** §7 경계표를 조이고 **다시 레이블하는 절차**는 발동하지 않는다.

**⚠️ 그러나 「경계표를 안 고쳐도 된다」로 읽지 않는다.** 세 가지가 같은 곳을 가리키고 있다.

1. 가장 보수적인 값 **89.4% 는 기준을 밑돈다** — 1건이 판정을 뒤집는 표본 크기다
2. 첫 판에서 갈린 5건 중 **4건이 `SERVICE_USAGE` 와 얽혀 있었다**
3. 아직 안 갈린 1건(`id 24`)도 **`ACCOUNT` × `SERVICE_USAGE` 겹침**이다

**절차가 발동하지 않는 것과 표가 멀쩡한 것은 다른 말이다.** 재레이블은 안 하되, 위 「남은 일」 2번(§7 표에 겹침 규칙 추가)은 **그대로 남는다.**

| 일치율 | 무엇을 하나 |
| --- | --- |
| **90% 이상** | **그대로 진행** ← 여기 |
| 90% 미만 | **§7 경계표를 조인 뒤 다시 레이블한다** |
| 조여도 안 오름 | D-046 재평가 조항 발동 — 카테고리 10종 → 5종 축소를 앞당긴다. 사람에게도 안 갈라지는 카테고리는 AI 에게 물어보는 것 자체가 성립하지 않는다 |

**남은 일 2가지** (이 문서 밖)

1. **`id 24` (ref 45) 의 최종 정답 확정** — §7 표로는 `ACCOUNT` 지만 2차 작성자 확인이 필요하다. 확정 전에는 `inquiries-50.csv` 의 정답 50건이 완성되지 않고, **TRI-77(측정 1·8ⓐ)을 시작할 수 없다**
2. **§7 표에 `ACCOUNT` × `SERVICE_USAGE` 겹침 규칙 추가 검토** — 위 권고 참조. `PRD.md` 수정이라 별도 PR
