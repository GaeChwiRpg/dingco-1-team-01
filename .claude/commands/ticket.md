**일을 나눠 주는 사람이 아니다 — 담당은 구역(P1/P2/P3)으로 이미 정해져 있다 (D-015, 재배정은 D-031).**

받은 사람이 **다른 문서를 열지 않고도 코드를 칠 수 있는 상태**로 만들어 주는 것이다.
너는 코드를 쓰지 않는다. 고르고, 상태를 옮기고, 컨텍스트를 모아 준다.

## 공통 — 어디서 무엇을 읽나

**일정·상태·담당은 Jira, 티켓 내용은 Jira 본문, 코드 연결은 PR 제목.** 셋을 섞지 마라.

### Jira (일정·상태의 원본)

- 사이트 `https://dingco-1-team-01.atlassian.net` · cloudId `08a0a4d5-7335-44a5-b49a-d75016ba3eab` · 프로젝트 **`TRI`**
- 이슈 종류 4단: **에픽 → 스토리 → 하위 작업**, 그리고 딸린 데 없는 **작업**(TRI-75). **실제로 치는 건 하위 작업**이다
- 상태 4종과 전환 id: **`11` 할 일 · `21` 진행 중 · `31` 검토 중 · `41` 완료** (실측 확인)
- **마감일(`duedate`)이 일정의 전부다.** 스프린트도 스토리 포인트도 안 쓴다. 지연 판정은 `duedate < 오늘 && status != 완료` 하나뿐이다

### ⚠ 목록 조회는 그대로 받으면 잘린다 — 반드시 `jq` 로 뽑는다

**이 팀은 티켓 본문(description)에 설계 근거를 통째로 적는다.** 그래서 응답이 매우 크다. 실측값:

| 조회 | 응답 크기 | 결과 |
| --- | --- | --- |
| 89건 전체 | 약 44만 자 | **잘림** |
| 미완료 20건 (한 사람) | 약 10만 자 | **잘림** |

**`fields` 를 좁혀도 본문은 따라온다.** 좁히기로는 못 막는다. 그래서 절차는 이렇다.

1. `searchJiraIssuesUsingJql` 을 그냥 친다. 잘리면 **결과가 파일로 저장되고 그 경로가 알려진다**
2. 그 파일을 `Read` 로 통째로 읽지 마라 — 같은 이유로 또 잘린다. **`jq` 로 필요한 칸만 뽑는다**

```bash
F=<알려준 파일 경로>
jq -r '.issues.nodes[] | [.key, .fields.issuetype.name, .fields.status.name,
  (.fields.assignee.displayName // "미배정"), (.fields.duedate // "-"),
  ((.fields.labels // []) | join(",")), (.fields.parent.key // "-"), .fields.summary]
  | @tsv' "$F" | column -t -s$'\t'
```

**몇 건을 읽었는지 세라.** `jq -r '.issues.nodes | length'` 와 `.issues.pageInfo.hasNextPage` 를 함께 본다.
`hasNextPage` 가 `true` 면 `nextPageToken`(= `endCursor`)을 넘겨 다음 장을 받고, `false` 가 될 때까지 반복한다.
**일부만 보고 판단하는 게 이 커맨드의 최악이다** — 못 찾은 것과 없는 것을 구별하지 못하면 조용히 틀린다.

**JQL 은 단순하게 친다.** `summary ~ "..."` 로 티켓을 걸러내지 마라 — 제목 형식에 기대면 형식이 조금만 달라도 소리 없이 빠진다.
거르는 건 JQL 이 아니라 받아온 뒤 `jq` 다.

### 티켓 내용 — **`TICKETS.md` 는 없다. Jira 본문이 그 자리다**

한 건을 볼 때는 `getJiraIssue` 로 본문까지 읽는다. 이 팀의 티켓 본문에는 이미 이런 게 들어 있다.

- **할 일** — 한두 줄 요약
- **만들 파일** / **고칠 파일** — 헌법의 「코드 위치」와 같은 경로
- **흐름** — 코드 블록으로 그린 순서
- **끝났다고 볼 조건** — 체크리스트. 이게 사실상 리뷰 기준이다
- **받아들이는 한계** — 안 막기로 한 것
- 근거 **D-번호** — 본문에 그대로 적혀 있다

**본문에 없는 것을 지어내지 마라.** 「끝났다고 볼 조건」이 비어 있으면 "본문에 없음"이라고 쓴다.

### GitHub — **이슈는 쓰지 않는다. PR 제목이 유일한 연결선이다**

이 저장소의 GitHub Issue 는 **0건**이다 (실측). `Closes #N` 도 쓰지 않는다.
티켓과 코드는 **PR 제목·본문에 적힌 `TRI-번호`** 로만 이어진다.

```bash
gh pr list --repo GaeChwiRpg/dingco-1-team-01 --state all --limit 40 \
  --json number,title,state,headRefName,author \
  --jq '.[] | [.number, .state, .author.login, .title] | @tsv'
```

제목에서 `TRI-\d+` 를 전부 뽑는다. **`TRI-51·52·82` 처럼 한 PR 이 여러 건을 담는다** — 하나만 뽑고 끝내지 마라.
`TRI-56~58` 같은 **범위 표기도 쓴다.** `~` 를 만나면 앞뒤를 펼쳐 3건으로 센다.

**GitHub 에서 상태를 만들지 마라.** PR 의 열림/머지 여부를 **읽기만** 한다. Jira 가 원본이다.

## 모드 B. 다음 티켓 추천 — **내 구역 안에서만 고른다**

**배당이 아니다.** 이미 내 것인 티켓 중에서 **다음에 칠 것**을 고르는 모드다.

### 1. 후보를 거른다

```text
project = TRI AND assignee = currentUser() AND status = "할 일" ORDER BY duedate ASC
```

여기서 **하위 작업**만 남기고(에픽·스토리는 담는 그릇이지 치는 단위가 아니다), **아래 넷을 다 통과한 것만** 후보다.

1. **부모 스토리가 죽어 있지 않다.** 부모가 `할 일` 인데 형제 하위 작업이 하나도 안 끝났으면 그 스토리부터 시작하는 것이다 — 그건 후보로 두되 「시작 순서」에 적는다
2. **선행이 끝나 있다.** 티켓 본문에 `TRI-번호` 로 적힌 앞 작업이 **전부 `완료`** 여야 한다. 본문에 선행이 안 적혀 있으면 **없는 것으로 본다 — 지어내지 마라**
3. **건드릴 파일이 진행 중·검토 중 티켓과 겹치지 않는다.** 본문의 「만들 파일」끼리 대조한다. 하나라도 겹치면 탈락
4. **내가 방금 반려한 티켓이 아니다** (이번 대화에서 "다른 거" 라고 한 것)

**파일이 겹치는 상대가 내 티켓이면 그건 충돌이 아니라 직렬 병목이다** — "앞 티켓이 끝나야 한다"로 안내한다.
**상대가 남의 티켓이면 계약 A/B/C 가 갈라 준 자리인지 먼저 본다.** 계약이 갈라 준 자리면 겹칠 리가 없고,
겹친다면 **계약을 넘고 있다는 신호**다 — 그때는 추천하지 말고 **"헌법 「모듈 간 계약」을 넘는다. 세 담당자 합의 + `DECISIONS.md` 항목이 먼저다"** 라고 쓴다.

넷 다 통과한 게 없으면 **거기서 멈추고 왜 없는지 말한다.** 억지로 추천하지 않는다.
**"추천할 게 없다" 는 대개 "내 구역이 남의 구역을 기다리고 있다"** 는 뜻이다.
그때는 새 티켓을 찾지 말고 **막고 있는 구역의 담당자에게 가서 그 티켓을 같이 끝낸다.** 누구를 찾아가야 하는지까지 적어 준다.

### 2. 3건 이내로 추천한다

우선순위는 이 순서다.

1. **마감이 지났거나 오늘인 것** — 일정이 이미 밀린 것부터
2. **막고 있는 게 많은 티켓** — 이게 안 끝나면 몇 건이 못 시작하는지 본문의 선행 표기를 역으로 센다
3. **측정 티켓**(`measurement` 라벨, 본문에 「측정 N」) — 실측은 데이터를 쌓는 시간이 필요해 일찍 걸어야 한다
4. **같은 부모 스토리 안에서 이미 시작한 것이 있는 티켓** — 스토리를 하나씩 닫는 게 반쯤 열린 스토리 여럿보다 낫다

형식:

```text
■ 추천 1 · TRI-54 — @Retryable(3) + @Recover 구현 (실패 시 FAILED + 큐 삽입)
    마감: 2026-08-09 (D-1)   |   부모: TRI-17 (할 일)
    왜: 이게 끝나야 TRI-55 재시도 실측(측정 4)이 시작됨
    선행: TRI-49 (완료 ✓) · TRI-51 (검토 중 ⚠)
    파일 충돌: 없음
■ 추천 2 · ...

■ 지금 못 치는 것 중 눈에 띄는 것
    TRI-53 — 선행 TRI-40(1단 캐시)이 아직 할 일 (P1 이용택) ← 막히면 여기로 간다
    TRI-66 — 선행 TRI-64·65 가 안 끝남 (내 구역, 순서대로 쳐야 함)
```

### 3. 고르게 한다 — **멋대로 시작하지 않는다**

`AskUserQuestion` 으로 추천 3건 + "다른 거" 를 선택지로 준다.

### 4. 시작 직전에 한 번 더 확인한다

**담당자를 새로 찍는 절차는 없다 — 이미 내 티켓이다.** 여기서 하는 건 **상태 전환뿐**이다.

그래도 `getJiraIssue` 로 한 번 더 본다. **내가 다른 자리에서 이미 시작해 뒀을 수 있다.**

- **상태가 이미 `진행 중` 이상 → 전환하지 말고 그대로 말한다.** 되돌리지 않는다. 1번으로 돌아가 다시 추천한다
- 여전히 `할 일` → `transitionJiraIssue` 로 **`21` 진행 중**

**GitHub 쪽에 할 일은 없다** (이슈를 안 쓴다). 대신 **PR 제목에 `TRI-번호` 를 넣으라고 알려 준다** — 그게 유일한 연결선이다.

### 5. 시작했으면 모드 A 출력을 이어서 낸다

시작한 티켓의 컨텍스트를 바로 보여준다. 여기서 한 번 더 부르게 하지 않는다.

## 모드 A. 조회 — 출력 형식

`getJiraIssue` 로 본문까지 읽은 뒤, 아래 9줄을 **이 순서 그대로**. 줄을 빼거나 순서를 바꾸지 않는다.

```text
■ TRI-47 · 하위 작업 · 검토 중 · 김준현 · 마감 2026-08-08 — 비동기 분류 리스너 만들기
■ 부모: TRI-14 (진행 중) — 시스템은 접수 후 뒤에서 AI 를 불러 분류와 확신도를 받는다 · 에픽 TRI-4 (P2)
■ 근거 결정: D-058(클래스 이름) D-031(트랜잭션 ①②분리) D-033(체인 금지) D-014(캐시≠절감)
■ 만들/고칠 파일: service/event/InquiryReceivedEventListener, @Async 설정
■ 계약 영향: 계약 A 수신 쪽 — 있음 / 계약 B·C — 없음
■ API 변경: 없음  (있으면 → API-CONTRACT.md 동반 갱신 필수, 헌법 「작업 경계」)
■ 끝났다고 볼 조건: 접수 API 스레드를 막지 않는다 / 재사용 판단을 여기서 한다 / 2단 hit 이면 REUSED 행 저장이 곧 ② / 클래스 최상단 javadoc 3줄
■ 선행: TRI-46 (완료 ✓) · TRI-83 (검토 중 ⚠ — 같은 PR 로 묶임)
■ 같은 파일을 건드리는 진행 중 티켓: 없음   |   연결된 PR: #30 (OPEN)
```

**「계약 영향」 줄을 빼지 마라.** 이 팀에서 병렬 작업이 굴러가는 근거가 계약 A/B/C 세 개뿐이라,
계약을 건드리는 티켓은 **세 담당자 합의 + `DECISIONS.md` 항목**이 먼저다 (헌법 「모듈 간 계약」).

| 계약 | 무엇 | 건드리면 |
| --- | --- | --- |
| **A** `InquiryReceivedEvent` | P1 → P2 로 넘기는 접수 신호 | 이용택 · 김준현 합의 |
| **B** 큐 삽입 필수 칸 | P2 → P3 로 넘기는 검토 항목 | 김준현 · 김은빈 합의 |
| **C** 분류 캐시 값 구조 | P1 읽기·쓰기 ↔ P2 쓰기 ↔ P3 쓰기 | **3인 전원 합의** |

**관련 문서는 구간만 가져온다.** 파일 전체를 읽지 말고 `Grep` 으로:
`DECISIONS.md`(본문에 나온 D-번호 전부) · `PRD.md`(관련 § · 측정 번호) · `API-CONTRACT.md`(해당 endpoint) ·
`CLAUDE.md`(`@Transactional` 위치 / 락·동시성 / 캐시 전략 / blind 규칙 / Lombok 규칙).

그 아래 **"이 티켓에서 지켜야 할 것"** 3줄 이내. 해당 티켓에 실제로 걸리는 것만. 일반론 금지.
자주 걸리는 것: **불변 규칙 3개** · **`@Transactional` 은 ①②③ 세 자리뿐** · **감사 표본 blind (D-010)** · **`@Data`·`@Setter` 금지 (D-057)**.

## 모드 E. 팀 현황판 — 3인의 일정과 막힌 곳

**혼자 쓰는 모드가 아니다.** 데일리에 붙여 읽거나 `INTEGRATION-LOG.md` 를 쓸 때 근거로 쓴다.

### 1. 한 번에 읽는다


**89건이라 확실히 잘린다.** 위 「공통」의 `jq` 절차를 그대로 쓴다. PR 목록도 함께 읽는다.

### 2. 이렇게 보여준다

```text
■ 팀 현황 (2026-08-08 기준 · Jira 실측 N건)

  담당      완료   검토중  진행중  할일   지연

    없음. 단 아래 2건은 규칙만 따르면 잘못 옮기는 자리다 (모드 D 예외 1·2)
    TRI-47  #21 머지됐지만 같은 티켓의 #30 이 열려 있음
    TRI-38  #18 머지됐지만 형제 TRI-37·39 만 완료. 담당자 확인 필요

    P2 TRI-53 (②커밋 후 캐시 저장) ← P1 TRI-40 (1단 캐시) 이 아직 할 일
    P3 TRI-44 (③ 캐시 덮어쓰기)    ← 같은 계약 C. 셋이 같은 캐시를 쓴다
```

막히는 자리는 대부분 계약이 만나는 지점이다. **누가 누구를 기다리는지 이름으로 적는다.**

### 3. 지연을 셀 때 「진짜 지연」과 「동기화 미반영」을 갈라 놓는다

판정식은 `duedate < 오늘 && status != 완료` 하나지만, **여기에 걸린 것 중 일부는 일이 밀린 게 아니라 Jira 만 안 옮긴 것**이다.
**연결된 PR 이 `MERGED` 인 티켓은 지연 목록에 넣되 「동기화 미반영」이라고 표시한다.**
안 가르면 사람이 이미 끝낸 일을 밀린 일로 보고받게 되고, 그러면 이 현황판을 안 믿게 된다.

### 4. 숫자를 지어내지 마라

Jira 에서 읽은 건수만 쓴다. **속도·처리량 같은 성능 수치는 이 모드에서 아예 다루지 않는다** — 측정은 본인 실측만 (헌법 「AI 검증 규칙」).

## 모드 D. 밀린 Jira 상태 맞추기

**PR 에서 일어난 일 중 Jira 에 반영이 안 된 것을 찾아 옮긴다.** Jira 전환을 자동으로 해 주는 것은 아무것도 없으므로 이게 유일한 보정 장치다.
**`/ticket 동기화` 는 PR 을 머지한 직후에 친다.** 잊고 지나가도 다음에 치면 밀린 게 한꺼번에 따라온다.

### 1. 두 개를 읽는다

```bash
gh pr list --repo GaeChwiRpg/dingco-1-team-01 --state all --limit 40 \
  --json number,title,state,author --jq '.[] | [.number, .state, .author.login, .title] | @tsv'
gh api user --jq .login
```

Jira 쪽은 「공통」의 JQL + `jq` 로 이미 들고 있다.
PR 제목에서 `TRI-\d+` 를 **전부** 뽑고 `~` 범위는 펼친다 (`TRI-56~58` → 56·57·58).

### 2. 판정한다 — **PR 은 읽기만 하고, 옮기는 건 Jira 뿐이다**

| PR | Jira | 할 일 |
| --- | --- | --- |
| `MERGED` | `완료` 아님 | → `transitionJiraIssue` **`41` 완료** |
| `OPEN` | `검토 중` 아님 (`할 일`·`진행 중`) | → `transitionJiraIssue` **`31` 검토 중** |
| PR 없음 | `검토 중` | → **손대지 않고 목록에만.** 어디서 검토 중인지 사람이 안다 |
| — | 담당자 비어 있음 | → `editJiraIssue` 로 채움 — **아래 조건** |

**⚠ 위 표를 그대로 따르면 틀리는 경우가 둘 있다. 실제로 겪었다 (2026-08-08).**

**예외 1 — 같은 티켓을 담은 PR 이 여럿이면 「가장 나중 것」이 이긴다.**
머지된 PR 하나만 보고 완료로 옮기지 마라. **그 티켓을 담은 PR 을 전부 모은 뒤 가장 최근 것의 상태로 판정한다.**
겪은 예: TRI-47 은 **#21(클래스 개명 문서, 머지됨)** 과 **#30(실제 구현, 열림)** 양쪽에 있다.
#21 만 보고 완료로 옮기면 **아직 리뷰 중인 일이 끝난 것으로 둔갑한다.** 이럴 때는 **열려 있는 쪽을 따라 `검토 중` 으로 두고 손대지 않는다.**

**예외 2 — 한 PR 의 형제들 중 혼자만 안 옮겨져 있으면 담당자가 일부러 남긴 것으로 본다.**
`TRI-37·39·38` 처럼 한 PR 이 여러 건을 담았는데 **일부는 이미 `완료` 고 하나만 `진행 중`** 이면,
그건 옮기는 걸 잊은 게 아니라 **그 건만 남은 일이 있다는 신호**다 (겪은 예: TRI-38, PR #18).
**옮기지 말고 목록에 적어 담당자에게 확인을 넘긴다.** 특히 **남의 구역이면 절대 대신 옮기지 않는다.**

> 두 예외의 공통점: **PR 이 머지됐다는 사실은 「그 티켓이 끝났다」와 같은 말이 아니다.**
> 옮기기 전에 **"이 티켓을 담은 PR 이 이것 하나뿐인가", "같은 PR 의 형제들은 어떤 상태인가"** 를 먼저 본다.

**담당자 채우기**: 이 저장소는 GitHub 이슈를 안 써서 **"GitHub 배정을 보고 Jira 를 채우는" 경로가 없다.**
그래서 담당자가 비어 있으면 **PR 작성자**로만 유추한다 (`@techietaek`→이용택, `@whitejh`→김준현, `@agbink`→김은빈).
`lookupJiraAccountId` 로 조회해 **정확히 1명일 때만** 쓴다. 그 외에는 목록에만 적는다.
**PR 이 없는 티켓의 담당자는 절대 유추하지 마라** — 근거가 없다.

**Jira 가 앞서간 경우는 되돌리지 않는다.** Jira 는 `완료` 인데 PR 이 아직 열려 있어도 **PR 을 건드리지 말고 목록에만 적는다** —
사람이 손으로 미리 옮겼을 수 있고, PR 을 닫는 건 리뷰어가 하는 일이다.

**한 PR 이 여러 티켓을 담으면 전부 옮긴다.** PR #26 이 `TRI-51·52·82` 를 담았으면 세 건 다 대상이다.
**하나만 옮기고 끝내면 나머지가 영원히 검토 중으로 남는다.**

### 3. 보여주고 확인받은 뒤에 옮긴다

옮기기 전에 **무엇을 옮길지 먼저 보여주고 `AskUserQuestion` 으로 확인받는다.** 여러 건을 말없이 전환하지 않는다.

```text
■ Jira 로 옮길 것 3건
    TRI-51 — PR #26 머지됨 → 완료
    TRI-52 — PR #26 머지됨 → 완료
    TRI-82 — PR #26 머지됨 → 완료
■ 손대지 않는 것
    TRI-47 — #21 은 머지됐지만 같은 티켓의 #30 이 아직 열려 있음 (예외 1)
    TRI-38 — #18 머지됨. 그런데 형제 TRI-37·39 는 완료인데 이것만 진행 중 (예외 2)
             → 남의 구역(이용택)이라 대신 옮기지 않고 확인을 넘긴다
    TRI-81 — 검토 중인데 연결된 PR 없음. 어디서 검토 중인지 사람이 안다
    #31·#32 — 머지됐지만 제목에 TRI-번호 없음. 연결선이 없어 대상 아님
```

옮길 게 없으면 **"맞음" 한 줄로 끝낸다.**

## 제약

- **상태 전환은 사람이 고른 뒤에만 한다.** 추천과 `진행 중` 전환을 한 호흡에 처리하지 않는다. 티켓은 팀 공유 상태다
- **구역을 넘지 않는다.** 남의 구역 티켓을 추천하지 않는다. 넘어가야 하면 **두 사람이 합의하고 PR 제목에 `TRI-번호` 로 흔적을 남긴다** — 그건 사람이 하는 일이지 이 커맨드가 하는 일이 아니다
- **남이 잡은 티켓의 담당자를 바꾸지 않는다.** 비어 있는 칸만 채운다
- **계약 A/B/C 를 건드리는 티켓은 합의 여부를 먼저 묻는다.** `DECISIONS.md` 항목이 없으면 "항목이 먼저다" 라고 쓴다
- **선행이 안 끝났으면 추천하지도, 시작하라고 하지도 않는다**
- **없는 건 없다고 쓴다.** 관련 결정이 없으면 "근거 결정: 없음" 이다. 그럴듯한 D-번호를 지어내지 않는다
- **응답시간·절감률·오분류율을 추정해서 쓰지 않는다.** 측정은 본인 실측만 (헌법 「AI 검증 규칙」). 이 커맨드가 다루는 숫자는 **티켓 건수뿐**이다
- **감사 표본이 드러나는 값을 예시에 넣지 않는다.** `reason`·`confidence`·`threshold` 는 blind 다 (D-010)
- **일부만 읽고 판단하지 않는다.** 몇 건을 읽었는지 세고, 다 못 읽었으면 **그 사실을 말한다**
- **코드를 쓰지 않는다.** 구현은 티켓을 받은 사람이 한다

## 이 커맨드가 고장났을 때

멈추지 말고 **즉시 손으로 전환한다.** 도구 때문에 하루가 막히는 게 최악이다.
담당은 구역으로 이미 정해져 있어서, 여기서 잃는 건 편의뿐이다.

- **Atlassian MCP 가 응답 안 하면** → Jira 웹(`https://dingco-1-team-01.atlassian.net`)에서 손으로 카드를 옮기고 **바로 작업을 시작한다.** GitHub 쪽에 맞출 것은 없다 (이슈를 안 쓴다)
- **`/ticket` 자체가 안 돌면** → Jira 보드에서 **담당자 = 나 + 상태 `할 일`** 을 마감일 순으로 보고 하나 고른다. 티켓 본문에 「만들 파일」과 「끝났다고 볼 조건」이 다 있다
- **어느 쪽이든 PR 제목에 `TRI-번호` 를 넣는 것만은 빠뜨리지 마라** — 그게 없으면 나중에 모드 D 가 그 티켓을 영영 못 찾는다
